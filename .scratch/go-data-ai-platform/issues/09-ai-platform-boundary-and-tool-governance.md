# 确定 AI 平台边界与工具治理

Type: grilling
Status: resolved
Blocked by: 02, 04, 06, 07
Part of: ../map.md

## Question

Go AI Platform、Python EnergyAgent 和 Copilot Runtime 各自应拥有哪些状态与责任？需要确定 Investigation、AnalysisRun、Evidence、Finding、Recommendation、Review 和 Approval 的权威存储，Agent Tool API、用户与 Site 授权、服务身份、数据量限制、成本配额、异步执行、取消和恢复、工具审计，以及 Recommendation 到 Command 的安全隔离。

## Comments

- Go `ai-platform-service` 是 Investigation、AnalysisRun、Evidence 引用、Finding、Recommendation 和用户 Review 的唯一长期业务权威。Python EnergyAgent 与 Go `agent-worker` 只拥有可清理、可恢复的 ExecutionAttempt、Lease、Checkpoint 和短期中间结果，不能直接访问业务数据库或自行提交正式结果；候选结果必须经 AI Platform 的 Schema、Scope、Evidence、预算、版本和幂等校验后持久化。Node Copilot Runtime 只负责 CopilotKit/A2UI 协议桥、流式传输和短期连接上下文，不拥有长期业务状态。AI Recommendation 的内容审核属于 AI Platform，但任何设备控制 Approval、Command Intent 和执行状态仍由 Command Service/Governance 拥有。
- Agent Tool API 采用双主体授权。`agent-worker`/EnergyAgent 通过独立 Workload Identity 证明实际调用服务，`ai-platform-service` 为每个 AnalysisRun 和 ExecutionAttempt 签发短期、可撤销、与 Scope、Tool、预算和 Attempt 绑定的 `ToolExecutionGrant`，表达其代表的用户、服务账户或自动化主体。有效权限始终是服务自身能力、发起主体当前授权、Run 固定 Scope 与 Grant 限制的交集；Tool API 每次重新验证资源权威归属、Membership/SiteBinding、Run/Lease 和 Grant 状态。禁止向 Agent 转发浏览器 Access Token、Session Cookie 或 Refresh Token；浏览器离线不终止已持久化的异步运行，但用户或授权关系被正式撤销后，后续 Tool 调用必须停止。所有调用同时审计 initiating principal 与 executing service principal。
- `ai-platform-service` 维护中心化、版本化、允许列表化的 Tool Registry，并作为 Agent 唯一逻辑 Tool Broker；每个 AnalysisRun 固定一个由授权、Scope、分析模板和预算生成的 Tool Manifest，Agent 不能动态发现或调用 Manifest 之外的能力。工具必须窄而类型化，由领域所有者执行并再次验证资源归属和授权；第一版只允许只读查询、受控派生 Dataset/Artifact 创建和 Run 内部候选结果提交，禁止通用 SQL、任意 HTTP、Shell、代码执行、对象路径访问及任何设备控制或 IAM 写入。大结果通过固定 Dataset/Artifact 引用返回，所有结果明确工具版本、完整性、水位、质量、用量和审计信息，禁止静默截断。
- `ai-platform-service` 拥有权威 Budget/Quota Ledger，并在 AnalysisRun 创建时形成不可变预算快照。配额按平台、Environment、Organization、发起主体、分析模板和 Run 分层，实际限制取最严格交集；预算同时覆盖数据扫描、Dataset、Tool 调用、模型 Token/调用、执行时间、Attempt、并发与规范化 Cost Credits。Run 入队前必须原子预留预算，执行期间每次 Tool 和模型调用实时检查并按稳定调用 ID 幂等计量，结束后按实际用量结算并释放未使用预留。预算耗尽时停止新增工作并明确进入 `BUDGET_EXHAUSTED`，禁止静默缩小范围、降低质量或将部分结果发布为完整 Finding；第一版不允许 Agent 在运行中自行追加预算，高成本运行需要显式权限或 Budget Approval。AI 任务使用独立资源池和按 Organization 公平调度，不能影响命令、遥测摄取或在线查询。
- AnalysisRun 是持久化异步资源，创建返回 `202 Accepted`、状态地址与 `statusCursor`。其业务状态采用 `QUEUED → RUNNING → SUCCEEDED/FAILED/CANCELLED/TIMED_OUT/BUDGET_EXHAUSTED/AUTHORIZATION_REVOKED/EXPIRED`，取消必须经过 `CANCELLATION_REQUESTED`；所有终态不可重新打开，重试创建新的关联 Run。任务允许至少一次投递，但同一时刻仅一个 ExecutionAttempt 持有有效 Lease、递增 Fencing Token 和 Attempt 专属 Tool Grant；旧 Attempt 失去 Lease 后不能继续调用 Tool、消费预算、续写 Checkpoint 或提交结果。Checkpoint 只能使用版本化、无凭证、不可执行的结构化格式，并仅在工作流、Scope、Dataset、Tool、模型与预算版本兼容时恢复。正式结果由 AI Platform 在验证当前围栏、预算、Evidence、Schema、取消与 Deadline 后原子提交；取消、完成、超时与接管竞争由事务确定唯一结果，浏览器或 Copilot Runtime 断线不得自动取消或重建 Run。
- `ai-platform-service` 保存类型化 Provenance Graph，将 AnalysisRun、ExecutionAttempt、ToolCall、ModelCall、Dataset/Artifact、Evidence、Finding、Recommendation 与 Review 关联起来；关键安全和状态事件通过本地 Outbox 进入独立防篡改 Audit Ledger。模型输出本身不能作为 Evidence，正式 Evidence 必须引用固定 Dataset/Artifact 或领域权威资源，并包含 revision、内容哈希、范围、水位、质量、定义版本和产生它的 ToolCall；Finding 的关键 Claim 必须显式关联 Evidence，Recommendation 必须关联 Finding。默认只保存 Prompt/工作流版本、结构化输入引用、参数、用量、输出 Schema 和哈希，不永久保存完整 Prompt、模型隐藏推理或凭证；完整 Payload 仅在明确政策下加密、短期、受限保存。历史结果不因数据或算法修订被静默覆盖，而通过 invalidation、supersede 和新的 AnalysisRun 建立血缘；平台只承诺数据可重现和工作流可重放，不对外部模型输出承诺完全确定性复现。
- AI Platform 只能生成结构化、不可执行的 Recommendation 与 Canonical ProposedAction，禁止 EnergyAgent、`agent-worker`、Copilot Runtime 或 Tool Broker 直接创建 Command、调用 ThingsBoard RPC 或持有控制凭证。Recommendation 的 Review/接受只表示内容审核，不等于控制 Approval。第一版任何设备控制都必须由当前用户显式提交，并由 Command Service 使用当前身份重新验证 Organization/Site 权限、目标归属、Device Binding、Canonical Capability、参数单位与范围、遥测新鲜度、并发状态、风险及审批策略；控制请求必须绑定 Recommendation 及其 revision，过期、失效或已变化的建议不得执行。未来自动执行只能由预先批准的确定性 Automation Policy 经 Automation Service 调用 Command Service，Agent 仍无控制能力。Command Service 始终拥有 Command Intent、执行和结果状态，`OUTCOME_UNKNOWN` 不得触发 AI 自动重试；Recommendation、CommandRequest 与 Command 之间必须保留完整审计血缘。
- 正式 Finding 和 Recommendation 使用不可变内容 revision；Agent 只提交 Candidate Result，AI Platform 校验后创建正式资源，任何 Claim、Evidence、Scope、风险或 ProposedAction 变化都必须产生新 revision 或新资源。Review 是绑定目标 ID 与 revision 的独立追加式资源，决策采用 `ACCEPTED/REJECTED/NEEDS_MORE_EVIDENCE/NOT_APPLICABLE/DEFERRED`，当前 disposition 由版本化 Review Policy 确定，旧 Review 不自动继承到新 revision。内容生命周期使用 `ACTIVE/SUPERSEDED/INVALIDATED/EXPIRED/RESOLVED/ARCHIVED`，并与 Review disposition 和实施状态严格分离；Evidence 或数据缺陷通过 invalidation 传播，历史资源和 Review 不得被静默覆盖或删除。Recommendation 的实施状态由 CommandRequest/Command 投影独立维护，执行失败不能反向改写内容审核结论。所有审核、修订、失效和控制交接必须使用当前授权、revision 前置条件和完整审计。
- Copilot Runtime 只能部署在 `platform-gateway` 后，使用自身 Workload Identity 和 AI Platform 签发的短期、Scope 受限 `InteractionGrant`，不得接收或转发浏览器 Access Token、Session Cookie 或 Refresh Token。需要持久化的 Conversation 与 InteractionTurn 由 `ai-platform-service` 拥有，Copilot Runtime 只保存流式缓冲、关联 ID 和短期连接状态。页面路由、active Site、选中资源、用户消息、Tool 文本和模型输出全部视为不可信交互内容，只能作为请求提示，不能改变授权、Run Scope、Tool Manifest、预算或系统策略。A2UI 只允许类型化组件和受控 Intent，禁止任意 HTML、JavaScript、内部 API 请求及直接控制动作；自然语言确认最多打开结构化业务表单，不能直接创建 Review、Approval 或 Command。流式断开不取消或重建后台 Run，对话内容也不自动成为 Evidence；对话与附件必须执行数据最小化、大小限制、Scope 授权、保留/删除和敏感信息治理。
- 模型调用统一经过 AI Platform 受治理的 Model Policy/Adapter 边界；EnergyAgent 不得持有供应商凭证、直接访问模型 Endpoint 或自行选择供应商、区域和具体模型。每个 AnalysisRun 固定版本化 `ModelPolicySnapshot`，声明能力类别、允许数据分类、区域、上下文与输出上限、成本等级、保留/训练政策及有限回退链；实际模型由确定性路由策略选择并完整记录。模型输入必须执行 Scope 约束、数据分类和最小化，`RESTRICTED` 数据默认不得发送到外部模型，跨区域或不满足保留政策的回退禁止静默发生。任何回退都必须使用已评估、语义兼容且预算允许的部署并记录原因。供应商响应必须通过运行时 Schema、Evidence、单位、范围和 Canonical Action 校验后才能成为 Candidate Result；模型不能作出授权、预算、Review Policy 或 Command 安全决策。模型、Prompt 和路由政策变更必须经过版本化评估、影子运行、灰度与 Kill Switch 治理，自托管模型也遵循同一规则。
- Go AI Platform、`agent-worker`、Python EnergyAgent 与 Copilot Runtime 使用相互分离、契约优先的协议。队列只传递 AnalysisRun 引用和所需版本，Worker 取得 Lease 后从 AI Platform 读取不可变、绑定 Attempt 与 Fencing Token 的 `AgentExecutionSpec`。`agent-worker` 与 EnergyAgent 第一版采用 Protobuf/gRPC v1 执行协议，EnergyAgent 必须声明支持的协议、工作流、Checkpoint 和结果 Schema 版本；执行流只传类型化进度和 Artifact 引用，正式 Candidate Result 通过受控提交 API 交给 AI Platform 校验并原子持久化。Run 创建时固定工作流、Tool、模型、Prompt、Checkpoint 与结果契约版本，恢复和重试不得静默升级；发布采用新旧版本并行、能力路由和旧 Run 排空，不要求 Go、Python、Node 与前端锁步上线。Copilot Runtime 只使用 Interaction/A2UI 业务契约，不能访问 Agent 执行、Lease、Fencing、Checkpoint 或结果提交接口。所有跨语言类型由仓库内 Protobuf/OpenAPI/JSON Schema 生成并通过兼容性检测和跨语言契约测试，禁止共享数据库实体、LangGraph State 或供应商专有对象。
- AnalysisRun 的执行状态与分析结果质量严格分离；`SUCCEEDED` 只表示工作流、校验和持久化成功，另以 `FINDINGS_AVAILABLE/NO_MATERIAL_FINDING/INSUFFICIENT_EVIDENCE/DATA_QUALITY_BLOCKED/INCONCLUSIVE` 表达 Result Disposition。每个分析模板固定版本化 QualityGatePolicy，由确定性代码检查 Dataset 完整性、覆盖率、时间范围、单位、资源 Scope、Evidence、Claim 支持、Recommendation 条件和治理状态；Finding 与 Recommendation 数量允许为零，禁止为满足输出数量制造结论。模型自报 confidence 不能直接作为概率或安全信号，正式置信等级由数据质量、Evidence 强度、一致性、替代假设和经过校准的评估政策计算，并与控制风险严格分离。无法验证的资源 ID、无 Evidence Claim、静默截断、错误单位或越权引用必须被拒绝；证据不足、数据阻断和矛盾结果应被明确表达，而不能通过模型重试或措辞包装成正式 Finding。质量版本、线上指标与评估集必须支持回归检测、灰度、失效标记和 Kill Switch。
- Investigation、Conversation、AnalysisRun、Evidence、Finding、Recommendation 与 Review 均由 owning Organization 拥有，并绑定服务端解析的最大资源 Scope 与数据分类；创建者只作为发起主体，不拥有绕过当前 IAM 的永久个人访问权。新资源默认 `RESTRICTED`，可通过显式、审计化操作发布为 `SITE_SCOPED` 或 `ORGANIZATION_SCOPED`，第一版不支持匿名或链接分享。人工访问始终取当前 Membership、RoleBinding、SiteBinding、资源 Scope、数据分类与 AI Collaboration Grant 的交集；Collaboration Grant 只表达 `VIEWER/CONTRIBUTOR/REVIEWER/INVESTIGATION_MANAGER` 等协作角色，不能创造用户原本没有的租户或 Site 权限。跨 Site 正式结果要求访问者拥有全部相关 Scope，缺少部分权限时拒绝整个资源，不静默裁剪 Evidence；跨 Organization 协作同时要求 IAM 跨组织授权和显式 AI 协作授权。Conversation、Dataset、正式结果、导出、Review、诊断与控制交接分别授权，ToolExecutionGrant 与 InteractionGrant 不得用于人工数据访问。列表、搜索、通知、实时事件和统计同样执行存在性保护与当前授权检查，权限撤销后旧 Session、Cursor 和订阅不得继续访问。
- AI Platform、`agent-worker`、EnergyAgent、Copilot Runtime、模型调用与 AI Tool 查询必须使用独立资源池、队列、连接池、并发预算和优先级，AI 批处理流量优先降级，不能影响 Command、Telemetry Ingest、IAM 或在线查询。平台对模型部署、Tool 版本、工作流/Prompt、Organization 与全 AI 平面提供版本化、可审计的 Circuit Breaker 和 Kill Switch，支持 `BLOCK_NEW/DRAIN/ABORT_ACTIVE/READ_ONLY`；Worker 在续租、Tool 和模型调用时重新验证，不能依赖陈旧缓存。队列有界并执行 Admission Control、Queue Deadline、Organization 公平调度及恢复限速；依赖故障只能按模板定义的必需/可选能力降级，禁止绕过 Dataset、Evidence、授权、预算、模型区域或审计门禁产生“降级正式结果”。AI 计算平面故障时已有正式资源应尽量保持只读可用；安全、跨租户或合规风险结果进入 `QUARANTINED` 并阻止普通 Review 发布与 Command 交接。恢复后必须按 Run、Attempt、Fencing Token、ToolCall、ModelCall、Budget 和 Outbox 进行权威对账，使用稳定 ID 恢复或清理，不能重复执行或形成重试风暴。
- AI 数据按 `EPHEMERAL_EXECUTION/CHECKPOINT/SHORT_DIAGNOSTIC/INVESTIGATION_WORKING_SET/BUSINESS_RECORD/IMMUTABLE_AUDIT` 分类，并在创建时固定版本化 `RetentionPolicySnapshot`；具体期限由平台、Organization、数据分类、资源类型与合规政策配置，不散落在服务代码中。Checkpoint、Grant、流式缓冲、失败 Candidate 与完整模型诊断采用短期保留，正式 Finding、Recommendation、Review、必要 Provenance 和审计摘要按业务政策长期保留；大型 Dataset 和原始 Payload 可以到期，但必须保留最小 Manifest、内容哈希、Tombstone 及其对 Evidence 可用性和结果有效性的影响，不能继续声称完全可重现。删除采用异步、幂等、引用感知的状态机，覆盖数据库、对象存储、搜索、缓存、导出和供应商 Payload；删除失败明确进入 `PARTIALLY_DELETED`，备份恢复后重放 Deletion Ledger。Conversation 删除不自动删除正式结果，被提升为 Evidence 的 Turn 必须形成独立 Snapshot。Legal Hold 只能暂停删除，不能扩大访问或解除隔离。生产客户数据默认不得用于供应商训练或自动进入内部训练/评估集，任何此类用途必须经过独立的数据治理流程。
- AI 平面采用分层 SLI/SLO，分别衡量北向只读与写 API、Copilot 交互、Queue Admission 与公平等待、按模板服务等级划分的 AnalysisRun 完成、Tool/模型调用、预算结算、数据质量、结果质量、Provenance 完整性和 Audit 传播；`99.9%` 作为异步 AI 服务可用性基线，具体延迟与完成目标通过容量测试配置。状态机、租户隔离、Fencing、预算上限、Evidence 完整性、授权撤销与 Command 隔离是硬不变量，不以 Error Budget 容忍。所有同步和异步步骤通过 Trace Context 与 Run、Attempt、ToolCall、ModelCall、Dataset 和结果 ID 关联，日志与指标执行敏感数据最小化和高基数控制。SLO 排除规则必须预先版本化，供应商、容量和发布故障不得事后任意排除；质量、成本和可靠性指标按 Workflow、Prompt、ModelPolicy、实际模型、Tool Manifest 与 QualityGate 版本切分，并由合成探测、灰度比较、Error Budget 和 Kill Switch 驱动发布。AI Platform 团队拥有端到端 Run 与正式 AI 业务状态并承担首轮事故协调，Agent Runtime、Copilot、领域服务、IAM/安全、Command 与 SRE 分别拥有其执行、交互、领域数据、授权、控制和基础设施边界，每个告警必须有明确 Owner 与 Runbook。
- Investigation 是长期权威聚合，生命周期使用 `OPEN/RESOLVED/CLOSED/ARCHIVED/QUARANTINED`，运行、审核和实施状态作为独立维度，Scope 使用不可变 revision。分析按服务端定义的 Lane 管理，每个 Lane 同一时刻最多一个 Active Run，并使用单调递增 Generation；已有 Active Run 时，新建请求默认冲突，只有显式 `replaceActive` 才能在事务中创建新 Run、更新 Active Pointer 并请求取消旧 Run。AnalysisRun 执行状态与结果提升严格分离，只有仍匹配当前 Active Run、Generation、Scope Revision 和 Lane Policy 的成功结果才能原子生成新的 Investigation Result Set 并成为当前结果；迟到或被取代的成功结果完整保留，但标记为 `NOT_PROMOTED_STALE`，不得按完成时间、事件顺序或新 Run 失败而自动覆盖或复活。`latestSuccessfulRun`、`activeRun` 和 `currentResultSourceRun` 分别维护。Investigation 的解决、关闭、归档、隔离与重新打开必须由显式、当前授权且带 revision 前置条件的业务动作完成，不能由模型、Run 成功或 Command 成功自动推进；只有当前有效 Result Set 中的 Recommendation 才可进入新的控制交接。

## Answer

Go `ai-platform-service` 是 AI 业务控制平面和唯一长期权威，拥有 Investigation、Conversation、AnalysisRun、Evidence 引用、Finding、Recommendation、Review、预算账本、Provenance、结果版本与生命周期。`agent-worker` 和 Python EnergyAgent 只执行由平台签发的短期 Attempt，拥有 Lease、Fencing Token、Checkpoint 与可清理中间结果；Copilot Runtime 只承担 Interaction/A2UI 协议桥、流式连接和短期缓冲。任何组件都不得共享业务数据库、浏览器凭证或 ThingsBoard 控制凭证。

Agent 只能通过 AI Platform 的中心化 Tool Registry/Tool Broker 使用版本化、窄类型、允许列表化的 Tool。每个 Run 固定 Tool Manifest、Scope、预算、模型、工作流和结果契约；双主体授权同时验证发起主体与执行服务，领域服务再次确认资源权威归属。第一版仅允许只读查询、受控 Dataset/Artifact 创建及候选结果提交，禁止通用 SQL、任意 HTTP、Shell、代码执行、直接对象路径、IAM 写入和设备控制。

AnalysisRun 是可取消、可恢复的持久化异步资源，采用至少一次投递、单一有效 Attempt Lease、递增 Fencing Token、版本化 Checkpoint 和原子结果提交。执行状态与结果质量、结果提升分别建模；预算覆盖数据扫描、Tool、模型、时间、Attempt、并发与 Cost Credits，并在入队前原子预留、运行中幂等计量。迟到或被取代的 Run 可以保留历史结果，但不得覆盖当前 Investigation Result Set。

正式结果必须通过确定性 Schema、Scope、Evidence、质量、预算和治理门禁。模型输出不是 Evidence；Finding 的关键 Claim 必须引用固定 Dataset/Artifact 或领域权威资源，Recommendation 必须关联 Finding。Review 绑定不可变内容 revision 并追加保存；执行状态、内容状态、Review disposition 和控制实施状态相互独立。允许 `NO_MATERIAL_FINDING`、`INSUFFICIENT_EVIDENCE`、`DATA_QUALITY_BLOCKED` 和 `INCONCLUSIVE`，禁止为满足输出数量制造结论。

Recommendation 只能包含不可执行的 Canonical ProposedAction。接受 Recommendation 不等于 Command Approval；任何控制均由当前用户或预先批准的确定性 Automation Policy 显式发起，并由 Command Service 基于当前身份、Site 归属、Device Binding、Capability、单位、范围、新鲜度、风险和审批重新验证。EnergyAgent、agent-worker、Copilot Runtime 和 Tool Broker 永远不能直接创建 Command 或调用 ThingsBoard RPC。

模型调用经过受治理的 Model Policy/Adapter，执行数据分类、区域、保留、训练、成本、有限回退和质量评估。AI 平面使用独立资源池、队列、熔断和 Kill Switch，不影响 Command、Telemetry Ingest、IAM 或在线查询。Conversation、Dataset、Checkpoint、诊断、业务记录与审计按版本化 Retention Policy 分别保留和删除；安全风险结果进入 `QUARANTINED`。跨语言协议由 Protobuf/OpenAPI/JSON Schema 生成并执行兼容性测试，所有关键状态、授权、用量、Evidence 和控制交接均形成可追溯审计链。
