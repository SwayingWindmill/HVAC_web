# 智慧能源系统非功能需求与容量规划设计

## 一、设计目标

前面已经定义了：

```text
Device
→ Point
→ Telemetry
→ Metric
→ Energy
→ Optimization
→ Control
```

非功能需求解决的是另一组问题：

```text
系统能承载多少？

响应有多快？

数据能不能丢？

故障多久恢复？

设备增加十倍怎么办？

数据库能存多久？

网络断开怎么办？

控制多久必须有结果？
```

因此非功能需求不是“附加要求”，而是决定：

```text
数据库架构
消息架构
边缘架构
部署架构
缓存策略
数据保留策略
扩容策略
```

的基础。

整个容量规划建议围绕以下核心指标展开：

```text
Site Count

Gateway Count

Device Count

Point Count

Telemetry Values / Second

MQTT Messages / Second

Storage / Day

API QPS

WebSocket Connections

Command Rate

Retention

Availability

RPO / RTO
```

---

# 二、容量规划最重要的原则

智慧能源系统不能只按照：

```text
有多少用户？
```

规划容量。

真正决定系统压力的通常是：

```text
Point 数量
×
采样频率
×
数据保存周期
```

例如：

```text
100,000 Points
```

如果每：

```text
60 秒
```

采一次，与每：

```text
1 秒
```

采一次，对系统压力相差：

```text
60 倍
```

因此最核心的容量指标应该是：

# Effective Telemetry Rate

即：

```text
有效测点值 / 秒
```

简称：

```text
Values Per Second
```

---

# 三、Telemetry 吞吐计算模型

如果所有 Point 采样周期一样：

```text
Values/s
=
Point Count / Sampling Interval
```

例如：

```text
100,000 Points

Sampling = 10s
```

则：

```text
10,000 values/s
```

每天：

```text
10,000 × 86,400

= 864,000,000 values/day
```

也就是：

```text
8.64 亿条测点值 / 天
```

---

# 四、实际系统不能简单使用总 Point 数

实际平台通常是混合采样。

例如：

```text
20,000 Points
每 5 秒

30,000 Points
每 10 秒

50,000 Points
每 60 秒
```

则：

```text
20,000 / 5
+
30,000 / 10
+
50,000 / 60
```

得到约：

```text
7,833 values/s
```

每天约：

```text
676,800,000 values
```

即：

```text
约 6.77 亿 values/day
```

因此平台应该长期维护一个指标：

```text
telemetry_values_per_second
```

而不是只知道：

```text
point_count
```

---

# 五、Point 数和 Telemetry 数必须分开

例如一个 Site 有：

```text
100,000 Points
```

不代表所有 Point 都持续产生时序数据。

其中可能：

```text
70,000 TELEMETRY

10,000 COUNTER

10,000 STATE

5,000 SETTING

5,000 COMMAND
```

真正高频产生历史数据的主要是：

```text
TELEMETRY

COUNTER

STATE
```

因此容量模型应进一步按 Point Type 分类。

---

# 六、推荐采样基线

第一版可以采用下面的设计参考：

|数据类型|推荐采样周期|
|---|--:|
|实时总功率|1～5s|
|PCS 功率|1～5s|
|电流、电压|5～10s|
|SOC|5～10s|
|SOH|30～300s|
|温度|10～30s|
|水压、流量|10～30s|
|累计电量|30～60s|
|设备运行状态|状态变化 + 周期刷新|
|设备配置|变化时|
|铭牌信息|初始化/变化时|

原则是：

# 业务需要多快，就采多快。

而不是：

# 能采 1 秒就全部采 1 秒。

---

# 七、采集频率与上传频率分离

建议明确：

```text
Polling Interval
```

与：

```text
Upload Interval
```

不是一回事。

例如 Edge：

```text
每 1 秒读取 PCS
```

但 Cloud：

```text
每 5 秒上传一个 Batch
```

这 5 秒内可以保留：

```text
AVG

MIN

MAX

LAST
```

或者根据业务保留全部 1 秒数据。

这样可以减少：

```text
MQTT Message Rate
```

同时保持现场采集精度。

---

# 八、MQTT Message Rate

除了：

```text
values/s
```

还需要计算：

```text
messages/s
```

假设：

```text
1 Device = 50 Points
```

设备每：

```text
5s
```

上传一个 Batch。

10,000 台设备则：

```text
10,000 / 5
=
2,000 messages/s
```

但一条 Message 可能包含：

```text
50 values
```

因此：

```text
messages/s
```

与：

```text
values/s
```

必须分别监控。

---

# 九、推荐 MQTT 批量消息

不要：

```text
一个 Point
=
一条 MQTT Message
```

推荐：

```text
一个 Device
+
一个 Timestamp
+
多个 Points
=
一条 Message
```

例如：

```json
{
  "ts": 1786197600000,
  "seq": 123456,
  "points": {
    "active_power": 126.4,
    "voltage_a": 382.1,
    "voltage_b": 381.8,
    "voltage_c": 382.6,
    "soc": 65.2
  }
}
```

这样 MQTT 的：

```text
Topic

Header

TLS

Broker
```

开销都会明显降低。

---

# 十、数据存储容量计算

Telemetry 存储量可以估算为：

```text
Daily Storage
=
Values Per Day
×
Average Bytes Per Value
```

但：

```text
Average Bytes Per Value
```

不能拍脑袋确定。

它受到：

```text
Schema

Index

Timestamp

Point ID

Quality

Compression

Database Page

WAL
```

影响。

因此必须通过真实 Schema 做 Benchmark。

---

# 十一、规划阶段的存储系数

规划时可以先设置两个系数：

```text
raw_bytes_per_value
```

和：

```text
compressed_bytes_per_value
```

例如先用：

```text
Raw:
约 80 Bytes / value

Compressed:
约 25 Bytes / value
```

作为**容量估算假设**。

这不是 ClickHouse 固定性能值。

真正数值必须通过实际表结构、索引和压缩策略压测确定。

---

# 十二、存储计算示例

前面的：

```text
7,833 values/s
```

每天：

```text
676,800,000 values
```

如果压缩后实际测得：

```text
25 Bytes / value
```

则一天约：

```text
16.9 GB
```

30 天约：

```text
507 GB
```

这只是：

```text
Telemetry Primary Data
```

还没有计算：

```text
Replica

Backup

WAL

Temporary Space

Indexes

Metric

Logs
```

所以实际服务器磁盘不能按：

```text
507GB
```

直接购买。

---

# 十三、容量安全系数

建议所有生产容量至少保留：

```text
50%
```

以上 Headroom。

例如预计：

```text
1 TB
```

实际不要只准备：

```text
1 TB
```

可以规划：

```text
1.5～2 TB
```

可用空间。

数据库磁盘长期不建议运行到：

```text
95%
```

才扩容。

---

# 十四、磁盘使用阈值

建议：

```text
< 70%
正常
```

```text
70% ～ 80%
Capacity Warning
```

```text
80% ～ 90%
High
```

```text
> 90%
Critical
```

应在：

```text
70%～80%
```

阶段就规划扩容。

---

# 十五、数据生命周期

推荐采用：

```text
Raw
→ Downsample
→ Aggregate
→ Archive
```

的数据生命周期。

例如：

|数据层|示例粒度|推荐用途|
|---|--:|---|
|Raw|1～5s|故障分析、近期趋势|
|Fine Aggregate|1min|日常历史查询|
|Business Aggregate|15min|EMS、需量、电价|
|Long-term Aggregate|1h|长期趋势|
|Metric|Day/Month|KPI、报告、财务|

---

# 十六、第一版保留策略

一个参考策略：

```text
Raw 1～5s

保留 30～90 天
```

```text
1min

保留 1～2 年
```

```text
15min

保留 3～5 年
```

```text
1hour

长期保存
```

```text
Daily / Monthly Metric

长期保存
```

具体保留时间由：

```text
合同

法规

客户要求

成本

分析需求
```

决定。

---

# 十七、为什么不建议永久保存全部 1 秒 Raw

假设：

```text
1,000,000 Points
```

全部每秒采集。

就是：

```text
1,000,000 values/s
```

每天：

```text
86.4 billion values
```

即：

```text
864 亿 values/day
```

长期保存成本会非常高。

所以必须从架构层建立：

```text
Sampling Policy

Retention Policy

Aggregation Policy
```

不能等数据库满了才处理。

---

# 十八、冷热数据分层

建议：

```text
HOT
```

保存最近：

```text
7～30 天
```

高频数据。

主要用于：

```text
实时趋势

故障排查
```

---

```text
WARM
```

保存：

```text
1min / 15min
```

聚合数据。

用于：

```text
EMS

历史分析

报告
```

---

```text
COLD
```

保存长期归档。

可以进入：

```text
Object Storage
```

降低成本。

---

# 十九、指标数据容量

Metric 数据通常远小于 Raw Telemetry。

例如：

```text
100,000 Points
```

可能最终只有：

```text
10,000 Assets
×
数十个 Metrics
```

按：

```text
15min / day / month
```

保存。

因此：

```text
Raw Telemetry
```

一般才是容量规划的主要对象。

可以定义三个参考等级。

## Small

例如：

```text
Site:
≤ 20

Gateway:
≤ 100

Device:
≤ 2,000

Point:
≤ 100,000

Effective Telemetry:
≤ 5,000 values/s
```

适合：

```text
Docker Compose
+
独立 PostgreSQL/ClickHouse
+
Redis
+
单节点或双节点 MQTT
```

---

# 二十一、Medium

参考：

```text
Site:
20～200

Gateway:
100～2,000

Device:
2,000～20,000

Point:
100,000～1,000,000

Telemetry:
5,000～50,000 values/s
```

通常需要：

```text
独立数据库服务器

多个 API 实例

多个 Telemetry Worker

MQTT HA

数据库 Replica

集中监控
```

并评估：

```text
Kafka
```

是否有必要。

# 二十二、Large

参考：

```text
Site:
200+

Gateway:
2,000+

Device:
20,000+

Point:
1,000,000+

Telemetry:
50,000～100,000+ values/s
```

通常进入：

```text
分布式消息系统

多 Worker

MQTT Cluster

Database HA

冷热分层

对象存储

容器编排

灾备
```

范围。

这些数字只是架构分级参考，不是固定产品上限。

---

# 二十三、扩容不能只按照 Point Count

两个系统：

```text
System A:
1,000,000 Points
Sampling 60s
```

和：

```text
System B:
200,000 Points
Sampling 1s
```

System B 的实时压力可能反而更大。

所以真正的容量 Dashboard 应显示：

```text
Total Points

Active Points

Values/s

Messages/s

Storage/day

Query QPS
```

---

# 二十四、API 性能目标

第一版建议定义 P95 指标，而不是只定义平均值。

例如：

|API 类型|P95 目标|
|---|--:|
|登录/普通 CRUD|< 500ms|
|Site/Asset 查询|< 500ms|
|Latest Telemetry|< 300ms|
|Energy Overview|< 1s|
|24h 趋势|< 1s|
|7～30 天聚合趋势|< 2s|
|Alarm List|< 1s|
|Command Create|< 500ms|

这是设计目标。

实际验收需要结合数据规模和部署规格确定。

---

# 二十五、为什么使用 P95

假设：

```text
平均响应 = 200ms
```

但：

```text
20% 请求 = 5s
```

平均值仍可能看起来不错。

所以应主要观察：

```text
P50

P95

P99
```

特别是：

```text
P95
```

与：

```text
P99
```

---

# 二十六、历史查询保护

前端不能随意发：

```text
pointId = xxx

from = 2020

to = 2026

interval = raw
```

然后扫描几年 5 秒数据。

API 应设置：

```text
Query Guardrail
```

---

# 二十七、查询粒度自动选择

例如：

```text
≤ 24h
```

可以：

```text
Raw / 1min
```

```text
1～7 days
```

使用：

```text
1min / 15min
```

```text
7～90 days
```

使用：

```text
15min / 1h
```

```text
> 90 days
```

优先：

```text
1h / Daily
```

---

# 二十八、前端单次点数限制

趋势图通常不需要：

```text
100,000 个点
```

直接返回浏览器。

例如一张图控制在：

```text
500～2,000 samples
```

通常已经足够。

后端可以自动：

```text
Downsample
```

---

# 二十九、Latest API 批量限制

例如：

```text
POST /telemetry/latest
```

建议允许批量请求。

但单次可以限制：

```text
≤ 500～1,000 Point IDs
```

避免一个页面一次请求：

```text
100,000 Points
```

---

# 三十、列表 API

所有大列表：

```text
Devices

Assets

Alarms

Commands
```

必须分页。

不允许：

```text
GET /devices
```

直接返回：

```text
100,000 Devices
```

---

# 三十一、WebSocket 容量

实时 Dashboard 需要重点规划：

```text
Concurrent Connections
```

和：

```text
Messages/s
```

不能只规划 HTTP QPS。

例如：

```text
1,000 在线浏览器
```

每个浏览器订阅：

```text
100 Points
```

并且每秒都更新。

潜在推送量就是：

```text
100,000 value updates/s
```

---

# 三十二、WebSocket 不应该直接镜像所有 Point

建议前端主要订阅：

```text
Site Overview

Asset Summary

Realtime Metric
```

而不是：

```text
一个用户订阅 20,000 个原始 Point。
```

实时大屏使用：

```text
业务聚合结果
```

更合理。

---

# 三十三、WebSocket Subscription 模型

建议：

```text
site:{id}:overview

asset:{id}:realtime

device:{id}:realtime

point:{id}
```

其中：

```text
point
```

级订阅主要用于：

```text
设备调试页面
```

而不是 Dashboard 主页面。

---

# 三十四、Realtime 延迟目标

可以定义：

```text
Device Timestamp
→
React Display
```

端到端延迟。

普通能源监控：

```text
P95 < 5s
```

重要实时场景：

```text
P95 < 2s
```

具体取决于：

```text
设备采样周期
+
Edge Upload
+
MQTT
+
Cloud Processing
+
WebSocket
```

---

# 三十五、Telemetry Ingestion 延迟

建议定义：

```text
Telemetry Processing Lag
```

即：

```text
Cloud Process Time
-
Event Time
```

目标例如：

```text
P95 < 5s
```

如果：

```text
P95 > 30s
```

应认为数据链路出现明显积压。

---

# 三十六、告警检测延迟

关键实时规则：

```text
事件到达 Cloud
→
Alarm Created
```

可以设计：

```text
P95 < 3s
```

但如果规则本身要求：

```text
持续 60 秒
```

这 60 秒属于：

```text
Rule Duration
```

不应该计算为系统处理延迟。

---

# 三十七、Control 性能目标

控制链路需要拆开。

## Command Creation

```text
React
→
Control Service
```

例如：

```text
P95 < 500ms
```

---

## Cloud → Gateway

在正常网络条件下，可以设目标：

```text
P95 < 2s
```

---

## Gateway → Device

根据协议和设备不同。

例如：

```text
Modbus
```

可能是：

```text
几十～几百毫秒
```

但某些设备动作本身需要几秒。

因此不能统一定义：

```text
所有控制 1 秒完成。
```

---

# 三十八、Command 最重要的是状态，而不是绝对速度

必须区分：

```text
CREATED

SENT

DEVICE_ACK

EXECUTED

VERIFIED
```

一个：

```text
START_CHILLER
```

可能需要：

```text
几十秒
```

才能验证真正运行。

而：

```text
SET_POWER
```

可能几秒内达到目标。

所以：

```text
command_timeout
```

和：

```text
verification_window
```

应该按 Command Template 定义。

---

# 三十九、可用性目标

建议按能力分别定义。

第一版生产设计可以参考：

```text
Web / EMS:
99.9%
```

```text
Telemetry Ingestion:
99.9%+
```

```text
Alarm Platform:
99.9%
```

```text
Control Cloud:
99.9%+
```

但现场安全不能依赖这些数字。

因为即使 Cloud 不可用：

```text
Edge
+
PLC
+
BMS
```

仍必须保证现场安全。

---

# 四十、系统可用性必须分层

不要只定义：

```text
Platform Availability
```

而应该定义：

```text
Web Availability

API Availability

Telemetry Availability

MQTT Availability

Alarm Availability

Control Availability

Edge Availability
```

例如：

```text
报表系统故障
```

不应该被算成：

```text
设备采集系统故障。
```

---

# 四十一、Graceful Degradation

系统应该支持降级运行。

例如：

```text
Optimization Down
```

仍然：

```text
EMS 正常
Telemetry 正常
Control Manual 正常
```

---

```text
Report Down
```

仍然：

```text
Realtime Monitoring 正常
```

---

```text
Cloud Down
```

仍然：

```text
Edge Collection 正常
Local Safety 正常
```

---

建议：

```text
P0
```

包括：

```text
Edge Safety

Device Acquisition

Control Safety

Command Audit
```

---

```text
P1
```

包括：

```text
Realtime EMS

```

---

```text
P2
```

包括：

```text

```

---


包括：

```text

```

---

# 四十三、可靠性目标

Telemetry Pipeline 应具备：

```text
Retry

Idempotency

Deduplication

Late Data

Out-of-order Data

Store & Forward
```

能力。

---

# 四十四、数据不应依赖 Exactly Once 假设

IoT 环境中更实际的设计是：

```text
At-least-once Delivery
+
Idempotent Processing
+
Deduplication
```

因为：

```text
网络重连

Gateway Replay

MQTT Retry
```

都可能产生重复数据。

---

# 四十五、Telemetry 幂等键

可以使用：

```text
Gateway ID
+
Device ID
+
Sequence
+
Timestamp
```

或者更精确的数据标识。

重点是：

```text
同一批数据重复上传
```

不能被无条件保存多次。

---

# 四十六、迟到数据目标

建议提前定义：

```text
Maximum Accepted Late Data
```

例如：

```text
7 days
```

或者：

```text
30 days
```

超出之后是否仍允许补传，需要按照项目规定。

---

# 四十七、Edge Offline Buffer

边缘网关需要明确：

```text
Offline Buffer Duration
```

第一版可以规划：

```text
至少 3～7 天
```

关键场景可以：

```text
7～30 天
```

具体取决于：

```text
Local Disk

Values/s

数据重要性
```

---

# 四十八、Edge 缓存容量计算

例如一个 Gateway：

```text
2,000 values/s
```

假设本地编码后：

```text
30 Bytes/value
```

一天约：

```text
5.18 GB
```

7 天大约：

```text
36 GB
```

再考虑：

```text
索引

日志

数据库空间

安全余量
```

就不能只配：

```text
32 GB Disk
```

---

# 四十九、Edge Disk 规划

网关磁盘应同时考虑：

```text
Operating System

Logs

Configuration

Telemetry Cache

OTA Package

Temporary Files
```

所以不能把全部磁盘容量给 Telemetry。

建议至少保留：

```text
20%～30%
```

安全空间。

---

# 五十、恢复目标 RPO

RPO 回答：

> 发生灾难时最多允许丢多少数据？

不同数据类型应不同。

---

# 五十一、业务主数据 RPO

例如：

```text
Tenant

Site

Asset

Device

Point

Tariff

Safety Policy
```

建议目标：

```text
RPO ≤ 5min
```

关键配置甚至应接近：

```text
0
```

---

# 五十二、Command / Audit RPO

对于已经被平台接受的关键控制：

推荐设计目标：

```text
RPO = 0
```

含义不是“数据库永远不坏”，而是：

# Command 没有可靠持久化，就不能向设备下发。

即：

```text
Persist
↓
Commit
↓
Dispatch
```

不能：

```text
Dispatch
↓
以后再写数据库
```

---

# 五十三、Telemetry RPO

Cloud 中心数据库可以例如：

```text
RPO ≤ 15min
```

但由于存在：

```text
Edge Store & Forward
```

Cloud 故障期间现场采集数据仍可补传。

所以应区分：

```text
Central Database RPO
```

和：

```text
Physical Acquisition Data Loss
```

---

# 五十四、RTO

RTO 回答：

> 故障以后多久恢复？

可以参考：

|能力|RTO 设计目标|
|---|--:|
|Control Cloud|≤ 15～30min|
|MQTT / IoT Ingestion|≤ 30min|
|EMS API|≤ 1h|
|PostgreSQL Primary|≤ 1h|
|Historical Reporting|≤ 4h|

但现场：

```text
Edge Safety
```

不能等待 Cloud RTO。

必须继续独立运行。

---

# 五十五、Cloud 与 Edge 的容灾关系

因此系统整体可靠性不是：

```text
Cloud 绝不故障
```

而是：

```text
Cloud HA
+
Edge Autonomy
+
Data Replay
```

三者结合。

# 五十六、数据库连接容量


不应该配置：

```text

×
100 connections
=
2,000
```

# 五十九、Redis 容量

Redis 主要按照：

```text

Device State

Rule State

WebSocket State
```

规划。

例如：

```text

```

每个 Latest Value 实际 Redis 占用即使只有几百 Byte：

整体也可能达到：


# 六十、Redis 不保存全部历史



职责必须明确。

不能因为 Redis 快就把大量历史数据都放进去。

# 六十一、MQTT Connection Capacity

需要规划：

```text

```

全部通过：

```text

```

连接 Cloud。

MQTT Broker 看到的主要连接数可能只有：

```text

```

而不是：

```text
10,000
```

具体取决于架构。

# 六十二、MQTT 关键容量指标

至少监控：

```text
Publish Latency

Authentication Rate
```

# 六十三、MQTT 网络带宽

网络规划可以按照：

```text

×
Average Message Size
```

估算。

```text

```

平均 Payload：

```text

```

仅 Payload 就约：

```text

```

还要增加：

```text

TCP

MQTT

Network Overhead
```

以及峰值余量。

# 六十四、峰值因子

容量不能只按平均值。

建议定义：

```text
Peak Factor
```

例如：

```text

```

如果平均：

```text

```

至少验证：

```text

```

甚至更高突发能力。

# 六十五、为什么能源系统会有突发

例如：

```text

```

```text

+
Replay
```

可能瞬间造成：

```text
高于平时数倍
```

流量。

所以系统必须区分：

```text

```

和：

```text
Replay Traffic
```

# 六十六、Replay 限速

Edge 历史补传应该：

```text
Rate Limited
```

例如：

```text
Realtime
优先
```

```text
Replay
后台限速
```

否则恢复网络时容易把整个 Cloud 打满。

# 六十七、重连风暴

MQTT Broker 故障恢复以后：

```text

```

不能全部：

```text

```

立即重连。

```text

+
Jitter
```

避免：

```text

```

# 七十四、Batch 的延迟与吞吐权衡



```text
batch_size
```

和：



# 一百一十、容量规划与成本

# 一百一十一、关键数据优先级



```text

```

因此 Retention 应支持：

```text

```

或：

# 一百一十八、最终设计原则

整个非功能与容量规划建议坚持以下原则：

**第一，不用设备数量代替 Telemetry 吞吐。**

真正核心的是 Values/s。

**第二，不是所有 Point 都应该采用同一个采样周期。**

采样频率由业务价值决定。

**第三，原始数据不能无限长期保存。**

必须从第一天建立 Retention 和 Downsampling。

**第四，规划平均负载的同时必须规划峰值和 Replay。**

网络恢复时的补传往往比正常流量更危险。

**第五，API、Telemetry、WebSocket 和 Control 是四种不同的性能模型。**

不能用一个 QPS 指标描述整个系统。

**第六，容量必须留有 Headroom。**

正常生产不能长期工作在 90%～100% 资源使用率。

**第七，数据库容量必须通过实际 Schema 压测。**

不能只使用理论 Bytes/Row。

**第八，Cloud RPO 与现场数据损失必须分开理解。**

Edge Store & Forward 可以显著降低 Cloud 故障造成的现场数据损失。

**第九，Command 和 Audit 属于特殊数据。**

关键命令必须先可靠持久化，再下发。

**第十，容量规划是持续过程，不是上线前做一次 Excel。**

随着：

```text
Site

Device

Point

Sampling

Retention
```

不断变化，平台必须持续计算容量趋势。

# 一百一十九、最终结论

智慧能源平台的容量不能简单定义成：

```text
支持100万设备
```

真正有意义的能力应该描述为：

```text
支持多少 Site

支持多少 Gateway

支持多少 Active Points

持续支持多少 Values/s

峰值支持多少 Messages/s

Telemetry 延迟是多少

数据能够保存多久

API 在什么规模下保持什么 P95

网络断开能够缓存多久

故障以后多久恢复
```

因此整个非功能目标最终应该形成：

# Capacity + Performance + Reliability + Availability + Recoverability + Scalability

六个维度。

对于目前这套 **Go + React + PostgreSQL/ClickHouse + Redis + MQTT + Edge Gateway** 架构，第一阶段最合理的做法不是一开始追求“百万设备平台”，而是先建立一个明确、可验证的基准，例如：

```text
100,000 Points

5,000～10,000 Values/s

100+ Gateways

1,000+ Devices

100～500 Concurrent Users
```

在这个规模下验证：

```text
连续采集稳定

历史查询稳定

数据不丢

断网可补传

告警及时

控制可靠

数据库可恢复

资源仍有足够余量
```

验证通过后，再逐级扩大到：

```text
500,000 Points

1,000,000 Points

50,000+ Values/s

100,000+ Values/s
```

并根据真实瓶颈逐步引入：

```text
MQTT Cluster

Kafka

Multiple Workers

DB Replica

Storage Tiering

Container Orchestration
```

这样容量架构是由真实数据推动演进，而不是提前堆砌复杂技术。
