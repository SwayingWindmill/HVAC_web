# 智慧能源系统计量、结算与对账规则详细设计

> 版本：V1.0  
> 上位设计：智慧能源系统能源指标体系设计、能源拓扑设计、Point/Metric 标准、ER 模型与数据库表结构设计 V2  
> 技术基线：PostgreSQL + ClickHouse + Redis + Go  
> 适用范围：电力计量、需量、电费、内部能源结算、财务确认、客户/电网账单对账  
> 核心定位：本设计不重复定义 `daily_energy`、`max_demand`、`energy_charge` 等 Metric，而是定义“用什么数据算、什么时候算、何时锁定、错了如何修、如何对账”

---

# 1. 设计目标

已有能源指标体系解决：

```text
Point
→ Telemetry
→ Metric
→ KPI
```

以及：

```text
Metric是什么
公式是什么
单位是什么
时间粒度是什么
质量策略是什么
```

本设计进一步解决：

```text
哪个表是结算依据？
哪个表只是监测依据？

CT/PT倍率在哪里生效？
设备已经乘倍率时平台还能不能再乘？

累计电量清零怎么办？
电表换表怎么办？
Counter rollover怎么办？

缺数时能不能插值？
估算值能不能进财务结算？

峰平谷如何切时间片？
15分钟需量如何对齐窗口？

账单周期怎么定义？
月中电价变更怎么算？

补传数据到了以后自动重算到什么时候？
什么时候必须LOCK？

LOCK之后发现错误怎么办？

系统账单和电网账单差多少算异常？
人工修改如何审批、留痕和回退？
```

# 2. 核心原则

## 2.1 计量事实与指标结果分离

```text
Meter Reading
= 计量事实

Metric
= 计算结果
```

禁止直接把：

```text
人工填的月电量
```

伪装成：

```text
原始电表Telemetry
```

---

## 2.2 结算源必须明确

任何结算对象必须绑定：

```text
Authoritative Meter
```

不能运行时随便选择一个有数据的设备。

---

## 2.3 结算优先使用累计量

优先级保持：

```text
结算电表累计值
>
设备累计值
>
功率积分
>
估算
```

如果已有可靠 `energy_import` Counter：

```text
不优先用active_power积分替代
```

---

## 2.4 已确认结算不能被迟到数据静默修改

结算确认后：

```text
Snapshot
+
Revision
```

而不是：

```text
后台自动覆盖原月账单
```

---

## 2.5 任何人工修正都必须可追溯

必须记录：

```text
Original
Corrected
Reason
Evidence
Operator
Approver
Time
```

# 3. 计量对象模型

建议区分：

```text
Physical Meter
Settlement Meter
Monitoring Meter
Check Meter
Virtual Meter
```

---

# 4. Physical Meter

真实物理计量设备。

例如：

```text
总进线电表
分项电表
光伏并网表
储能充放电表
```

---

# 5. Settlement Meter

作为正式结算依据的表计。

属性：

```text
settlement_role = PRIMARY
```

每个结算边界原则上只能有一个当前有效主结算源。

---

# 6. Check Meter

用于：

```text
交叉校验
异常检测
对账
```

不直接替代 Primary。

例如：

```text
电网关口表
+
园区自有总表
```

其中一个是 Primary，另一个可为 Check Meter。

---

# 7. Monitoring Meter

只用于：

```text
实时监控
趋势
告警
能源分析
```

不能直接进入财务结算。

---

# 8. Virtual Meter

通过多个物理表或拓扑计算得到。

例如：

```text
HVAC Energy
=
Chiller
+
Pump
+
Cooling Tower
```

Virtual Meter 必须有：

```text
definition
version
source bindings
effective period
```

---

每个结算对象必须定义：

```text

```

例如：

```text
Site Grid Import
Building Electricity
Tenant Electricity
PV Export
ESS Charge
```

边界至少包含：

```text
tenant_id
site_id
subject_type
subject_id
energy_type
direction
```

推荐：

# 11. 主计量源绑定

建立：

```text

```

核心字段：

```text

subject_id

```

---

# 12. 防止重复计量

Energy Topology 决定：

```text
父表
子表
能源流向
```

例如：

```text
总表 = 1000kWh
分表A = 400kWh
分表B = 500kWh
```

不能：

```text
1000 + 400 + 500
```

站点总购电量应使用明确的：

```text
MAIN_INCOMER / GRID_IMPORT
```

而不是遍历所有电表求和。

---

# 13. CT/PT 倍率模型

必须明确：

```text
设备输出是Primary Value
还是Secondary Value
```

字段建议：

```text
ct_ratio
pt_ratio
meter_multiplier
ratio_application_mode
```

---

# 14. 倍率生效模式

统一：

```text
DEVICE_APPLIED
EDGE_APPLIED
PLATFORM_APPLIED
```

---

# 15. DEVICE_APPLIED

设备寄存器已经返回一次侧真实值：

```text
Cloud禁止再次乘CT/PT
```

---

# 16. EDGE_APPLIED

设备返回二次侧值，由 Edge Device Template：

```text
raw
× CT
× PT
→ Standard Point
```

Cloud 接收到的已经是标准一次侧值。

---

# 17. PLATFORM_APPLIED

只建议用于：

```text
历史遗留
人工抄表
特定结算导入
```

实时 IoT 链不推荐。

---

# 18. 防止重复倍率

配置发布前必须校验：

```text
ratio_application_mode
```

如果：

```text
DEVICE_APPLIED
```

则 Edge：

```text
ct_ratio = 1
pt_ratio = 1
```

或禁止再次启用倍率。

---

# 19. 倍率变更

CT/PT 更换后必须产生：

```text
新有效期版本
```

例如：

```text
2026-01-01 ~ 2026-06-30
CT = 100/5

2026-07-01 ~
CT = 200/5
```

历史结算不能使用当前倍率重算过去所有数据。

---

# 20. Counter 基础模型

累计量：

```text
energy_import
energy_export
```

按照：

```text
End Counter - Start Counter
```

计算。

但必须处理：

```text
Reset
Rollover
Replacement
Missing
Correction
```

---

# 21. Counter 原始样本

ClickHouse 中保留：

```text
event_time
point_id
value
quality
source_seq
```

不得为了“看起来连续”而直接修改 Raw Counter。

---

# 22. Counter Reset

判定候选条件：

```text
current < previous
```

但不能直接认为一定是 Reset。

进一步判断：

```text
Device Restart
Known Reset Event
Value near zero
Firmware Event
Meter Replacement
```

---

# 23. Reset Event

确认后记录：

```text
counter_event
```

类型：

```text
RESET
ROLLOVER
REPLACEMENT
CORRECTION
```

---

# 24. Reset 后电量

例如：

```text
Before Reset:
9980 kWh

After Reset:
20 kWh
```

当日总电量：

```text
(9980 - Start)
+
(End - 20)
```

不能：

```text
End - Start
```

直接产生负值。

---

# 25. Counter Rollover

如果仪表最大：

```text
999999.9
```

然后回到：

```text
0
```

则：

```text
delta
=
(max_counter - previous)
+
current
```

前提：

```text
rollover_max
```

必须来自设备定义，不能猜。

---

# 26. Meter Replacement

换表必须建立正式事件：

```text
meter_replacement
```

记录：

```text
old_device_id
new_device_id
old_final_reading
new_initial_reading
replacement_time
reason
work_order
operator
```

---

# 27. 换表后的连续结算

例如：

```text
Old Meter:
Start 10000
Final 10500

New Meter:
Initial 20
End 120
```

期间电量：

```text
(10500 - 10000)
+
(120 - 20)
=
600 kWh
```

---

# 28. 禁止复用旧 Device ID

物理设备更换：

```text
new device_id
```

```text
asset_id
```

不变。

# 29. Counter Replacement Boundary


必须成为结算分段边界。

# 32. 数据质量分级

结算输入至少区分：

```text
GOOD
PARTIAL
ESTIMATED
MANUAL

```

---

# 33. 结算完整率

计算：

```text
actual expected samples
```

或者 Counter 边界数据覆盖情况。

必须输出：

```text
completeness
```

---

# 34. 缺失数据分类

```text
SHORT_GAP
MEDIUM_GAP
LONG_GAP
BOUNDARY_GAP
```

---

# 35. SHORT_GAP

例如：

```text
< 5min
```

可针对：

```text
Power
Temperature
```

采用插值。

但：

```text
Counter
```

通常不需要逐样本插值，只需有可靠边界值。

---

# 36. MEDIUM_GAP

例如：

```text
5min ~ 2h
```

是否估算由：

```text
metric quality policy
```

决定。

---

# 37. LONG_GAP

例如：

```text
> 2h
```

财务结算默认：

```text
不得自动估算为VALID
```

应：

```text
PARTIAL / ESTIMATED / REVIEW_REQUIRED
```

---

# 38. BOUNDARY_GAP

最关键。

例如月初/月末没有 Counter 值：

```text
不能随意找远距离最近值代替
```

必须使用边界插值或人工确认规则。

---

# 39. Counter Boundary Interpolation

如果：

```text
00:00前后存在可靠Counter
```

可按时间线性估算边界值。

例如：

```text
23:59:50 = 1000.0
00:00:10 = 1000.2
```

00:00估算：

```text
1000.1
```

结果质量：

```text
ESTIMATED
```

---

# 40. Power Integration

没有可靠 Counter 时：

```text
Energy ≈ Σ Power × Δt
```

必须记录：

```text
calculation_method = POWER_INTEGRAL
```

不能伪装成：

```text
COUNTER_DELTA
```

---

# 41. 积分算法

至少支持：

```text
RECTANGLE
TRAPEZOID
```

第一阶段推荐：

```text
TRAPEZOID
```

对于不规则采样更稳健。

---

# 42. 最大积分间隔

如果两个样本间隔超过：

```text
max_integration_gap
```

不能直接把前一个功率延续整个缺失区间。

必须：

```text
mark missing
```

或进入估算策略。

---

# 48. Fixed Demand Window

例如：

```text
10:00~10:15
10:15~10:30
10:30~10:45
```

每个窗口：

```text
Demand
=
Window Energy / Window Hours
```

或按业务规则定义平均功率。

# 49. Sliding Demand Window

如果合同要求滑动窗口，则：

```text

step = 1min
```

必须显式配置。

不能与 Fixed 15min 共用同一计算语义而不区分版本。

---

# 50. Demand Boundary

```text

```

对齐。

不是按 UTC 00:00 对齐。

---

# 51. Demand Missing Data

窗口完整率不足：

```text

=
PARTIAL / INVALID
```

# 52. Billing Demand

当前周期。


# 65. CALCULATING

# 67. LOCKED

```text

```

# 68. Settlement Grace Period

# 69. Late Data

# 70. Late Data After Lock

# 155. 最终冻结原则

第一：

```text
结算必须有明确的Authoritative Source
```

第二：

```text
CT/PT倍率只能生效一次
```

第三：

```text
Counter必须处理Reset / Rollover / Replacement
```

第四：

```text
需量必须按正式窗口规则计算
不能用瞬时最大功率代替
```

第五：

```text
Tariff必须按生效时间和Site Timezone版本化
```

第六：

```text
Late Data在Lock前自动重算
Lock后走Revision
```

第七：

```text
Estimated / Manual不能伪装成GOOD
```

第八：

```text
已结算数据必须Snapshot
```

第九：

```text
任何修正必须保留Original和Audit
```

第十：

```text
结算结果必须能够一路追溯到
Meter → Point → Telemetry → Formula → Tariff → Snapshot
```

最终平台必须能够回答：

```text
这笔电费为什么是这个数？

用了哪块表？

起止读数是多少？

CT/PT倍率是多少？

这期间有没有换表或清零？

峰平谷怎么分的？

需量窗口怎么算的？

用了哪个电价版本？

有没有估算或人工修正？

和电网账单差多少？

谁最终确认并锁定？
```

这些问题都能准确回答，并且历史结果不会因为后台补传数据而静默改变时，智慧能源系统才真正具备可用于结算、财务和审计的能力。
