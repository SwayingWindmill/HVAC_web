# 智慧能源系统告警与规则引擎设计

## 一、设计目标

智慧能源系统中的告警不能简单理解成：

```text
value > threshold
```

真实场景会出现：

```text
SOC < 15%

持续 60 秒

并且 PCS 正在放电

才产生 HIGH 告警
```

或者：

```text
Gateway Offline
```

以后下面 200 台设备全部离线。

这时不能产生：

```text
201 个独立严重告警
```

而应该识别：

```text
Gateway Offline
```

为根因，并抑制下游重复告警。

因此整个告警系统应该解决：

```text
检测

判断

去重

延迟

恢复

抑制

关联

升级

通知

处理

审计

分析
```

最终形成：

# Event → Rule → Alarm → Action → Resolution

完整闭环。

---

# 三、Event、Rule、Alarm 必须分离

这是整个架构最重要的原则之一。

## Event

表示：

**发生了什么。**

例如：

```text
DEVICE_OFFLINE

SOC_CHANGED

PCS_FAULT

COMMAND_FAILED
```

---

## Rule

表示：

**什么情况下应该认为值得关注。**

例如：

```text
SOC < 15%
持续 60 秒
```

---

## Alarm

表示：

**规则触发以后形成的业务告警实例。**

例如：

```text
ESS001 SOC过低

HIGH

Triggered At 10:32
```

因此：

```text
Event ≠ Alarm
```

---

# 四、为什么 Event 与 Alarm 分开

例如：

```text
SOC = 14.9%
```

本身只是：

```text
Telemetry / Event
```

如果配置：

```text
SOC < 15%
持续 60 秒
```

只有满足规则之后才生成：

```text
Alarm
```

否则瞬间波动会产生大量无意义告警。

# 五、告警来源

建议规则引擎支持至少六种数据来源：

```text
TELEMETRY

DEVICE_STATE

EVENT

METRIC

SYSTEM

COMMAND
```

# 六、Telemetry Rule

针对实时 Point。

例如：

```text
battery_temperature_max > 55
```

```text
voltage_a > 250
```

```text
soc < 15
```

---

# 七、Device State Rule

例如：

```text
device.online == false
```

或者：

```text
pcs.state == FAULT
```

---

# 八、Event Rule

针对离散事件。

例如：

```text
BMS_FAULT
```

收到以后立即触发告警。

---

# 九、Metric Rule

针对业务指标。

例如：

```text
daily_energy
>
baseline_energy × 1.2
```

生成：

```text
ENERGY_CONSUMPTION_ABNORMAL
```

---

# 十、System Rule

用于平台运行。

例如：

```text
Telemetry Lag > 60s
```

```text
Database Disk > 90%
```

```text
Gateway Online Rate < 95%
```

---

# 十一、Command Rule

例如：

```text
command.status == FAILED
```

或者：

```text
过去10分钟命令失败率 > 20%
```

生成控制系统运行告警。

建议统一：

```text

STATE

CHANGE

DURATION
```

# 十三、Threshold Rule

最基础：

```text
value > threshold
```

例如：

```text
temperature > 55°C
```

---

# 十四、Range Rule

例如：

```text
voltage < 198V
OR
voltage > 242V
```

统一表达：

```text
NOT BETWEEN
```

---

# 十五、State Rule

例如：

```text
running_status == FAULT
```

或者：

```text
breaker_status == OPEN
```

---

# 十六、Change Rule

检测状态变化：

```text
ONLINE → OFFLINE
```

```text
RUNNING → FAULT
```

```text
NORMAL → EMERGENCY
```

---

# 十七、Missing Rule

智慧能源场景非常重要。

例如：

```text
active_power
```

正常每：

```text
5s
```

更新。

如果：

```text
30s
```

没有数据：

```text
POINT_DATA_MISSING
```

---

# 十八、Stale Rule

与 Missing 类似但语义不同。

例如：

设备仍在线：

```text
online = true
```

但：

```text
SOC
```

已经 5 分钟没有变化。

可以：

```text
STALE
```

---

# 十九、Duration Rule

防止瞬间噪声。

例如：

```text
SOC < 15%
```

持续：

```text
60s
```

才告警。

而：

```text
SOC = 14.9%
```

只持续 2 秒后恢复：

不产生告警。

---

# 二十、Delay

推荐规则支持：

```text
trigger_delay
```

例如：

```text
temperature > 55
trigger_delay = 30s
```

---

# 二十一、Recovery Delay

恢复也不要瞬间发生。

例如：

```text
Temperature < 52°C
```

持续：

```text
60s
```

以后才恢复。

避免：

```text
54.9
55.1
54.8
55.2
```

导致告警不断：

```text
OPEN
CLOSE
OPEN
CLOSE
```

---

# 二十二、Deadband

例如告警阈值：

```text
High Temperature = 55°C
```

恢复阈值不应也是：

```text
55°C
```

推荐：

```text
Trigger:
> 55°C

Recover:
< 52°C
```

其中：

```text
3°C
```

就是 hysteresis / deadband。

---

# 二十三、Hysteresis

建议规则直接支持：

```text
trigger_threshold

recovery_threshold
```

例如：

```text
High Voltage

Trigger:
> 250V

Recover:
< 245V
```

---

# 二十四、Rate Rule

检测变化速度。

例如：

```text
SOC change > 20% / minute
```

可能意味着：

```text
数据异常

BMS异常
```

---

# 二十五、Jump Rule

例如：

```text
Power
500kW
↓
5000kW
```

间隔：

```text
1s
```

可以产生：

```text
DATA_JUMP
```

---

# 二十六、Expression Rule

支持简单公式：

```text

-
battery_temperature_min
>
15
```

产生：

```text

```

# 二十七、Composite Rule

组合多个条件：

```text
SOC < 15%
AND
ess_power > 0
AND
pcs_status == RUNNING
```

表示：

```text
低SOC状态下仍在放电
```

# 二十八、AND / OR / NOT

规则表达式至少支持：

```text

OR

NOT
```

以及：

```text

>=

<

<=

==

!=

BETWEEN

IN
```

例如：

```text

```

但只在：



# 五十一、告警状态机

推荐：

```text
OPEN
  ↓

  ↓
RESOLVED
  ↓
CLOSED
```

```text

```

---

# 五十二、OPEN

规则当前处于触发状态。

---

# 五十三、ACKNOWLEDGED

用户已看到并确认：

```text
有人正在处理。
```

但问题仍存在。

因此：

```text
ACKNOWLEDGED ≠ RESOLVED
```

---

# 五十四、RESOLVED

规则恢复条件已经满足。

例如：

```text
Temperature < 52°C
持续60秒
```

---

# 五十五、CLOSED

告警处理流程正式结束。

可以是：

```text
自动关闭
```

或者：

```text
人工确认关闭
```

根据告警类型决定。

---

# 五十六、告警恢复

告警必须绑定：

```text
recovery_condition
```

不能只知道：

```text
怎么触发
```

却不知道：

```text
什么时候恢复。
```

---

# 五十七、Latch Alarm

有些严重告警即使现场恢复，也不应自动关闭。

例如：

```text
Emergency Shutdown
```

恢复后仍要求：

```text
Manual Reset / Close
```

可以设置：

```text
latching = true
```

# 六十、告警去重

如果：

```text
temperature > 55°C
```

持续两小时。

每 5 秒规则都会成立。

不能每 5 秒生成一个新 Alarm。

应该：

```text
第一次
→ OPEN

之后
→ 更新 occurrence_count / last_seen
```

---

# 六十一、告警重复计数

Alarm 可以维护：

```text
first_seen

last_seen

occurrence_count
```

例如：

```text
过去2小时触发 143 次
```

仍然对应一个业务 Alarm。

---

# 六十二、Flapping

如果设备：

```text
ONLINE

OFFLINE

ONLINE

OFFLINE
```

频繁切换。

可以检测：

```text
flapping
```

```text

```

```text

```

---

# 六十三、告警抑制 Suppression

例如：

```text

```

```text

```

```text

```

```text
Device Offline Alarm
```

# 六十四、为什么 Suppression 很重要

否则一个根因会导致：

```text
告警风暴
```

```text
真正的问题是什么。
```

# 六十五、Topology Suppression

```text
 ↓

```

```text
 ↓
```

# 八十五、控制型 Action



```text

```

不能绕过：

```text

```

正确：

```text

 ↓
Control Request
 ↓
Control Service
 ↓
Safety Validation
 ↓
```

# 八十六、告警规则与安全规则分离

非常重要。

例如：

```text
SOC < 15%
```

可以产生告警。

而：

```text
SOC < 10%
禁止放电
```

属于：

```text
Safety Policy
```

两者可以共享表达式引擎，但业务意义必须分离。

# 八十八、边缘规则与云端规则


适合：

```text

跨设备

跨站点
```

```text

>
```

# 九十一、历史告警补传

例如断网期间：

```text
10:00 Over Temperature

10:10 Recovery
```

11:00 网络恢复。

Cloud 收到后应该能够还原：

```text
10:00 Alarm Open

10:10 Alarm Resolved
```

而不是：

```text
11:00 新告警
```

因此必须使用：

```text
event_time
```

而不是单纯：

```text
receive_time
```

# 九十二、Out-of-order Event

例如先收到：

```text

```

再收到：

```text

```

Alarm Engine 必须考虑：

```text

```

# 一百七十九、最终设计原则

整个告警与规则系统建议坚持以下原则：

**第一，Event、Rule、Alarm 必须分离。**

事件表示事实，规则表示判断逻辑，告警表示业务实例。

**第二，触发条件和恢复条件必须同时定义。**

没有 Recovery 的规则是不完整的。

**第三，必须支持 Duration、Deadband 和 Hysteresis。**

避免工业数据波动造成告警抖动。

**第四，同一持续故障只维护一个活动 Alarm。**

不能每条 Telemetry 创建一个新告警。

**第五，必须具备 Suppression 和 Correlation。**

否则大型系统一定会出现告警风暴。

**第六，规则应基于 Standard Point 和 Standard Metric。**

不能绑定厂家寄存器。

**第七，云端告警和 Edge 安全规则职责必须分离。**

安全保护优先放 Edge / Device。

**第八，规则引擎不能直接绕过 Control Service 控制设备。**

任何动作都必须进入安全控制链。

**第九，规则、告警、确认、关闭全过程必须审计。**

系统必须可追溯。

**第十，告警体系最终目标不是“产生更多告警”，而是帮助运维人员更快找到真正的问题。**

# 一百八十、最终核心思想

智慧能源告警系统最终应该从传统：

```text
Value > Threshold
↓
Alarm
```

升级为：

```text
Data
 ↓
Context
 ↓
Rule
 ↓
Duration
 ↓
Correlation
 ↓
Root Cause
 ↓
Alarm
 ↓
Action
 ↓
Resolution
```

也就是说：

# 告警系统真正需要回答的不是“哪个值超限了”，而是“系统发生了什么、是否需要处理、真正的根因在哪里、应该由谁处理”。

最终形成：

```text
Observe
 ↓
Detect
 ↓
Understand
 ↓
Alert
 ↓
Respond
 ↓
Resolve
 ↓
Improve
```

这样告警中心才会真正成为整个智慧能源平台的运维中枢，而不是简单的“报警列表”。
