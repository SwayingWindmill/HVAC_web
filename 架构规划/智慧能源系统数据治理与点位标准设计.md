# 智慧能源系统数据治理与点位标准设计

## 一、设计目标

智慧能源系统接入的设备通常来自大量不同厂家。

同一个“有功功率”，不同厂家可能定义成：

```text
P
Power
ActivePower
TotalPower
KW
kWTotal
P_Total
Active_P
```

如果平台直接保留厂家原始命名，随着设备和项目增加，最终会出现：

- 点位名称混乱
    
- 单位不统一
    
- 同一指标多种编码
    
- AI 无法复用
    
- 报表大量定制
    
- EMS 逻辑绑定厂家
    
- 换设备就需要改代码
    

因此必须在系统层建立一套：

# 统一能源数据语言

核心原则：

> 厂家协议可以不同，但进入智慧能源平台以后，设备类型、点位编码、数据类型、单位和质量规则必须统一。

整体转换关系：

```text
厂家协议
   ↓
厂家设备模板
   ↓
原始寄存器 / Object / Tag
   ↓
标准 Point
   ↓
标准 Unit
   ↓
标准 Quality
   ↓
标准 Telemetry
   ↓
Metric / EMS / AI
```

---

# 二、数据治理总体架构

建议把数据治理分成六层：

```text
┌─────────────────────────────────────┐
│        业务指标 Metric              │
│ 能耗 / 成本 / 效率 / 碳 / KPI        │
├─────────────────────────────────────┤
│        标准 Point 模型              │
│ active_power / soc / temperature    │
├─────────────────────────────────────┤
│        标准设备模型                  │
│ Meter / PCS / BMS / Inverter        │
├─────────────────────────────────────┤
│        数据标准化                    │
│ Unit / Type / Quality / Timestamp   │
├─────────────────────────────────────┤
│        Device Template              │
│ Register / BACnet / OPC UA Mapping  │
├─────────────────────────────────────┤
│        原始设备协议                  │
│ Modbus / BACnet / OPC UA / IEC104   │
└─────────────────────────────────────┘
```

# 五、设备类型编码原则

统一采用：

```text
UPPER_SNAKE_CASE
```

例如：

正确：

```text
PV_INVERTER
POWER_METER
BATTERY_RACK
```

不建议：

```text
pvInverter
PowerMeter
meter01
光伏逆变器
```

数据库存：

```text
PV_INVERTER
```

UI 可以显示：

```text
光伏逆变器
```

做到：

**Code 面向机器，Name 面向用户。**

---

# 六、Point Code 是整个标准体系核心

Point Code 表示：

> 一个数据在整个智慧能源平台里的标准语义。

例如：

```text
active_power
```

不代表：

```text
某个厂家寄存器 40001
```

而是统一表示：

> 有功功率。

因此：

```text
Schneider Register 40001

Siemens Tag P_TOTAL

ABB Register 120

Sungrow Power
```

最终都可以映射：

```text
active_power
```

---

# 七、Point Code 命名规范

建议统一：

```text
lower_snake_case
```

例如：

```text
active_power

reactive_power

power_factor

energy_import

battery_voltage

cell_temperature
```

禁止：

```text
ActivePower

activePower

ACTIVE_POWER

有功功率

P
```

---

# 八、Point Code 结构

复杂点位建议按照：

```text
对象 + 属性
```

结构。

例如：

```text
battery_voltage

battery_current

battery_temperature
```

或者：

```text
dc_voltage

dc_current

dc_power
```

相位：

```text
voltage_a

voltage_b

voltage_c
```

避免：

```text
a_voltage

Ua

U_A

PhaseAVoltage
```

# 二十一、储能功率方向规范

这是必须统一的规则。

建议全平台定义：

```text
ESS Power > 0

= 放电
```

```text
ESS Power < 0

= 充电
```

或者反过来也可以。

但是：

# 必须全平台只有一种。

推荐：

```text
positive = discharge

negative = charge
```

那么：

```text
ess_power = 500 kW
```

表示：

```text
向负荷放电 500kW
```

而：

```text
ess_power = -300 kW
```

表示：

```text
充电 300kW
```

# 三十、TELEMETRY

表示连续实时值。

例如：

```text
active_power

temperature

soc

voltage
```

特征：

```text
持续变化

可历史趋势
```

---

# 三十一、COUNTER

累计量。

例如：

```text
energy_import

total_generation

total_water_volume
```

COUNTER 特别重要，因为它的聚合方式和普通 Telemetry 完全不同。

例如：

```text
小时用电量

≠ AVG(energy_import)
```

应该：

```text
Last Counter
-
First Counter
```

---

# 三十二、STATE

状态型数据。

例如：

```text
running_status

fault_status

breaker_status

online_status
```

数据：

```text
ON
OFF

OPEN
CLOSED

RUNNING
STOPPED
FAULT
```

---

# 三十三、SETTING

可读写配置参数。

例如：

```text
target_power

target_temperature

soc_upper_limit

soc_lower_limit
```

通常：

```text
READ_WRITE
```

---

# 三十四、COMMAND

动作型控制。

例如：

```text
start

stop

reset

emergency_stop
```

COMMAND 和 SETTING 要分离。

因为：

```text
SET_POWER = 500
```

是参数。

而：

```text
START
```

是动作。

```text

```


```text

```

# 三十七、ENUM

例如：

```text

```

值：

```text
0 = STOP

1 = MANUAL

2 = AUTO

3 = FAULT
```

应该建立：

```text
Enum Definition
```

不能让业务代码到处写：

```text

```

应该统一解析成：

```text
AUTO
```

---

# 三十八、BITSET

工业设备经常返回：

```text
16-bit fault register
```

例如：

```text
bit0 = OverVoltage

bit1 = UnderVoltage

bit2 = OverTemperature
```

建议：

原始点：

```text
fault_register
```

类型：

```text
BITSET
```

然后标准化为事件：

```text
OVER_VOLTAGE

UNDER_VOLTAGE

OVER_TEMPERATURE
```

# 四十七、数值转换标准

完整转换建议：

```text
Raw
 ↓
Decode
 ↓
Scale
 ↓
Offset
 ↓
Unit Conversion
 ↓
Standard Value
```

公式可以统一理解为：

```text
standard_value
=
(raw_value × multiplier + offset)
× unit_factor
```

# 四十八、Precision

每个标准 Point 建议定义默认精度。

例如：

```text
active_power        2

voltage             1

current             2

soc                 1

temperature         1

energy              2
```

但是：

**数据库不建议为了显示精度提前截断原始数据。**

显示层负责：

```text
round
```

---

# 四十九、Range 标准

每个 Point 可以维护：

```text
physical_min

physical_max
```

例如：

```text
soc

min = 0

max = 100
```

如果：

```text
SOC = 156
```

则：

```text
OUT_OF_RANGE
```

---

# 五十、Range 不应该等于 Alarm Limit

需要严格区分：

```text
Physical Range
```

和：

```text
Business Alarm Threshold
```

例如：

```text
Battery Temperature

Physical:

-40 ～ 100°C
```

但告警：

```text
> 55°C

HIGH
```

两者不是一回事。

---

# 五十一、Quality 标准体系

推荐所有 Telemetry 都有：

```text
quality
```

不允许只有：

```text
timestamp + value
```

标准 Quality：

```text
GOOD

BAD

TIMEOUT

OFFLINE

MISSING

STALE

OUT_OF_RANGE

PARSE_ERROR

ESTIMATED

MANUAL
```

---

# 五十二、质量码建议

数据库内部可以定义：

```text
0    GOOD

10   BAD

20   TIMEOUT

30   OFFLINE

40   MISSING

50   STALE

60   OUT_OF_RANGE

70   PARSE_ERROR

80   ESTIMATED

90   MANUAL
```

预留编号空间，方便以后扩展。

---

# 五十三、GOOD

表示：

```text
设备通信正常

数据解析正常

时间有效

值处于合理范围
```

---

# 五十四、TIMEOUT

例如：

```text
Modbus Request
```

超过：

```text
1000ms
```

无返回。

该次 Point：

```text
TIMEOUT
```

---

# 五十五、OFFLINE

不要一次 Timeout 就定义 Offline。

例如：

```text
连续 3 次通信失败

→ Device OFFLINE
```

之后相关测点：

```text
OFFLINE
```

---

# 五十六、STALE

设备可能在线，但一个 Point 很长时间没有更新。

例如：

```text
Point Sampling = 5s
```

但：

```text
30s
```

没有新数据。

标记：

```text
STALE
```

---

# 五十七、ESTIMATED

用于：

```text
插值

预测补值

估算值
```

例如报表缺一个 15 分钟数据：

```text
ESTIMATED
```

不能伪装：

```text
GOOD
```

---

# 五十八、MANUAL

人工补录数据：

```text
MANUAL
```

例如：

```text
人工录入天然气月度数据
```

必须和自动采集区分。

---

# 五十九、Timestamp 标准

平台统一使用：

```text
UTC
```

进行存储。

UI 根据：

```text
Site Timezone
```

显示。

建议不要直接在数据库存：

```text
2026-08-08 10:00
```

这种没有时区语义的时间。

---

# 六十、建议保留的时间

重要 IoT 数据可以同时记录：

```text
device_time

gateway_time

server_time
```

标准业务 timestamp 应通过明确规则选择。

通常优先：

```text
device_time
```

前提是设备时间可信。

否则：

```text
gateway_time
```

---

# 六十一、时间同步

Gateway 建议使用：

```text
NTP
```

定期校时。

并监测：

```text
clock_offset
```

例如设备时间与 Gateway 时间偏差：

```text
> 60s
```

生成：

```text
TIME_DRIFT
```

数据质量事件。

---

# 六十二、Sampling Policy

Point 标准除了 Code，还应该定义推荐采样周期。

例如：

|Point|推荐采样|
|---|--:|
|active_power|5s|
|voltage|10s|
|current|10s|
|soc|5-10s|
|temperature|30s|
|energy_import|60s|
|device_status|状态变化 + 60s|

但最终允许：

```text
Device Template
```

覆盖。

---

# 六十三、采样与上传分离

必须区分：

```text
polling_interval
```

和：

```text
upload_interval
```

例如：


# 一百零四、最核心的数据治理原则

整个智慧能源平台的数据治理可以浓缩成十条原则：

**1. Code 与 Name 分离。**

Code 给系统使用，Name 给用户显示。

**2. Vendor Point 与 Standard Point 分离。**

厂家协议不能进入业务层。

**3. Device 与 Point 分离。**

设备是什么，与设备产生什么数据是两个概念。

**4. Point 与 Metric 分离。**

设备原始语义与能源业务指标分离。

**5. Unit 必须统一。**

不能同一个指标存在 W、kW、MW 而没有标准化。

**6. Quality 是数据的一部分。**

Value 没有 Quality 就不是完整的工业数据。

**7. Timestamp 必须统一。**

数据库统一 UTC，显示按照 Site Timezone。

**8. Counter 与 Telemetry 必须区分。**

累计量不能按照普通实时值计算。

**9. 所有标准必须版本化。**

点位、设备模板、枚举和单位映射都必须受版本控制。

**10. 数据必须可追溯。**

任何业务指标最终应该能够追溯到具体 Device、Point 和原始数据。

# 一百零五、最终核心模型

整套数据治理最终可以浓缩成：

```text
Vendor Device
      ↓
Device Template
      ↓
Vendor Point
      ↓
Standard Point
      ↓
Standard Unit
      ↓
Quality
      ↓
Telemetry
      ↓
Metric
      ↓
Energy Business
```

这就是智慧能源平台的数据语言体系。

如果这套体系设计正确，那么未来即使：

```text
接入 100 个厂家

10,000 台设备

1,000,000 个测点
```

上层 EMS、AI 和优化系统仍然可以使用统一的数据模型。

因此：

# 点位标准不是 IoT 配置问题，而是整个智慧能源平台的数据基础设施。

真正应该长期稳定的是：

**Standard Device Type + Standard Point + Standard Unit + Standard Quality + Standard Metric**

厂家协议、设备型号和通信方式都可以不断变化，但这套标准语义层应该保持稳定。
