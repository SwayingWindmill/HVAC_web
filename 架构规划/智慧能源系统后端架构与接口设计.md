# 智慧能源系统后端架构与接口设计

> 文档编号：SE-ARCH-004  
> 版本：V2.0  
> 状态：CURRENT  
> 架构基线：ADR-013（ClickHouse Telemetry）+ ADR-014（Forecast / Optimization Production = Go）  
> 修订原则：统一 Go 后端、Go Forecast/Optimization 与 ClickHouse 数据职责；保留 Control/Safety 原有权威边界

## 一、整体目标

这一阶段主要解决四个问题：

**1. 后端服务怎么拆**

**2. 各服务之间怎么通信**

**3. IoT 数据怎么进入平台**

**4. 前端、算法和第三方系统怎么调用平台**

整体目标是形成：

```text
设备
 ↓
Gateway
 ↓
MQTT
 ↓
IoT接入服务
 ↓
数据处理
 ↓
Telemetry / Redis
 ↓
EMS业务服务
 ↓
AI / Optimization
 ↓
Control
 ↓
设备
```

最终形成完整闭环：

```text
采集 → 存储 → 分析 → 预测 → 优化 → 控制 → 反馈
```

# 二、总体后端架构

建议后端整体采用：

**模块化服务 + 事件驱动架构**

而不是项目第一天就拆成几十个微服务。

推荐逻辑架构：

```text
                         ┌───────────────┐
                         │ Web / App / BI │
                         └───────┬───────┘
                                 │
                         ┌───────▼───────┐
                         │  API Gateway  │
                         └───────┬───────┘
                                 │
          ┌──────────────────────┼─────────────────────┐
          │                      │                     │
 ┌────────▼────────┐    ┌────────▼────────┐   ┌───────▼────────┐
 │ Asset Service   │    │ Energy Service │   │ Alarm Service  │
 └─────────────────┘    └─────────────────┘   └────────────────┘

 ┌─────────────────┐    ┌─────────────────┐   ┌────────────────┐
 │ Device Service  │    │ Metric Service │   │ Control Service│
 └─────────────────┘    └─────────────────┘   └────────────────┘

 ┌─────────────────┐    ┌─────────────────┐   ┌────────────────┐
 │Telemetry Service│    │Forecast Service│   │Optimization Svc│
 └─────────────────┘    └─────────────────┘   └────────────────┘

以上生产服务统一采用 Go；Forecast 通过 ForecastEngine 解耦模型，Optimization 通过 SolverAdapter 解耦求解器。

                                 │
                         ┌───────▼───────┐
                         │ Kafka / Event │
                         └───────┬───────┘
                                 │
                         ┌───────▼───────┐
                         │ IoT Service   │
                         └───────┬───────┘
                                 │
                              MQTT
                                 │
                              Gateway
```

# 三、服务划分原则

服务不能按照数据库表一张表一个服务。

应该按照：

**业务领域**

进行拆分。

例如：

```text
device

point

gateway
```

这三类数据本质上都属于：

**Device Domain**

所以应该统一由：

```text
Device Service
```

负责。

# 九、Product API

设备模板应该独立管理。

例如创建一款电表模板：

```text
POST /api/v1/products
```

内容：

```json
{
  "productCode": "PM8000",
  "productName": "Schneider PM8000",
  "deviceType": "ELECTRIC_METER",
  "protocol": "MODBUS_TCP"
}
```

然后定义测点：

```text
POST /api/v1/products/{productId}/point-templates
```

例如：

```json
{
  "pointCode": "active_power",
  "pointName": "有功功率",
  "pointType": "TELEMETRY",
  "dataType": "DOUBLE",
  "unit": "kW",
  "protocolAddress": "40001",
  "multiplier": 0.01
}
```

这样新增：

```text
100 台 PM8000
```

就不需要重复配置 100 次点位定义。

# 十八、Control Service

Control Service 是整个平台中非常重要且必须独立设计的服务。

任何真实设备控制，都必须经过：

```text
Control Service
```

不能允许：

```text
Energy Service
Forecast Service
Optimization Service
Web Backend
```

直接调用 MQTT。

同样禁止：

```text
ForecastEngine
SolverAdapter
Offline AI Tool
```

直接持有 MQTT Publish Authority。

正确链路：

```text
Business Service
      ↓
Control Service
      ↓
Safety Validation
      ↓
Command
      ↓
IoT Service
      ↓
MQTT
      ↓
Gateway
      ↓
Device
```

---

# 十九、控制安全检查

Control Service 至少执行：

```text
Tenant 权限

Site 权限

User 权限

Device 在线

Device 可控

Point 可写

当前状态

目标值上下限

控制模式

安全联锁

命令频率限制
```

例如：

储能 SOC：

```text
SOC = 95%
```

这时算法要求：

```text
Charge = 500kW
```

Control Service 应该拒绝。

# 四十一、边缘缓存

现场网络断开是必然要考虑的。

所以 Gateway 必须有：

```text

```

例如使用：

```text

RocksDB
```

```text

point

value

quality

sequence
```

网络恢复后：

```text
Store
 ↓
Replay
 ↓
Cloud
```

这就是：

**断点续传。**

# 六十四、整个架构最关键的边界

最后必须明确五个关键边界。

## Device Service

回答：

**设备是什么、有什么点位。**

## Telemetry Service

回答：

**设备在某个时间产生了什么数据。**

## Energy Service

回答：

**这些设备数据在能源业务上意味着什么。**

## Optimization Service

回答：

**系统下一步应该如何运行。**

## Control Service

回答：

**这个策略能不能安全执行，以及如何执行。**

这五个领域不要混为一体。

最终完整的数据和业务链路可以浓缩成：

```text
Device
 ↓
Point
 ↓
Telemetry
 ↓
Metric
 ↓
Energy
 ↓
Forecast
 ↓
Optimization
 ↓
Command
 ↓
Device
```

这条链路，就是整个智慧能源系统最核心的软件主干。

从工程实现角度看，第一版最值得优先做好的不是 AI，而是：

**Device + Point + Telemetry + Energy + Command**

这五块一旦稳定，后续增加光伏、储能、充电、HVAC、AI 和 VPP，基本都可以沿着同一套架构继续扩展。
