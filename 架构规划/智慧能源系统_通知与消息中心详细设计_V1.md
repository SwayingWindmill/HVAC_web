# 智慧能源系统通知与消息中心详细设计

> 文档编号：SE-OPS-008  
> 版本：V1.0  
> 状态：CURRENT  
> 技术基线：Go Notification Service + PostgreSQL + Redis + MQ/Event Bus + External Channel Adapters  
> 适用范围：告警通知、审批通知、系统事件、运维通知、结算提醒、预测/优化异常通知、控制风险通知  
> 上位设计：告警与规则引擎设计、控制与安全架构、配置中心与版本发布设计、生产运维 Runbook、前端交互与能源控制 UX 规范  
> 核心目标：建立统一、可路由、可重试、可审计、可升级、可静默的消息中心，避免各业务模块自行直连短信、邮件、企微或钉钉

---

# 1. 系统定位

通知与消息中心负责：

```text
业务事件
↓
通知策略
↓
接收人解析
↓
渠道路由
↓
模板渲染
↓
发送
↓
回执
↓
重试 / 升级
↓
审计
```

它不负责：

```text
判断设备是否故障
决定Alarm是否触发
决定Command是否安全
决定Settlement是否锁定
```

这些由各自业务域负责。

---

# 2. 核心原则

第一：

```text
业务系统只产生事件
不直接调用短信/邮件厂商
```

第二：

```text
Notification != Alarm
```

第三：

```text
一次业务事件
可以产生多个通知
```

第四：

```text
送达失败
不能改变原业务事实
```

第五：

```text
去重、静默、升级
必须由规则控制
```

第六：

```text
所有发送结果必须可审计
```

# 232. 最终冻结原则

第一：

```text
任何业务模块不得直接调用外部通知渠道
```

第二：

```text
Notification不改变业务事实
```

第三：

```text
SENT不等于DELIVERED
```

第四：

```text
Dedup只抑制重复发送
不删除原业务事件
```

第五：

```text
Critical默认不能被普通Silence永久屏蔽
```

第六：

```text
Retry必须区分临时错误和永久错误
```

第七：

```text
外部渠道失败必须有明确可观测性
```

第八：

```text
所有通知必须可追溯到Source Event
```

第九：

```text
恢复后不能产生历史通知风暴
```

第十：

```text
消息中心的目标不是“尽可能多发消息”，
而是让正确的人在正确时间收到真正需要处理的信息
```

最终平台必须能回答：

```text
这条消息为什么发？

来自哪个业务事件？

匹配了哪条策略？

为什么发给这个人？

用了哪个模板版本？

走了哪个渠道？

发送是否成功？

是否真正送达？

失败后重试了几次？

有没有被静默、去重或升级？

谁确认收到？

三个月后还能不能完整追溯？
```

这些问题都能准确回答时，智慧能源系统才具备真正可运营的统一通知与消息中心能力。
