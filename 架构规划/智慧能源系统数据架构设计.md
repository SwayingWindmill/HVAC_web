# 智慧能源系统数据架构设计

## 一、数据架构目标

智慧能源系统的数据架构，不只是解决“数据存哪里”，而是解决以下几个核心问题：

1. **数据从哪里来**
    
2. **数据属于哪个设备、哪个园区、哪个业务**
    
3. **不同设备的数据如何统一表示**
    
4. **实时数据、历史数据、业务数据如何关联**
    
5. **能源拓扑如何表达**
    
6. **指标如何计算**
    
7. **数据质量如何保证**
    
8. **如何为 EMS、AI、优化调度和控制提供统一数据服务**
    

因此，智慧能源系统的数据架构应该围绕一个核心思想展开：

**统一对象模型 + 统一测点模型 + 统一时序模型 + 统一能源模型 + 统一拓扑模型。**

# 二、整体数据架构

整体数据流建议设计为：

```text
现场设备
   ↓
边缘网关
   ↓
IoT 接入
   ↓
数据标准化
   ↓
数据质量处理
   ↓
实时数据平台
   ↓
ClickHouse
   ↓
能源数据模型
   ↓
指标计算
   ↓
EMS / AI / 优化 / 报表 / API
```

进一步拆分：

```text
┌────────────────────────────────────┐
│             数据消费层              │
│ EMS / AI / BI / 报表 / API / 控制   │
└─────────────────┬──────────────────┘
                  │
┌─────────────────▼──────────────────┐
│             数据服务层              │
│ Query API / Metric API / Data API  │
└─────────────────┬──────────────────┘
                  │
┌─────────────────▼──────────────────┐
│             指标计算层              │
│ 能耗 / 成本 / 碳 / KPI / 能效 / 预测 │
└─────────────────┬──────────────────┘
                  │
┌─────────────────▼──────────────────┐
│             能源模型层              │
│ Asset / Device / Point / Topology  │
└─────────────────┬──────────────────┘
                  │
┌─────────────────▼──────────────────┐
│             数据存储层              │
│ PostgreSQL / ClickHouse / Redis / S3     │
└─────────────────┬──────────────────┘
                  │
┌─────────────────▼──────────────────┐
│             数据处理层              │
│ 清洗 / 标准化 / 聚合 / 数据质量      │
└─────────────────┬──────────────────┘
                  │
┌─────────────────▼──────────────────┐
│             数据接入层              │
│ MQTT / Modbus / BACnet / OPC UA    │
└────────────────────────────────────┘
```

# 四、Tenant 租户模型

Tenant 用于支持多企业、多客户的平台架构。

例如：

```text
Tenant A
 ├── 上海工厂
 ├── 苏州工厂
 └── 深圳工厂

Tenant B
 ├── 北京园区
 └── 天津园区
```

建议字段：

```text
tenant_id

tenant_code

tenant_name

status

timezone

currency

country

created_at

updated_at
```

作用包括：

- 数据隔离
    
- 用户隔离
    
- 权限隔离
    
- 设备隔离
    
- 计费隔离
    
- 报表隔离
    

原则：

**所有核心业务数据都应该带 tenant_id。**

# 十六、数据聚合策略

不建议所有历史数据永久保持 1 秒或者 5 秒粒度。

建议采用分层聚合。

例如：

```text
Raw
5 秒

↓

1 minute

↓

15 minutes

↓

1 hour

↓

1 day

↓

1 month
```

例如：

5 秒数据保留：

```text
30 天
```

1 分钟数据：

```text
1 年
```

15 分钟数据：

```text
3-5 年
```

小时和日数据：

长期保留。

具体期限根据项目要求确定。

# 二十七、数据质量规则

建议建立统一的数据质量引擎。


```text

↓
```

### 缺失检查

```text

```

---

### 通信检查

设备掉线：

```text

```

---

### 重复数据

检测重复 timestamp。

---

### 时间漂移

检测设备时间与服务器时间偏差。

```text
 ↓
```

```text
 ↓
Energy KPI
 ↓
EMS / AI
```

---

# 三十九、最重要的设计原则

整个数据架构中，有几个原则必须坚持。

## 第一：设备和测点必须分离

不能：

```text
一条设备记录对应一个数据。
```

应该：

```text
Device
 ↓
N 个 Point
```

---

## 第二：原始数据和业务指标必须分离

```text
Point
```

代表：

**设备数据。**

```text
Metric
```

代表：

**业务指标。**

---

## 第三：空间关系和能源拓扑必须分离

例如一个电表物理位置在：

```text
1号楼 3楼
```

但能源关系可能是：

```text
Transformer A
 ↓
Distribution Panel
 ↓
Meter
```

这是两种不同关系。

不能混在一起。

---

## 第四：Asset 和 Device 必须分离

Asset 是：

**业务资产。**

Device 是：

**通信设备。**

一个 Asset 可以包含多个 Device。

---

## 第五：所有数据必须有时间

能源系统本质上是：

**时间序列系统。**

---

## 第六：所有数据必须考虑质量

不能简单认为：

**设备上传的数据就是正确的数据。**

---

## 第七：所有控制必须可追溯

所有自动控制必须记录：

```text
策略

命令

执行

反馈

结果
```

---

# 四十、数据架构最终核心

整个智慧能源数据架构最终可以压缩成六个核心模型：

```text
Asset Model

Device Model

Point Model

Time Series Model

Energy Topology Model

Metric Model
```

也就是：

**资产模型**

解决：

> 这是什么？

**设备模型**

解决：

> 谁在采集或控制？

**测点模型**

解决：

> 采集什么？

**时序模型**

解决：

> 什么时间发生了什么？

**能源拓扑模型**

解决：

> 能源从哪里来、到哪里去？

**指标模型**

解决：

> 这些数据对业务意味着什么？

如果这六个模型设计正确，后续的：

- IoT
    
- EMS
    
- 光伏
    
- 储能
    
- 充电
    
- HVAC
    
- AI
    
- VPP
    
- 碳管理
    
- 优化调度
    

都可以在同一个数据底座上持续扩展。

因此，智慧能源平台的数据架构核心并不是“把数据放 PostgreSQL 还是 ClickHouse”，而是先把：

**对象关系、数据语义、能源关系和指标体系**

设计正确。

数据库只是实现这些模型的技术手段。
