# 智慧能源系统安全与控制架构设计

## 一、设计目标

智慧能源系统与普通信息系统最大的区别之一是：

**它最终可能对真实设备产生物理控制。**

例如：

- 储能充电
    
- 储能放电
    
- PCS 启停
    
- 空调温度设定
    
- 水泵启停
    
- 充电桩功率限制
    
- 光伏限功率
    
- 断路器控制
    
- HVAC 调度
    

因此系统安全不能只解决：

```text
用户能不能登录？
```

还必须解决：

```text
这个人有没有权限控制？

这个算法有没有权限控制？

当前设备状态允许控制吗？

目标值是否安全？

设备是否处于远程模式？

控制会不会和现场联锁冲突？

命令到底有没有执行成功？

出了问题以后谁能接管？
```

整个系统最终需要建立：

# 身份可信 + 权限受控 + 策略受限 + 控制可验证 + 操作可追溯 + 现场可接管

的完整安全控制体系。

---

# 二、安全总体架构

智慧能源系统建议采用分层安全模型：

```text
┌─────────────────────────────────────────┐
│              用户安全                    │
│ IAM / MFA / RBAC / Session              │
├─────────────────────────────────────────┤
│              API 安全                    │
│ TLS / Token / Gateway / Rate Limit      │
├─────────────────────────────────────────┤
│              业务权限                    │
│ Tenant / Site / Asset / Device          │
├─────────────────────────────────────────┤
│              控制权限                    │
│ Manual / Auto / Approval / Scope        │
├─────────────────────────────────────────┤
│              控制安全                    │
│ Range / Mode / Interlock / Safety Rule  │
├─────────────────────────────────────────┤
│              IoT 安全                    │
│ MQTT TLS / Device Identity / Cert       │
├─────────────────────────────────────────┤
│              Edge 安全                   │
│ Local Rule / Command Validation         │
├─────────────────────────────────────────┤
│              OT 安全                     │
│ PLC / PCS / BMS / Hardware Protection   │
└─────────────────────────────────────────┘
```

重要原则是：

**安全不能只放在云端某一个服务。**

应该形成：

```text
Cloud Safety
+
Edge Safety
+
Device Safety
```

多层防护。

---

# 三、控制总体链路

正常的控制链路应该是：

```text
User / Optimization
        ↓
Authorization
        ↓
Control Service
        ↓
Safety Validation
        ↓
Approval / Policy
        ↓
Command
        ↓
IoT Service
        ↓
MQTT
        ↓
Edge Gateway
        ↓
Local Safety Validation
        ↓
Protocol Adapter
        ↓
PCS / BMS / HVAC / EV
        ↓
Read Back / Feedback
        ↓
Command Result
        ↓
Cloud
```

而不应该是：

```text
React
 ↓
MQTT
 ↓
Device
```

也不应该：

```text
Optimization Algorithm
 ↓
MQTT
 ↓
PCS
```

所有控制必须经过统一的：

# Control Service

---

# 四、控制系统核心边界

整个系统建议明确五个控制边界。

## 第一层：业务授权

解决：

> 谁可以控制？

---

## 第二层：策略授权

解决：

> 为什么允许执行这次控制？

---

## 第三层：云端安全校验

解决：

> 这个命令从业务和设备状态上是否安全？

---

## 第四层：Edge 本地安全校验

解决：

> 到现场以后，当前实际状态是否仍然允许执行？

---

## 第五层：设备自身保护

解决：

> PCS、BMS、PLC 的硬件和控制器最终是否接受？

多层检查可以防止：

```text
云端错误
```

直接演化成：

```text
现场事故
```

---

# 五、身份认证 IAM

平台用户必须经过统一 IAM。

建议支持：

```text
Username / Password

MFA

SSO

OIDC / OAuth2
```

企业场景可以进一步接：

```text
Active Directory

LDAP

Corporate Identity Provider
```

---

# 六、用户身份与设备身份分离

必须区分：

```text
Human Identity
```

和：

```text
Machine Identity
```

例如：

```text
User
Gateway
Service
Optimization Engine
API Client
```

都应该拥有独立身份。

不能使用同一个：

```text
admin / admin
```

账号横跨系统。

---

# 七、服务身份

内部服务之间调用也不应该完全信任。

例如：

```text
Optimization Service
 ↓
Control Service
```

Control Service 应知道：

```text
Caller = optimization-service
```

而不是只知道：

```text
HTTP 请求来自内网。
```

可以逐步采用：

```text
Service Token

mTLS

Workload Identity
```

---

# 八、RBAC 权限模型

建议至少建立：

```text
User

Role

Permission
```

模型。

例如角色：

```text
System Admin

Energy Manager

Operator

Viewer

Finance

Maintenance

Security Admin
```

---

# 九、普通权限与控制权限分离

这是非常重要的原则。

用户有：

```text
device.read
```

不代表拥有：

```text
device.control
```

例如权限：

```text
asset.read

device.read

telemetry.read

alarm.ack

command.create

command.approve

command.execute

control.auto.enable
```

应该明确分离。

---

# 十、控制权限粒度

不能只有：

```text
can_control = true
```

建议至少支持：

```text
Tenant

Site

Asset

Device

Command Type
```

粒度。

例如：

```text
User A

可以控制：

Site 上海

Asset ESS001

Command SET_POWER
```

但不能控制：

```text
Circuit Breaker
```

---

# 十一、控制操作分类

建议将控制操作分级。

## Level 1：低风险

例如：

```text
调整展示参数

刷新设备状态

重新采集
```

---

## Level 2：普通运行控制

例如：

```text
HVAC setpoint

EV charge limit

ESS power setpoint
```

---

## Level 3：高风险控制

例如：

```text
PCS Start

PCS Stop

Breaker Open

Breaker Close

Emergency Stop Reset
```

---

## Level 4：关键保护配置

例如：

```text
SOC Safety Limit

BMS Protection Threshold

Maximum Discharge Limit
```

需要更严格权限。

---

# 十二、控制权限模型

可以设计：

```text
ControlPermission
```

包含：

```text
subject

site_scope

asset_scope

device_scope

command_type

risk_level

allowed_time

requires_approval
```

例如：

```text
Operator A

Site:
Shanghai

Device Type:
PCS

Command:
SET_POWER

Max Risk:
Level 2
```

---

# 十三、最小权限原则

所有角色采用：

# Least Privilege

原则。

例如：

能源分析人员只需要：

```text
read telemetry

read metric
```

不应该拥有：

```text
control
```

运维工程师可能有：

```text
device configuration
```

但不一定拥有：

```text
finance tariff
```

---

# 十四、职责分离

重要操作建议采用：

```text
Separation of Duties
```

例如：

```text
控制策略创建者
```

和：

```text
控制策略批准者
```

不能永远是同一个人。

特别是：

```text
高风险控制

自动控制上线

安全参数修改
```

---

# 十五、控制模式设计

设备或者资产应该具有统一 Control Mode。

建议：

```text
LOCAL

REMOTE_MANUAL

REMOTE_AUTO

MAINTENANCE

LOCKED
```

---

# 十六、LOCAL

表示：

```text
现场控制优先
```

云端控制全部拒绝。

例如：

```text
Local Panel

PLC
```

正在现场操作。

Control Service 返回：

```text
DEVICE_LOCAL_MODE
```

---

# 十七、REMOTE_MANUAL

允许：

```text
授权用户
```

从平台人工发起控制。

但是：

```text
Optimization
```

不能自动执行。

---

# 十八、REMOTE_AUTO

表示：

经过授权以后：

```text
Optimization

Rule Engine

Scheduler
```

可以自动执行。

这是高级智慧能源系统最终需要的模式。

---

# 十九、MAINTENANCE

设备正在检修。

通常：

```text
所有自动控制禁止
```

只允许特定 Maintenance Role 操作。

---

# 二十、LOCKED

设备因安全原因被锁定。

例如：

```text
严重故障

人工锁定

安全事件
```

任何远程控制：

```text
REJECT
```

---

# 二十一、模式切换权限

从：

```text
REMOTE_MANUAL
```

切换到：

```text
REMOTE_AUTO
```

本身就应该是一个受控操作。

不能让算法自己决定：

```text
我要进入自动控制模式。
```

必须通过：

```text
授权用户 / 审批策略
```

开启。

---

# 二十二、Manual 与 Auto 分离

控制来源建议统一：

```text
MANUAL

SCHEDULE

RULE

OPTIMIZATION

EMERGENCY

EXTERNAL
```

每个 Command 必须记录：

```text
source_type
```

例如：

```text
source_type = OPTIMIZATION
```

这样才能审计：

> 这个命令是人发的还是算法发的？

---

# 二十三、控制命令模型

Command 至少包含：

```text
command_id

tenant_id

site_id

asset_id

device_id

point_id

command_type

target_value

source_type

source_id

requested_by

risk_level

reason

status

requested_at
```

以及：

```text
approved_by

approved_at

sent_at

executed_at

completed_at

result

error
```

---

# 二十四、Command 状态机

推荐：

```text
CREATED
   ↓
VALIDATING
   ↓
WAITING_APPROVAL
   ↓
APPROVED
   ↓
SENDING
   ↓
SENT
   ↓
EXECUTING
   ↓
SUCCESS
```

异常状态：

```text
REJECTED

FAILED

TIMEOUT

CANCELLED

EXPIRED
```

---

# 二十五、命令必须有生命周期

错误设计：

```text
POST /control

→ mqtt.publish()

→ 200 OK
```

这只能说明：

```text
MQTT publish 成功。
```

不能说明：

```text
设备执行成功。
```

所以必须维护 Command 状态。

---

# 二十六、Command ID

所有命令必须拥有全局唯一：

```text
command_id
```

例如：

```text
CMD-20260808-000001
```

贯穿：

```text
React

Go API

Control Service

MQTT

Edge

Device Feedback
```

全链路。

---

# 二十七、命令幂等

如果因为网络问题：

```text
Command 123
```

发送两次。

Edge 收到：

```text
CMD123
CMD123
```

只能执行一次。

需要：

```text
Idempotency
```

机制。

Edge 维护：

```text
executed_command_cache
```

如果重复：

```text
直接返回原执行结果。
```

---

# 二十八、命令有效期

所有命令建议带：

```text
expire_at
```

例如一个：

```text
18:00 放电 500kW
```

的命令。

如果：

```text
18:30
```

由于网络恢复才收到，就可能已经失去意义。

应该：

```text
EXPIRED
```

而不是继续执行。

---

```text
Validation Pipeline
```

顺序：

```text
 ↓

 ↓
```

# 三十、Permission Check

例如用户：

```text
只能控制 Site A
```

却请求：

```text
Site B PCS
```

直接：

```text
FORBIDDEN
```

---

# 三十一、Device Online Check

设备：

```text
OFFLINE
```

通常不应该发送：

```text
SET_POWER
```

直接：

```text
DEVICE_OFFLINE
```

---

# 三十二、Point Writable Check

例如：

```text
active_power
```

是：

```text
READ
```

不允许写。

而：

```text
target_power
```

是：

```text
READ_WRITE
```

才允许。

---

# 三十三、数据类型检查

例如：

```text
target_power
```

要求：

```text
FLOAT
```

却收到：

```text
"AUTO"
```

应该在进入 IoT 之前拒绝。

---

# 三十四、Range Check

例如 PCS：

```text
max_charge_power = 500kW

max_discharge_power = 500kW
```

请求：

```text
2000kW
```

直接拒绝。

---

# 三十五、动态安全范围

安全范围不一定是固定值。

例如：

```text
max_discharge_power
```

可能来自 BMS 实时能力：

```text
Allowed Discharge Power
```

例如：

```text
Rated = 500kW

BMS Available = 180kW
```

当前最大只能：

```text
180kW
```

因此 Range Validator 应支持：

```text
Static Constraint

+

Dynamic Constraint
```

---

# 三十六、SOC 安全边界

例如储能规定：

```text
SOC Min = 10%

SOC Max = 95%
```

如果：

```text
SOC = 8%
```

收到：

```text
DISCHARGE 200kW
```

必须拒绝。

---

# 三十七、温度约束

例如：

```text
Battery Max Temperature > 55°C
```

则：

```text
Charge / Discharge
```

可以根据安全策略：

```text
Reduce Power

or

Reject Control
```

---

# 三十八、设备状态约束

例如 PCS 当前：

```text
FAULT
```

则：

```text
SET_POWER
```

无意义。

只有：

```text
RESET
```

可能允许。

因此 Validator 必须基于：

```text
Device State Machine
```

判断。

---

# 三十九、Interlock 联锁

控制系统必须支持：

```text
Interlock
```

例如：

```text
如果 Main Breaker = OPEN
```

禁止：

```text
PCS Grid Connected Operation
```

另一个：

```text
Cooling Pump = OFF
```

禁止：

```text
Chiller Start
```

---

# 四十、联锁模型

可以抽象为：

```text
Command

requires

Condition A

Condition B
```

例如：

```text
START_CHILLER

requires:

pump_running == true

valve_open == true

no_fault == true
```

---

# 四十一、硬联锁与软联锁

需要区分：

## Hard Interlock

由：

```text
PLC

BMS

Protection Relay

Hardware
```

实现。

云平台不能绕过。

---

## Soft Interlock

由：

```text
Cloud Control Service

Edge Rule Engine
```

实现。

用于额外业务安全。

关键安全必须优先：

```text
Hard Interlock
```

---

# 四十二、安全职责原则

云端绝不能承担：

```text
唯一的设备保护逻辑。
```

例如：

```text
过压

过温

短路

电池保护
```

这些必须由：

```text
Hardware / BMS / PLC
```

保证。

Cloud 只是：

```text
高级管理和额外防护。
```

---

# 四十三、Rate Limit

控制命令必须限制频率。

例如：

```text
SET_POWER
```

不能：

```text
每 10ms
```

变化一次。

可以定义：

```text
max_commands_per_minute
```

或者：

```text
min_interval
```

---

# 四十四、Ramp Rate

储能等设备还要考虑：

```text
Ramp Rate
```

例如：

当前：

```text
0kW
```

目标：

```text
500kW
```

可能不能瞬间变化。

可以定义：

```text
100kW / second
```

由策略：

```text
0

100

200

300

400

500
```

逐步调整。

---

# 四十五、Deadband

优化算法可能不断输出：

```text
498

501

499

502
```

不应该每次都控制。

可以定义：

```text
power_deadband = 10kW
```

如果变化小于：

```text
10kW
```

忽略。

减少设备频繁动作。

---

# 四十六、Minimum Hold Time

例如 HVAC：

```text
Chiller
```

启动以后应该至少运行：

```text
10 min
```

避免：

```text
Start

Stop

Start

Stop
```

频繁启停。

因此控制规则必须支持：

```text
minimum_on_time

minimum_off_time
```

---

# 四十七、Command Approval

高风险控制可以要求审批。

例如：

```text
OPEN_BREAKER
```

进入：

```text
WAITING_APPROVAL
```

由授权人员：

```text
Approve
```

以后才能执行。

---

# 四十八、双人审批

特别关键的操作可以：

```text
Four Eyes Principle
```

例如：

```text
Person A 发起

Person B 批准
```

防止：

```text
单人误操作
```

---

# 四十九、审批策略

可以定义：

```text
Risk Level 1

→ No Approval
```

```text
Risk Level 2

→ Optional Approval
```

```text
Risk Level 3

→ Required Approval
```

```text
Risk Level 4

→ Dual Approval
```

---

# 五十、审批超时

审批不能无限有效。

例如：

```text
Command Approved at 10:00
```

但：

```text
11:00
```

设备状态已经变化。

因此批准后的命令也应该：

```text
expire
```

并在执行前再次：

```text
Safety Validation
```

---

# 五十一、执行前二次检查

重要原则：

# Validate Before Execute

即使：

```text
10:00
```

审批通过。

实际：

```text
10:02
```

发送前，还要再次读取：

```text
SOC

Device Mode

Fault Status

Dynamic Limits
```

确认仍然安全。

---

# 五十二、Edge 二次校验

Cloud 检查通过以后，Edge 仍然必须再次检查。

因为从：

```text
Cloud Validation
```

到：

```text
Gateway Execution
```

之间设备状态可能改变。

例如：

```text
Cloud:
SOC = 20%
```

命令到 Edge 时：

```text
SOC = 8%
```

Edge 必须：

```text
REJECT
```

---

# 五十三、云端与 Edge 权限关系

Cloud：

```text
决定是否允许发起。
```

Edge：

```text
决定现场是否允许执行。
```

Device：

```text
最终决定硬件是否接受。
```

三层都必须有拒绝权。

---

命令消息建议：

# 五十五、命令签名

高安全场景可以增加：

```text
signature
```

确保：

```text
命令没有在途中被篡改。
```

Edge 验证：

```text
identity

timestamp

signature

command_id
```

# 五十六、防重放攻击

攻击者如果截获：

```text

```

不能以后重复发送。

可以通过：

```text
Command ID

Timestamp

Nonce
```

# 五十七、MQTT 安全

生产建议：

```text
MQTT over TLS
```

```text
8883
```

并且 Gateway 最好：

```text
独立证书
```

例如 Gateway G100：

只允许：

```text

energy/.../G100/+/command
```

```text
G100 state

```

```text
+
certificate
```

```text
certificate
```

确定：

```text
tenant

site

gateway
```

不能完全相信 MQTT Topic 里客户端自己写的 tenant。

# 八十七、Fallback Strategy

Cloud Optimization 故障以后：

Edge 可以：

```text

```

或者：

```text

```

例如储能：

```text

```

必须针对设备定义：


# 八十八、Fail Safe

系统故障时应该进入：

```text
安全状态
```

而不是任意状态。

例如：

```text

```

ESS 是否：

```text
0kW

Last Setpoint

Local EMS
```

必须由业务安全分析确定。

# 八十九、Fail Open 与 Fail Closed

不同场景不同。

例如：

安全控制通常倾向：

```text

```

即不确定时拒绝控制。

但某些持续运行系统可能需要：

```text
Fail Operational
```

维持本地运行。

不能所有设备一个规则。

# 九十一、网络重试

控制消息重试必须非常谨慎。

对于：

```text

```

通常可以幂等重试。

但对于：

```text
TOGGLE
```

这种命令非常危险。

应尽量避免设计：

```text
TOGGLE
```

而使用明确：

```text
OPEN

CLOSE

START

STOP
```

# 九十二、避免非幂等命令

优先：

```text
SET_MODE AUTO

SET_POWER 500

START

STOP
```

避免：

```text
TOGGLE_MODE

INCREASE_POWER
```

因为网络重试容易导致不可预期结果。

# 九十三、Read Back

命令写入设备以后：

```text

 ↓
Read Back
```

验证。

之后读取：

```text

```

或者：

```text

```

# 一百七十九、最核心原则

整套安全与控制架构最终建议坚持十条原则：

**第一，所有设备控制必须经过 Control Service。**

任何业务服务、React、AI、Optimization 都不能直接控制设备。

**第二，控制必须 Default Deny。**

没有明确权限和规则就拒绝。

**第三，安全检查必须云边两级执行。**

Cloud 通过不代表 Edge 必须执行。

**第四，硬件保护永远优先于软件控制。**

BMS、PLC、保护装置的安全边界不能被 Cloud 绕过。

**第五，Manual、Automatic、Local 必须明确区分。**

控制权必须清晰。

**第六，所有 Command 必须幂等、可过期、可追踪。**

不能只有一条 MQTT 消息。

**第七，所有执行必须有反馈和验证。**

Send Success 不等于 Device Success。

**第八，高风险控制需要审批和职责分离。**

尤其是断路器、保护参数、自动控制开启等操作。

**第九，算法只有建议权或受限执行权，不拥有无限控制权。**

Optimization 必须受 Safety Policy 约束。

**第十，任何关键系统故障都应该进入安全状态。**

Cloud、MQTT、Gateway 或策略异常不能导致设备处于不可控危险状态。

# 一百八十、最终核心思想

整个智慧能源控制系统真正的设计原则，可以浓缩成一句话：

# Optimization 决定“最好怎么做”，Safety 决定“允许怎么做”，Control 决定“如何可靠执行”。

最终形成：

```text
Observe
 ↓
Analyze
 ↓
Predict
 ↓
Optimize
 ↓
Validate
 ↓
Authorize
 ↓
Control
 ↓
Verify
 ↓
Audit
```

相比普通：

```text
Predict → Control
```

智慧能源生产系统必须增加：

```text
Validate

Authorize

Verify

Audit
```

四个关键环节。

# 智慧能源控制平台
