建议采用：

**Go + React + PostgreSQL/ClickHouse + Redis + MQTT**

第一阶段先不要急着引入 Kafka 和复杂微服务。

# 二、为什么不建议第一阶段全微服务

智慧能源系统早期主要复杂度其实来自：

```text
设备模型

测点模型

时序数据

能源模型

拓扑关系

控制链路
```

而不是 HTTP 服务数量。

所以第一阶段建议：

```text
energy-api
```

采用：

**模块化单体 Modular Monolith**

内部按照领域拆分：

```text
IAM

Tenant

Site

Asset

Device

Energy

Alarm

Control

Tariff
```

而以下几个高吞吐或者独立特征比较明显的服务单独部署：

```text
iot-service

telemetry-worker

optimization-service
```

以后流量扩大，再把内部模块独立成服务。


# 十六、MQTT Handler

逻辑可以设计为：

```go
func (h *MQTTHandler) HandleTelemetry(
	ctx context.Context,
	topic string,
	payload []byte,
) error {

	meta, err := ParseTopic(topic)
	if err != nil {
		return err
	}

	var msg TelemetryMessage

	if err := json.Unmarshal(payload, &msg); err != nil {
		return err
	}

	device, err := h.deviceRepo.FindByCode(
		ctx,
		meta.Site,
		meta.Device,
	)
	if err != nil {
		return err
	}

	batch, err := h.normalizer.Normalize(
		ctx,
		device,
		msg,
	)
	if err != nil {
		return err
	}

	return h.telemetry.Write(ctx, batch)
}
```

实际项目中不要在 handler 内塞全部业务逻辑。

# 二十一、ClickHouse 数据模型

推荐：

```sql
CREATE TABLE telemetry_raw (
    event_time      DateTime64(3, 'UTC'),
    ingest_time     DateTime64(3, 'UTC'),
    tenant_id       UInt64,
    site_id         UInt64,
    device_id       UInt64,
    point_id        UInt64,
    point_code      LowCardinality(String),
    value_double    Nullable(Float64),
    value_text      Nullable(String),
    value_bool      Nullable(UInt8),
    quality         LowCardinality(String),
    source_seq      UInt64
)
ENGINE = MergeTree
PARTITION BY toYYYYMM(event_time)
ORDER BY (tenant_id, site_id, device_id, point_id, event_time, source_seq);
```

核心查询维度：

```text
tenant_id + site_id + device_id + point_id + time range
```

# 二十二、Go 数据库访问

推荐：

```text
pgx
```

作为 PostgreSQL 驱动。

如果希望 SQL 明确可控，推荐：

```text
pgx + sqlc
```

而不是在整个能源平台里大量依赖 ORM 自动生成 SQL。

原因：

智慧能源系统后面会出现很多：

```text
复杂统计

CTE

窗口函数

ClickHouse 查询

时间聚合

批量写入
```

原生 SQL 往往更加清晰。

推荐组合：

```text
PostgreSQL: pgx + sqlc + golang-migrate
ClickHouse: clickhouse-go/v2
```

PostgreSQL 与 ClickHouse 使用独立连接池和 Repository/Query 边界，禁止通过 PostgreSQL 驱动访问 ClickHouse。

```go
func RegisterRoutes(
	r chi.Router,
	handler *Handler,
) {

	r.Route("/api/v1/devices", func(r chi.Router) {

		r.Get("/", handler.List)

		r.Post("/", handler.Create)

		r.Route("/{deviceId}", func(r chi.Router) {

			r.Get("/", handler.Get)

			r.Put("/", handler.Update)

			r.Delete("/", handler.Delete)

			r.Get("/points", handler.ListPoints)
		})
	})
}
```

# 五十三、Go Service 示例

例如 DeviceService：

```go
type DeviceService struct {
	repo DeviceRepository
}

func (s *DeviceService) Get(
	ctx context.Context,
	publicID string,
) (*Device, error) {

	tenantID := auth.TenantIDFromContext(ctx)

	device, err := s.repo.GetByPublicID(
		ctx,
		tenantID,
		publicID,
	)

	}

	return device, nil
}
```

# 六十四、最终软件主链路

整个 Go + React 智慧能源系统，最终应该围绕这一条链开发：

```text
                        React
                          │
                          ▼
                       Go API
                          │
                          ▼
Asset → Device → Point → Telemetry
                          │
                          ▼
                        Metric
                          │
                          ▼
                        Energy
                          │
                          ▼
                       Forecast
                          │
                          ▼
                     Optimization
                          │
                          ▼
                       Command
                          │
                          ▼
                       Control
                          │
                          ▼
                          IoT
                          │
                          ▼
                        Device
                          │
                          └──────────→ Telemetry
```

也就是最终形成：

**Device → Point → Telemetry → Metric → Energy → Forecast → Optimization → Command → Device**

这个闭环应该成为整个项目的软件架构主线。

如果使用 Go + React，我建议最先把下面五个 Go Domain 写扎实：

**Device Domain**

**Telemetry Domain**

**Energy Domain**

**Topology Domain**

**Control Domain**

这五块设计正确之后，智慧能源平台的主体架构基本就稳定了。
