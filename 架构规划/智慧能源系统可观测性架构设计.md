# 智慧能源系统可观测性架构设计

## 一、设计目标

智慧能源系统的可观测性不能只解决：

```text
CPU 高不高？

服务挂没挂？

接口有没有 500？
```

还必须回答：

```text
某个 Gateway 为什么离线？

某台设备的数据为什么断了？

Telemetry 为什么延迟了 30 秒？

一个 Point 为什么一直是 BAD？

昨日能耗为什么少了 20%？

某条告警为什么晚了 5 分钟？

某条控制命令为什么没有执行？

Optimization 明明生成了调度，为什么 PCS 没动作？

历史补传积压了多少？

哪个 Site 正在接近平台容量上限？
```

因此智慧能源平台的可观测性应该同时覆盖：

# 系统健康 + IoT连接 + 数据链路 + 能源业务 + 告警 + 控制 + Edge + 安全

而不是单纯的服务器监控。

---

# 二、总体可观测性模型

建议采用五类核心信号：

```text
Metrics

Logs

Traces

Events

Audit
```

其中：

```text
Metrics
```

回答：

> 系统现在整体怎么样？

```text
Logs
```

回答：

> 某个服务具体发生了什么？

```text
Traces
```

回答：

> 一个请求或一条数据经过哪些组件？

```text
Events
```

回答：

> 系统发生了哪些离散状态变化？

```text
Audit
```

回答：

> 谁做了什么、为什么、结果是什么？

# 六、Metrics 命名原则

建议统一使用：

```text
lower_snake_case
```

例如：

```text
http_requests_total

telemetry_values_total

gateway_online_count

command_success_total
```

如果采用 Prometheus 风格：

Counter：

```text
xxx_total
```

Gauge：

```text
xxx_count
xxx_seconds
xxx_bytes
```

Histogram：

```text
xxx_duration_seconds
```

保持整个 Go 平台一致。

---

# 七、Metrics Label 控制

Label 很重要，但不能无限使用。

合理：

```text
service

environment

result

protocol

device_type
```

谨慎：

```text
tenant_id

site_id
```

避免直接放：

```text
device_id

point_id

command_id

user_id
```

到高频 Metrics Label。

原因是：

```text
Cardinality Explosion
```

例如：

```text
1,000,000 Points
```

如果全部作为 Prometheus Label，会产生非常巨大的时间序列数量。

---

# 八、高基数数据放哪里

例如：

```text
device_id

point_id

command_id

trace_id
```

应该主要存在：

```text
Logs

Trace

Database
```

而不是全部作为 Metrics Label。

# 十一、Go API Metrics

建议至少：

```text
http_requests_total

http_request_duration_seconds

http_request_in_flight

http_response_size_bytes

http_errors_total
```

Labels：

```text
service

method

route

status_class
```

不要使用完整 URL：

错误：

```text
/api/v1/devices/uuid-001
/api/v1/devices/uuid-002
```

应该统一：

```text
/api/v1/devices/{deviceId}
```

避免高基数。

# 十二、API Latency

核心看：

```text
P50

P95

P99
```

例如非功能目标：

```text
Latest API P95 < 300ms
```

```text
Energy Overview P95 < 1s
```

这些必须直接形成 Dashboard。

---

# 十三、API Error Rate

建议：

```text
5xx Rate

4xx Rate
```

分别观察。

例如：

```text
5xx > 1%
```

通常属于系统异常。

但：

```text
403
```

可能只是权限拒绝，不能简单视为服务故障。

---

# 二十九、Values/s

必须长期展示：



# 三十、Messages/s

```text

```

```text

```


# 三十一、Telemetry Lag

核心指标：

```text
telemetry_processing_lag_seconds
```

定义：

```text
processing_time
-
event_time
```

例如：

```text
Device Time:
10:00:00

Cloud Process:
10:00:04
```

则：

```text
Lag = 4s
```

---

# 三十二、Telemetry Lag SLO

结合前面的非功能目标：

```text

```

应形成标准 Dashboard。

同时监控：

```text
P50

P95

P99

Max
```


必须监控：

# 四十、Replay Backlog

例如：


# 四十一、Realtime 与 Replay 分离

Dashboard 要分别显示：

```text
Realtime Throughput

Replay Throughput
```

否则网络恢复时：

```text
Values/s
```

突然暴涨，很难判断是否真实设备负载增加。

# 四十三、Metric Lag

例如：

```text

```

```text

```



# 六十二、IoT Log

记录：

```text

```

# 六十三、Telemetry Log

不要记录每一个：

```text
Point Value
```

否则日志量会巨大。

正常高频 Telemetry 应主要通过：

```text
Metrics
```

观察。

```text

```

# 六十四、Control Log

重要控制必须记录：

```text

result
```

# 六十五、Security Log

```text

```

---

# 六十六、Audit Log

Audit 与普通日志不同。

必须结构化保存：

```text
Who

When

Action

Resource

Before

After

Reason

Result
```

例如：

```text
User A
修改 ESS SOC_MIN
15%
→
10%
```

---

# 六十七、Audit 不依赖普通日志系统

普通日志可能：

```text
7天后删除
```

但：

```text
Control Audit

Security Audit
```

可能需要保留多年。

因此 Audit 最好独立持久化。

---

# 六十八、Log Level

统一：

```text
DEBUG

INFO

WARN

ERROR
```

生产环境默认：

```text
INFO
```

临时诊断可以针对：

```text
某个 Gateway

某个 Device
```

# 六十九、动态 Debug

非常建议 Edge / IoT 支持：

```text
Scoped Debug
```

例如：

```text

```

而不是整个 IoT 平台：

```text
DEBUG ON
```

否则日志量可能爆炸。

# 一百六十八、最终设计原则

整个智慧能源可观测性体系建议坚持以下原则：

**第一，可观测性不只是服务器监控。**

必须覆盖 Device、Gateway、Telemetry、Metric、Alarm、Control。

**第二，Metrics、Logs、Trace、Event、Audit 各自承担不同职责。**

不要全部依赖日志。

**第三，智慧能源平台最重要的技术指标之一是 Telemetry Lag 和 Data Quality。**

服务不宕机但数据不更新，同样属于系统故障。

**第四，高基数数据不能随意作为 Metrics Label。**

device_id、point_id 主要进入 Logs / Trace / Database。

**第五，所有非功能 SLO 必须能够在线持续测量。**

不能只在测试报告中存在。

**第六，Telemetry 高流量 Trace 需要采样，Control Trace 应尽可能完整保留。**

不同业务价值采用不同策略。

**第七，Cloud、Edge、Device 三层都必须可观察。**

否则 OT 问题和 Cloud 问题无法快速区分。

**第八，可观测性告警和能源业务告警要区分。**

一个监控平台，一个监控真实能源资产。

**第九，Dashboard 必须围绕问题定位设计，而不是为了展示更多图表。**

运维必须能够快速回答“故障在哪里”。

**第十，可观测性本身也必须进行容量治理。**

Metrics、Logs、Trace 也需要 Retention、Sampling 和 Cardinality 管理。

# 一百七十、最终结论

智慧能源系统真正成熟的可观测性，不应该只是做到：

```text
“服务器挂了能报警。”
```

而应该做到：

```text
“我知道哪个Site出现问题。”

“我知道问题发生在哪个Gateway。”

“我知道是哪一段Telemetry Pipeline变慢。”

“我知道哪些数据因此缺失。”

“我知道哪些Metric受到影响。”

“我知道某个Alarm为什么产生。”

“我知道某条Command为什么被拒绝。”

“我知道一个故障最终影响了哪些用户和能源业务。”
```

最终形成：

# Observe → Detect → Correlate → Diagnose → Respond → Recover → Improve

完整运维闭环。

对于当前这套智慧能源平台，推荐从第一版就落地：

```text
Structured Logs

Prometheus-style Metrics

Request / Trace Context

Gateway Health

Telemetry Lag

Data Quality

Command Observability

核心 Dashboard
```

然后随着平台规模扩大，再逐渐增加：

```text
Distributed Trace

Data Observability

Root Cause Correlation

Capacity Forecast

Optimization Observability
```

这样可观测性会成为：

**部署运维、容量规划、测试验收、安全控制和生产稳定性的共同基础设施。**
