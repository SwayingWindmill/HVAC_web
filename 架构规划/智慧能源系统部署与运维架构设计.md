# 智慧能源系统部署与运维架构设计

## 一、设计目标

智慧能源系统与普通互联网系统不同。

它不仅包含：

- Web
    
- API
    
- 数据库
    
- 消息系统
    

还连接：

- Edge Gateway
    
- 电表
    
- 光伏
    
- 储能
    
- HVAC
    
- 充电桩
    
- PLC
    
- 工业设备
    

因此部署与运维架构必须同时考虑：

**IT 系统稳定性**

和

**OT 系统连续运行能力。**

总体目标是建立：

```text
可部署
+
可扩展
+
可监控
+
可升级
+
可恢复
+
可审计
```

的生产运行体系。

---

# 二、总体部署架构

推荐整体采用：

```text
Edge
+
Central Platform
+
Data Platform
+
Monitoring Platform
```

架构。

总体结构：

```text
                    用户
                     │
                HTTPS / WSS
                     │
                     ▼
              ┌─────────────┐
              │ Load Balancer│
              │    Nginx     │
              └──────┬──────┘
                     │
          ┌──────────┴───────────┐
          │                      │
          ▼                      ▼
       React                  Go API
                                  │
                 ┌────────────────┼────────────────┐
                 │                │                │
                 ▼                ▼                ▼
             PostgreSQL         Redis          MQTT Broker
             ClickHouse                           │
                                                  │
                                           IoT Service
                                                  │
                                                  ▼
                                                Edge
                                                  │
                                              OT Device
```

后台同时运行：

```text
Telemetry Worker

Alarm Engine

Metric Engine

Forecast Service

Optimization Service
```

旁边增加统一：

```text
Monitoring

Logging

Tracing

Backup
```

体系。

# 三、环境划分

至少建议建立四套环境：

```text
Development

Testing

Staging

Production
```

---

# 四、Development 环境

开发环境主要用于：

```text
本地开发

接口调试

数据库开发

MQTT模拟

React调试
```

推荐开发人员通过：

```text
Docker Compose
```

启动：

```text
PostgreSQL

ClickHouse

Redis

MQTT Broker

Go API

IoT Service

Telemetry Worker
```

前端：

```text
React Dev Server
```

可以单独启动。

---

# 五、开发环境目标

开发环境必须做到：

```text
一条命令
```

可以启动基础依赖。

例如：

```text
docker compose up
```

而不是要求每个开发人员手工安装：

```text
PostgreSQL

Redis

MQTT

ClickHouse
```

否则环境差异会越来越严重。

---

# 六、Testing 环境

Testing 用于：

```text
API Test

Integration Test

Device Simulator Test

MQTT Test

Database Migration Test

Control Test
```

应尽量接近生产架构。

但可以使用较小资源。

---

# 七、Staging 环境

Staging 应尽可能：

```text
与 Production 一致
```

用于：

```text
Release Candidate

数据库升级验证

配置验证

性能验证

OTA验证

控制流程验证
```

生产升级之前：

```text
必须先经过 Staging。
```

---

# 八、Production 环境

生产环境主要目标：

```text
稳定

安全

可恢复

可观测
```

不能把生产环境当测试环境。

必须严格限制：

```text
直接登录数据库

直接修改配置

手工执行 SQL

直接 SSH 改程序

直接修改 MQTT 配置
```

所有变更应有正式流程。

---

# 九、环境隔离

不同环境必须拥有独立：

```text
Database

Redis

MQTT

Storage

Secrets

Domain

Configuration
```

禁止：

```text
Development
```

直接连接：

```text
Production Database
```

也不要让测试设备向正式 MQTT Broker 发送数据。

第一阶段不建议直接 Kubernetes。

对于：

```text
单园区

中小规模

开发早期
```

推荐：

```text
Linux Server

+

Docker Compose
```

运行：

```text
Nginx

Frontend

Go API

IoT Service

Telemetry Worker

PostgreSQL / ClickHouse

Redis

MQTT

Optimization Service
```

---

# 十二、第一阶段部署结构

```text

│
├── nginx
│
├── frontend
│
├── energy-api

├── iot-service
│
├── telemetry-worker

├── optimization-service

├── postgres
│
├── redis
│
```

# 十三、什么时候引入 Kubernetes

当出现：

```text
多服务器

多服务实例

高可用

大量站点

持续发布

自动扩缩容

团队规模扩大
```

以后，再迁移：

```text
Kubernetes
```

比较合理。

不要因为“微服务”三个字，就从第一天开始搭 Kubernetes。

# 十五、网络分区

建议至少划分：


# 十六、Public Zone

只暴露必要入口：

```text
HTTPS

WSS

MQTT TLS
```

例如：

```text

8883
```

数据库不能暴露公网。

# 十七、Application Zone

部署：

```text
Go API

Energy Service

Alarm Service

Control Service

IoT Service

Workers
```

只能通过内部网络访问：

```text
PostgreSQL

Redis

MQTT
```

---

# 十八、Data Zone

部署：

```text
PostgreSQL

ClickHouse

Redis

Object Storage
```

原则：

```text
只有授权的 Application Service 可以访问。
```

---

# 十九、Management Zone

部署：

```text
Monitoring

Logging

Backup

Admin

Deployment
```

运维人员通过受控入口访问。

# 二十、OT / Edge 网络

现场：

```text
Cloud / Data Center
        │
        │ MQTT TLS
        ▼
    Edge Gateway
        │
        │ OT Protocol
        ▼
 Modbus / BACnet / OPC UA
        │
        ▼
     Devices
```

Cloud 不应该直接访问：

```text
PCS

BMS

PLC
```

而是：

```text
Cloud
 ↓
Gateway
 ↓
OT Device
```

# 二十一、反向代理层

推荐：

```text
Nginx
```

或者其他成熟 Gateway。

主要负责：

```text
TLS

Reverse Proxy

Static Files

WebSocket

Rate Limit

Compression
```

---

# 二十二、React 部署

React 构建：

```text
npm build
```

产生静态资源。

生产环境不要：

```text
npm run dev
```

应该：

```text
React Build
 ↓
Static Assets
 ↓
Nginx
```

---

# 二十三、API 部署

Go API 推荐：

```text
Stateless
```

尽量不要把：

```text
Session

Local File State

Task State
```

保存在某一台 API Server。

状态放到：

```text
PostgreSQL

Redis

Object Storage
```

这样才能：

```text
API Instance 1

API Instance 2

API Instance 3
```

水平扩展。

---

# 二十四、IoT Service 部署

IoT Service 与普通 API 不完全一样。

它可能维持：

```text
MQTT Connection

Gateway Session

Device Session
```

需要明确：

```text
连接由谁负责

Session 怎么分配

多实例如何协调
```

---

# 二十五、Telemetry Worker

Telemetry Worker 负责：

```text
数据消费

标准化

缓存

写 ClickHouse

告警计算

指标触发
```

应该设计成：

```text
可多实例运行
```

规模增加时：

```text
Worker 1

Worker 2

Worker 3
```

共同消费任务。

---

# 二十六、服务无状态原则

除了：

```text
Database

Redis

Message Broker

Object Storage
```

之外，大部分业务服务应该：

```text
Stateless
```

这样才能实现：

```text
Rolling Upgrade

Auto Scaling

Failover
```

---

# 二十七、PostgreSQL 部署

第一阶段：

```text
PostgreSQL
+
ClickHouse
```

可以部署在一台独立数据库服务器。

不要与：

```text
大量 Worker

MQTT Broker

React
```

共享所有 CPU 和磁盘资源。

---

# 二十八、数据库高可用

中大型项目建议：

```text
Primary
+
Replica
```

形成：

```text
PostgreSQL Primary
        │
        ├── Replica 1
        └── Replica 2
```

Primary：

```text
Write
```

Replica：

```text
Read / Standby
```

---

# 二十九、数据库备份

数据库至少需要：

```text
Full Backup

Incremental / WAL Backup
```

策略。

例如：

```text
每天完整备份

持续 WAL 归档
```

这样可以支持：

```text
Point-in-Time Recovery
```

---

# 三十、RPO

必须明确：

```text
Recovery Point Objective
```

意思是：

> 最多允许丢多少数据？

例如：

```text
RPO ≤ 15 min
```

代表灾难发生时：

最多允许损失：

```text
15分钟数据。
```

对于关键能源系统可能要求更低。

---

# 三十一、RTO

必须明确：

```text
Recovery Time Objective
```

意思是：

> 系统故障以后多久必须恢复？

例如：

```text
RTO ≤ 1 hour
```

---

# 三十二、不同数据不同 RPO

例如：

```text
用户配置

RPO ≈ 0
```

```text
财务结算数据

RPO ≈ 0
```

而实时 Telemetry：

即使中心系统短暂丢失，也可能通过：

```text
Edge Store & Forward
```

进行补传。

这也是边缘架构的重要价值。

---

# 三十三、ClickHouse 生命周期

Telemetry 数据量通常最大。

需要：

```text
Retention

Compression

Aggregation

Archive
```

四个策略。

例如：

```text
5s Raw Data
 ↓
保留 30～90 天

1min Data
 ↓
保留 1～2 年

15min Data
 ↓
保留 5 年

Hourly / Daily
 ↓
长期保存
```

具体时间按照业务要求调整。

---

# 三十四、Redis 部署

Redis 主要保存：

```text
Latest Telemetry

Device State

Gateway State

Realtime Metric

Cache

Distributed Lock
```

Redis 中的数据原则上应该：

```text
可重建
```

不能把唯一业务数据只放 Redis。

---

# 三十五、Redis 故障

如果 Redis 丢失：

```text
Latest Value
```

应该能够从：

```text
ClickHouse

MQTT新数据
```

重新恢复。

因此 Redis：

```text
是加速层
```

而不是最终数据源。

---

# 三十六、MQTT Broker 部署

MQTT 是：

```text
Edge ↔ Cloud
```

关键通信基础设施。

必须监控：

```text
Connections

Subscriptions

Message Rate

Dropped Messages

Authentication Failure

Latency
```

---

# 三十七、MQTT 高可用

关键生产环境建议：

```text
MQTT Broker Cluster
```

而不是单实例。

因为如果 MQTT 故障：

```text
Gateway无法上传实时数据

Control无法下发
```

虽然 Edge 可以继续本地运行，但中心平台能力会下降。

---

# 三十八、对象存储

用于：

```text
报表

模型

导出文件

日志归档

设备文件

OTA包

历史冷数据
```

例如：

```text
S3 Compatible Storage
```

不要把：

```text
PDF

Excel

Firmware

Model File
```

全部直接存 PostgreSQL BLOB。

# 四十、Static Config



# 四十九、Database Migration

数据库升级必须进入发布流程。

例如：

```text

        ↓

        ↓

```

不能开发人员上线后手工：


# 五十、Migration 原则

migration 必须：

```text
可审查

可重复

可记录
```

并在：

```text
Staging
```

验证。

---

# 五十一、数据库兼容性升级

生产升级最好采用：

```text
Backward Compatible Migration
```

例如先：

```text
ADD COLUMN
```

再升级应用。

不要：

```text
先 DROP COLUMN
```

导致旧版本立即挂掉。

---

# 五十二、发布策略

第一阶段可以：

```text

 ↓
Deploy
 ↓
Start
```

适用于内部低风险测试环境。

生产建议：

```text
Rolling Deployment
```

---

# 五十三、Rolling Deployment

例如：

```text

API v1
```

逐台升级：

```text

API v1
API v1
```

然后：

```text

API v1
```

```text

API v2
```

# 五十四、Blue-Green

重要版本可以考虑：

```text

```

```text

```


# 五十五、Canary


# 六十一、业务技术指标

# 六十二、API 监控

至少监控：

```text

P50 latency

P99 latency

4xx

5xx

Timeout
```

例如：

```text

```

```text

```

```text
5s
```

---

# 六十三、Telemetry Pipeline 监控

必须监控：

```text
Incoming Values/s

Normalized Values/s

Written Values/s

Rejected Values/s

Queue Length

Processing Delay
```

整个链路：

```text
Gateway
 ↓
MQTT
 ↓
IoT
 ↓
Worker
 ↓
ClickHouse
```

每一段都应该可观察。

---

# 六十四、Telemetry Lag

非常重要。

定义：

```text
processing_time
-
event_time
```

例如：

设备数据时间：

```text
10:00:00
```

平台处理时间：

```text
10:00:20
```

则：

```text
Lag = 20s
```

如果正常应该：

```text
< 5s
```

就说明链路出现拥塞。

---

```text
Messages In

Authentication Failure

```

---

# 六十六、Gateway 监控

# 一百四十二、最终设计原则

部署与运维架构建议坚持以下原则：

**第一，生产、测试、开发必须隔离。**

不能共享核心数据库、MQTT 和 Secrets。

**第二，业务服务尽量无状态。**

为水平扩展和故障恢复做好准备。

**第三，数据库、MQTT 和时序数据属于关键基础设施。**

需要重点监控和备份。

**第四，Cloud 与 Edge 必须具有故障隔离能力。**

Cloud 故障不能导致现场安全系统停止。

**第五，所有生产变更必须可追溯。**

包括软件、数据库、设备模板、规则和控制参数。

**第六，备份必须定期验证恢复。**

“有备份文件”不等于“能够恢复”。

**第七，可观测性从项目第一天建设。**

Logs、Metrics、Trace 不是系统做完以后再补。

**第八，优先监控业务技术指标。**

例如：

```text
Device Online Rate

Telemetry Lag

Data Quality

Command Success Rate
```

这些往往比单纯 CPU 更重要。

**第九，部署架构应该随规模演进。**

第一阶段：

```text
Docker Compose
```

后期：

```text
HA / Kubernetes / Kafka / Cluster
```

不要过度设计，也不要没有演进空间。

**第十，控制系统与普通互联网服务区别对待。**

所有涉及真实能源设备的控制链路，都必须优先考虑：

```text
Safety

Audit

Availability

Fallback
```

而不仅仅是性能。
