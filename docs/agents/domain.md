# 业务文档

本仓库是单一上下文：根目录一份 `GLOSSARY.md`，架构决定在 `docs/adr/`。

## 看代码前

读 `GLOSSARY.md` 里和当前主题相关的名词，再读 `docs/adr/` 里和要动的地方相关的决定。

## 用术语表里的词

问题单标题、重构提议、猜测的原因、测试名、页面文字，提到业务概念时都用 `GLOSSARY.md` 的标题词；「不要说」里的词换成标题词。

- **名词格式**：每个业务词用 1-2 句写清「它是什么」，并在下面用「不要说：」列出禁用别称；超时、错误类型这类通用编程名词不放进业务术语表。
- **缺词处理**：需要的业务概念术语表里没有，先检查是不是在发明新说法（能用旧词就换回旧词），确认真缺时直接补进根目录 `GLOSSARY.md`。未来如果仓库拆出多个独立上下文，再在根目录建 `GLOSSARY-MAP.md`。

## ADR 格式与何时写

ADR 放在 `docs/adr/NNNN-slug.md`，编号按现有最大号加一。只在同时满足以下三条时才新建 ADR：

1. **日后难改**：换方案成本高、不是顺手改几行能撤回。
2. **不看背景会意外**：后来读代码的人会问「为什么当时要这么做」。
3. **确实在真实方案之间做过取舍**：有被拒绝的备选方案和理由（一两段写清背景、决定和取舍理由即可，只在必要时补 Status、Considered Options、Consequences）。

## 和 ADR 冲突时说出来

产出和已有的 ADR 冲突时，明确指出来再讨论，例如：

> _和 ADR 0016（使用方不保存负责方主数据的副本）冲突，但值得重新讨论，因为……_
