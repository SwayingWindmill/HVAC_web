# 问题单的交付流程

每张问题单按这五步交付，每一步做到「完成」那一句才进下一步。

1. **读清楚要做什么。** 读问题单、上级规格、评论、依赖的单子、`GLOSSARY.md` 和相关的 ADR；记下从哪个提交开始做，手头无关的改动单独提交。改动不熟悉的模块前先用 `how` 走读运行路径；涉及防御逻辑、阈值或历史取舍时，先用 `why` 查 `git blame`、PR 讨论与 ADR；涉及跨模块多状态设计或共享契约改动时，先用 `architect` 出结构草图，并用 `blast-radius` 跑真实代码验证关键假设与影响面。已经写成可以直接开工的单子，直接实现。
   完成：能用 `GLOSSARY.md` 的词说出要交付的每个行为和它的验收方式。
2. **参照外部项目时先读源码。** 借鉴外部项目时，看固定版本的官方源码、测试和文档，按 `AGENTS.md` 在 `docs/architecture/` 里记下采纳、改造或拒绝了什么。产品文档和设计文档比旧的实现更有说服力。
   完成：每个借来的设计都有固定版本的出处和取舍理由。
3. **一个行为一个行为地做。** 在规格约定的公开接口上，每个行为先写一个会失败的测试，再写代码让它通过；每一步都打通真实的产品路径，例如从页面一直到数据库。编辑 `.ts`/`.tsx` 时遵循 `typescript-best-practices`；如果同类错误或人工纠错重复出现两次，顺手按 `correct` 技能用类型或门禁消掉。
   完成：规格里的每个行为都有一个先失败、后通过的测试，并且在产品里能走通。
4. **在真实环境里按 `verify` 取证验收。** 在 WSL 里构建、测试、运行；按 `verify` 技能在 1440px 宽度下运行网页并把修改前后的截图与命令输出留在 `.scratch/verify/`。录制数据的测试结果和真实环境（`https://localhost:8443`）的结果分开记录。改动控制指令协议、设备围栏或 MQTT 回执关联状态时，加跑 `npm run command:formal` 验证 `P1`-`P6` 不变量。
   完成：每条验收标准都有可复查的运行输出或 1440px 截图证据。
5. **去噪、双轴审查后自动 PR 并合入。** 先按 `deslop` 技能对照分支差异清理多余注释与兜底，再做两方面审查（`code-review` 技能：是否符合仓库规范、是否符合规格）；改完直接推分支、按 `pr` 技能模板开关联问题单的 PR（附上 `Evidence` 与 `Merge Danger`），盯完 GitHub Actions：CI 全绿即自动 squash 合并进 `main` 并删分支，CI 失败则修复重跑直到全绿合并。
   完成：PR 已在 CI 全绿下合入 `main`，两方面审查的问题都已处理或写进 PR；验收全部完成后才关问题单。

对外发消息、重置数据和触发生产部署仍要当前会话里用户的授权。
