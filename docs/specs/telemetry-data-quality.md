# 点位数据质量

遥测在收下一条读数时，按站点文件里这个点位的质量配置做检查，把结果写在读数的质量上，并给出这个点位的健康。冷机 COP 只用质量为好的读数。告警用单独的数据质量规则告诉人，不再对每条温度发一条 6 小时的「提示」。

## 检查

| 检查 | 什么时候算有问题 | 读数怎么留 |
| --- | --- | --- |
| 量程 | 数值小于 `minimum_number` 或大于 `maximum_number`。量程设在传感器与工况的物理可信极限，不拿狭窄工艺期待值当量程拒收 | 拒收，质量无效，原因 `OUT_OF_RANGE`。当前值仍是上一条可信读数，点位健康记为无效（冷启动从未有过可信读数而只收到超量程拒收点时，健康原因仍保留 `OUT_OF_RANGE` 供告警评估） |
| 通讯异常值 | 数值落在配置的异常值上，容差 0.05。松雅轩设 `[38.4, -999, 85, 999]` | 收下，质量部分，原因 `SENTINEL`，并成为当前值；同时不叠加 `FLATLINE` |
| 采集源不可信 | 网关或设备协议上报非 0 质量位（例如无线探头离线降级 `quality: 1`） | 拒收或按规则置标 `SOURCE_UNTRUSTED`，拒收行同样记入点位健康原因；不叠加 `FLATLINE` |
| 跳变 | 与上一条相差超过 `maxStep`，而且两条相隔不超过 `maxStepWindowSeconds`（不写则按 15 分钟）。隔得更久的变化不当成跳变 | 收下，质量部分，原因 `SPIKE` |
| 卡住 | 数值没变（含非数值 `run_state` 连续追踪 `unchanged_since`），并且已经持续到配置的时长。配了「运行时」与 `flatlineStabilizeSeconds` 时，机组新开机未满稳定期先跳过，过了稳定期仍不变才记 `FLATLINE`；停机期未配停机时长则不报 | 收下，质量部分，原因 `FLATLINE`。历史回放不做这一条，因为它要对着当时的上一条，而不是现在的当前值 |
| 计算输入 | 这条读数是用别的点算出来的（供冷量、供回水温差、累计供冷量）。那些点当前质量不是好，或者健康是可疑或无效 | 收下，质量部分，原因 `DERIVED_INPUT`。累计量仍然更新，只是这一段用电或供冷会被记成可疑；派生计算设备（带 `derive`）在告警侧不再重复逐点发 `suspect` |
| 过期 | 点位自己的新鲜时限 `fresh_within_seconds`。站点文件里的 `staleAfterSeconds` 写入这个时限；不写则仍是采样周期的 3 倍 | 当前快照的新鲜度变成过期。健康原来是健康时改成过期（20 分）；已经是可疑或无效的不改口；且其它点位引用它作同伴状态时按过期忽略 |

量程、类型、单位不对，仍然拒收，和原来一样。跳变、异常值、卡住、输入不可信，以及铭牌和物理关系对不上（规格 `docs/specs/equipment-nameplate.md`，原因以 `PHYSICS_` 开头）是「部分」：人能在页面上看到这个数，冷量和能效不用它。

## 点位健康

每个当前点位带 `health`：`status` 为 `HEALTHY` / `SUSPECT` / `BAD` / `STALE`，`score` 为 100 / 40 / 0 / 20，`reasons` 是上面的原因。设备页上，不是健康的点位标「可疑」「无效」或「过期」。实时页的冷站 COP 只在相关读数健康时才算。

## 站点文件

`qualityProfiles` 写一套检查，点位用 `qualityProfile` 点名。接入脚本把它写进 `telemetry_runtime.freshness_policies` 的量程列和 `quality_checks`。没有档案的点位和以前一样，不设量程。

松雅轩：量程设为物理可信极限，冷冻水 `[-2, 40] °C`、冷却水 `[0, 50] °C`、房间 `[-10, 50] °C`、室外 `[-25, 50] °C`、湿球 `[-10, 40] °C`、用途未定的通道 `[-10, 60] °C`（`2.8 °C` 过冷低温正常收下并由过程规则 `chiller-leaving-low` 触发严重防冻保护，而不是当成量程异常丢弃）。异常值设 `[38.4, -999, 85, 999]`。冷/冷却水在对应机组进入运行且度过 `flatlineStabilizeSeconds`（600 秒）开机热平衡期后，连续 30 或 45 分钟不动才报卡住；室外温度 3 小时不动。供冷量看 `t16`、`t18` 当前是否可信，只标部分质量，不在告警侧复制发一条重复的 `suspect` 或 `btu-chw-direction`。

从别的点复制来的读数（`from`）同样做检查，这样优化读的房间温度、室外温度也会被标上。告警只报测点自己那一条，不把复制的再报一遍。

## 告警

规则文件的 `dataQuality` 与 `deviceUntrusted` 按质量档案生成规则，代替旧的每点一报或泛滥刷屏：

- 「数据不可信」（`data-quality/suspect/<device>/<point>`）：健康原因包含超出量程、跳变、异常值、采集源不可信或计算输入不可信并持续 `durationSeconds`（松雅轩 300 秒）触发；`temperature-uid20/t16`、`t18` 为「严重」，其余为「警告」，派生计算设备跳过不发。当非派生设备上具备至少 1 个其余仍可信的点位时才报单点；当全设备（>= 2 个受监点位）同时不可信时，自动收口并静音。
- 「整台采集异常」（`device-untrusted/<device>`，根因告警，`MAJOR`，#749）：当非派生设备的全部受监点位同时处于不可信状态（`OUT_OF_RANGE` / `SENTINEL` / `SOURCE_UNTRUSTED`）持续 180 秒，只发这一条整机根因告警，说明并替代同设备被暂抑的多条点位与下游规则；任一点位恢复可信即清除。
- 「读数长时间没有更新」（`readings-not-updated/<device>`）：各传感器叶子条件要求不存在不可信故障原因，不再因单个通道 `OUT_OF_RANGE` 拒收就额外报一次全设备未更新。
- 「卡住」（`data-quality/flat-running` / `flat` / `readings-flat`）：全部使用 `VALID_ONLY` 质量策略，叠加 `flatlineStabilizeSeconds` 持续门控，机组全部停机或读数恢复变化即自动恢复。

同一条规则同时只有一条告警（原来的去重）。过程告警仍是「只用好的读数」，所以点位变成部分或无效时，供水过高这类告警会停在「判断不了」，直到读数恢复可信。

## 下游

冷机 COP 的 15 分钟均值只取 `quality = 'GOOD'` 的功率、水温和供冷量。故障诊断和节能验证本来就只用好的读数。供冷量这一条若输入不可信，自己会被标成部分，COP 和之后按好的读数汇总的供冷都会丢掉这一段。温差相对探头误差过小也是同样的处理，见 `docs/specs/measurement-uncertainty.md`。
