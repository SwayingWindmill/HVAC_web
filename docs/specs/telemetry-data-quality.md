# 点位数据质量

遥测在收下一条读数时，按站点文件里这个点位的质量配置做检查，把结果写在读数的质量上，并给出这个点位的健康。冷机 COP 只用质量为好的读数。告警用单独的数据质量规则告诉人，不再对每条温度发一条 6 小时的「提示」。

## 检查

| 检查 | 什么时候算有问题 | 读数怎么留 |
| --- | --- | --- |
| 量程 | 数值小于 `minimum_number` 或大于 `maximum_number`（这两列原来就有，站点接入以前一直写空） | 拒收，质量无效，原因 `OUT_OF_RANGE`。当前值仍是上一条可信读数，点位健康记为无效 |
| 通讯异常值 | 数值落在配置的异常值上，容差 0.05。松雅轩的 38.4 是温度模块的通讯错误，冷却水 15–45 ℃ 的量程盖不住它 | 收下，质量部分，原因 `SENTINEL`，并成为当前值 |
| 跳变 | 与上一条相差超过 `maxStep`，而且两条相隔不超过 `maxStepWindowSeconds`（不写则按 15 分钟）。隔得更久的变化不当成跳变 | 收下，质量部分，原因 `SPIKE` |
| 卡住 | 数值没变，并且已经持续到配置的时长。配了「运行时」时：有机组在运行用较短的时长；机组都停着用较长的时长，没有较长时长就不报 | 收下，质量部分，原因 `FLATLINE`。历史回放不做这一条，因为它要对着当时的上一条，而不是现在的当前值 |
| 计算输入 | 这条读数是用别的点算出来的（供冷量、供回水温差、累计供冷量）。那些点当前质量不是好，或者健康是可疑或无效 | 收下，质量部分，原因 `DERIVED_INPUT`。累计量仍然更新，只是这一段用电或供冷会被记成可疑 |
| 过期 | 点位自己的新鲜时限 `fresh_within_seconds`。站点文件里的 `staleAfterSeconds` 写入这个时限；不写则仍是采样周期的 3 倍 | 当前快照的新鲜度变成过期。健康原来是健康时改成过期（20 分）；已经是可疑或无效的不改口 |

量程、类型、单位不对，仍然拒收，和原来一样。跳变、异常值、卡住、输入不可信，以及铭牌和物理关系对不上（规格 `docs/specs/equipment-nameplate.md`，原因以 `PHYSICS_` 开头）是「部分」：人能在页面上看到这个数，冷量和能效不用它。

## 点位健康

每个当前点位带 `health`：`status` 为 `HEALTHY` / `SUSPECT` / `BAD` / `STALE`，`score` 为 100 / 40 / 0 / 20，`reasons` 是上面的原因。设备页上，不是健康的点位标「可疑」「无效」或「过期」。实时页的冷站 COP 只在相关读数健康时才算。

## 站点文件

`qualityProfiles` 写一套检查，点位用 `qualityProfile` 点名。接入脚本把它写进 `telemetry_runtime.freshness_policies` 的量程列和 `quality_checks`。没有档案的点位和以前一样，不设量程。

松雅轩：冷冻水 3–20 ℃，冷却水 15–45 ℃，房间 10–40 ℃，室外 −10–45 ℃，湿球 −10–40 ℃，用途未定的通道 −10–60 ℃。38.4 是异常值。供水在有机组运行时 30 分钟不动就算卡住，机组都停着要 24 小时；室外温度 3 小时不动。供冷量看 t16、t18 现在是否可信。

从别的点复制来的读数（`from`）同样做检查，这样优化读的房间温度、室外温度也会被标上。告警只报测点自己那一条，不把复制的再报一遍。

## 告警

规则文件的 `dataQuality` 按质量档案生成规则，代替 `readingsFlat` 那种每条温度 6 小时一条「提示」：

- 「数据不可信」：健康原因里有超出量程、跳变、异常值或计算输入不可信。供回水和供冷量是「严重」，其余是「警告」。恢复是这些原因都没了。
- 「卡住」：和上面的时长一致。机组运行时的那条，机组全部停机也会恢复。

同一条规则同时只有一条告警（原来的去重）。过程告警仍是「只用好的读数」，所以点位变成部分或无效时，供水过高这类告警会停在「判断不了」，直到读数恢复可信。

## 下游

冷机 COP 的 15 分钟均值只取 `quality = 'GOOD'` 的功率、水温和供冷量。故障诊断和节能验证本来就只用好的读数。供冷量这一条若输入不可信，自己会被标成部分，COP 和之后按好的读数汇总的供冷都会丢掉这一段。
