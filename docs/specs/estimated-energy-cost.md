# 估算电度电费只有一个定义：Cube 按电价窗口给能耗区间计价

#575（父 #574，ADR 0023）。2026-10-17 与用户确认：由 Cube 计价，而不是查询服务、小时指标或浏览器；优化建议和 M&V 这次一起改。本文是实现契约。

现在电度电费在四处各算一遍：浏览器（`touEnergyCost`，按分钟把一小时拆到各时段）、报告服务、`energy_cost` 指标和 M&V（三者共用 `libs/tariffmodel`，整小时按小时开始时的电价）。三个站点的电价时段边界都在整点上，所以眼下数字一致；出现半点换时段，或电价换版本时，就会各说各话。Agent 还没有电费。

## 决定

| 决策 | 结论 |
| --- | --- |
| 谁定义电费 | Cube。内部 cube 把站点总表的用电区间与「电价窗口」做 ASOF JOIN，逐条区间计价；公开视图 `site_energy_cost` 给出电费、已计价电量、未计价电量，可按电价时段拆分 |
| 为什么不是查询服务计价 | 读路径只依赖 ClickHouse，不在每次读取时同步调用 Registry；电费是可相加的度量，按日、月、站点的汇总在 ClickHouse 里完成，能用 Cube 的缓存和预聚合；Agent 的语义查询（#573）直接能问电费，权限沿用视图的行策略 |
| 电价窗口 | ClickHouse 26.3 的时区函数要求时区是常量，没法按每个电价版本的时区在 SQL 里判断时段。所以由 Go 把电价版本按它自己的时区、日类型展开成逐日的 UTC 窗口 `[开始, 结束)`，带时段代码和电度单价；相邻同时段同单价的窗口合并。夏令时、将来的节假日日历都只在这一处处理 |
| 每条区间按什么时刻计价 | 区间结束时刻所在的窗口。与 Cube 把区间归入「结束时刻所在时段」的汇总规则一致；能耗区间中位数 2 秒、90% 不超过 60 秒（服务器实测），半点换时段自然算准，不再把一小时拆开 |
| 电价版本 | 与现在的 `LoadImportTariffs` 相同：站点电网进线（多条时取边界编码最小的一条）上，分配与版本都生效的那段时间，按当时生效的已发布版本计价。电价调整后窗口重算，已经算过的期间也跟着新窗口变（估算值，不是账单；账单仍以结算为准） |
| 币种 | 只支持 CNY；遇到其他币种的电价版本，投影明确报错停在该站点 |
| 质量 | 与能耗一致：`VALID_ONLY` 只计有效区间，`VALID_AND_SUSPECT` 再加可疑区间 |
| 缺电价 | 落在任何窗口之外的电量记为「未计价电量」，不按 0 元算；读者显示「部分时段没有电价」，与现在报告的 `UNPRICED_HOURS` 一致 |
| 谁写窗口 | 能源处理域（`modules/energy`）的电价窗口投影，跟能耗投影一起跑在遥测运行时里，用同一个工作负载身份（ADR 0017）向 Registry 取电价，Registry 新增内部接口返回站点在一段时间内的进线电价版本。工作负载角色 `energy-projection` 增加 `tariff.read` |
| 需量电费 | 按月最大需量算，不属于电度电费，这次不动 |
| 退役 | 浏览器的 `touEnergyCost`/`touCostByLabel`、报告服务自己的计价、`energy_cost` 指标（`TARIFF_ENERGY_COST`）以及 `tariffmodel.Rates`/`Covering` 全部删除 |

## 行为

### 电价窗口投影

1. 每 5 分钟一轮。需要计价的站点 = ClickHouse 里有站点总表用电区间的 `(tenant_id, site_id)`；时间范围从该站点第一条用电区间所在的本地日开始，到「现在 + 3 天」所在本地日结束。
2. 向 Registry `GET /internal/v1/registry/sites/{siteId}/import-tariffs?from=&to=`（`tariff.read` 授权）取这段时间的进线电价版本：生效区间（版本与分配的交集）、时区、币种、各时段（日类型、起止本地分钟、电度单价）。没有分配电价的站点返回空列表。
3. 用 `libs/tariffmodel` 展开窗口。电价版本序列的摘要与上次相同、范围已覆盖，就什么都不写；摘要相同只是范围要往后延，就按当前代次追加新的日子；摘要变了或范围要往前扩，就写一个新代次的完整窗口，写完再记同步行。
4. `analytics.tariff_price_windows_visible` 只露出每个站点最新同步行指向的代次，所以新代次是写完才切换；旧代次随后删除。
5. Registry 出错、币种不是 CNY 或时区无效时，该站点这一轮失败并记日志和计数，不写任何窗口，其他站点照常；已有窗口保持不变。

### Cube 与查询服务

6. 内部 cube `site_energy_cost_facts`：站点总表（`accounting_scope = 'SITE'`）用电区间 ASOF LEFT JOIN 可见窗口（同租户、同站点、`period_end >= window_start`），`period_end < window_end` 时取该窗口的单价和时段代码，否则未计价。两侧都先按站点过滤（`FILTER_PARAMS`），行策略与 `energy_facts` 相同。
7. 公开视图 `site_energy_cost`（站点电费估算）：`cost_valid_cny`、`cost_valid_and_suspect_cny`、`priced_valid_kwh`、`unpriced_valid_kwh`、`unpriced_valid_and_suspect_kwh` 等度量，`site_id`、`tariff_period`、`period_end` 维度；中文标题和说明写清楚「估算、只含电度电费、不含需量电费、以结算为准」。
8. 能耗序列（`energyType = electricity`）的每个点带 `cost`：`amountCNY`、`unpricedKWh`、按时段的 `periods[{periodCode, energyKWh, amountCNY}]`；供冷量没有 `cost`。查询服务多发一个按「时段 × 电价时段」分组的 Cube 查询。

### 读者

9. 能耗分析（估算电费、分时电费）、总览、报告（当月和未归档月份在页面上拼出来的部分）读能耗序列里的 `cost`。
10. 报告服务的月度快照从同一个能耗序列取每日电费和按时段电费；`energyCostStatus` 由 `unpricedKWh` 决定。
11. Agent 的能耗序列和同比工具原样带出电费，系统策略说明它是估算。
12. 优化建议以工作负载身份（与 #572 相同）向 IAM 取授权、读查询服务：最近一个完整且全部计价的日子的电费和用电量，二者来自同一个能耗序列点。
13. M&V 的节省金额：每个核验小时的避免电量 × 该小时的平均电价（该小时站点用电的电费 ÷ 已计价电量），电价来自查询服务；该小时没有已计价电量时记为未计价小时，与现在相同。

## 切片与 PR

1. **电价窗口与 Cube 电费**：`tariffmodel` 展开窗口、Registry 接口、投影、ClickHouse 表与视图、Cube cube/视图、能耗序列带 `cost`、OpenAPI。验收：松雅轩 2026-09 的月电费与现有报告快照一致。
2. **网页、报告、Agent 读同一个电费**：删掉浏览器和报告服务的计价。验收：能耗分析、总览、报告在 1440px 下用真实数据看过，数字与切片 1 一致。
3. **优化建议和 M&V**：两者改读查询服务，退役 `energy_cost` 指标和 `tariffmodel.Rates`/`Covering`。验收：服务器上重新生成的优化建议和 M&V 核验金额与改造前一致（边界都在整点）。

## 测试接缝（已与用户确认）

1. `tariffmodel` 展开窗口：工作日、周末、版本切换、夏令时时区。
2. 投影把窗口写进 ClickHouse，代次切换后只露出新窗口（分析集成测试）。
3. 查询服务经 Cube 返回电费、按时段电费和未计价电量（分析集成测试）。
4. 网页读接口里的电费（e2e 测试桩）。
5. 服务器真实验收：松雅轩 9 月电费与报告快照一致；页面在 1440px 下看过。
