# 估算电费：只由 Cube 按电价窗口计算

问题单 #575（上级 #574，ADR 0023）。2026-10-17 和用户确认：电费由 Cube 算，不由查询服务、小时指标或浏览器算；优化建议和节能验证（M&V）一起改。三步都已完成并在服务器上验收。

以前电度电费在四处各算一遍：浏览器（`touEnergyCost`，按分钟把一小时拆到各时段）、报告服务、`energy_cost` 指标和 M&V（三者共用 `libs/tariffmodel`，整小时按小时开始时的电价）。三个站点的电价时段边界都在整点上，所以当时数字一致；一旦出现半点换时段，或电价换版本，就会各说各话。AI 助手那时还读不到电费。

## 定下来的做法

| 问题 | 做法 |
| --- | --- |
| 谁定义电费 | Cube。内部 cube 把站点总表的用电区间与「电价窗口」做 ASOF JOIN，逐条区间计价；公开视图 `site_energy_cost` 给出电费、已计价电量、未计价电量，可按电价时段拆分 |
| 为什么不是查询服务计价 | 读电费时只依赖 ClickHouse，不在每次读取时同步调用 Registry；电费是可以直接相加的数，按日、月、站点的汇总在 ClickHouse 里完成，能用 Cube 的缓存和预聚合；AI 助手的语义查询（#573）直接能问电费，权限沿用视图的行策略 |
| 电价窗口 | ClickHouse 26.3 的时区函数要求时区是常量，没法按每个电价版本的时区在 SQL 里判断时段。所以由 Go 把电价版本按它自己的时区、日类型展开成逐日的 UTC 窗口 `[开始, 结束)`，带时段代码和电度单价；同一版本内相邻同时段同单价的窗口合并（延长覆盖范围时从上次的终点另起窗口）。夏令时、将来的节假日日历都只在这一处处理 |
| 每条区间按什么时刻计价 | 区间结束时刻所在的窗口。与 Cube 把区间归入「结束时刻所在时段」的汇总规则一致；能耗区间中位数 2 秒、90% 不超过 60 秒（服务器实测），半点换时段自然算准，不再把一小时拆开 |
| 电价版本 | 与现在的 `LoadImportTariffs` 相同：站点电网进线（多条时取边界编码最小的一条）上，分配与版本都生效的那段时间，按当时生效的已发布版本计价。电价调整后窗口重算，已经算过的期间也跟着新窗口变（估算值，不是账单；账单仍以结算为准） |
| 币种 | 只支持 CNY；遇到其他币种的电价版本，同步电价窗口时明确报错，这个站点停下 |
| 质量 | 与能耗一致：`VALID_ONLY` 只计有效区间，`VALID_AND_SUSPECT` 再加可疑区间 |
| 缺电价 | 落在任何窗口之外的电量记为「未计价电量」，不按 0 元算；读者显示「部分时段没有电价」，与现在报告的 `UNPRICED_HOURS` 一致 |
| 谁写窗口 | 能源模块（`modules/energy`）里的电价窗口同步，和「把电表读数算成用电量」的程序一起跑在 `telemetry-worker` 里，用同一个后台服务身份（ADR 0017）向设备登记服务（Registry）取电价；Registry 为此加了一个内部接口，返回站点一段时间内的进线电价版本。后台服务的角色 `energy-projection` 加了 `tariff.read` |
| 需量电费 | 按月最大需量算，不属于电度电费，这次不动 |
| 退役 | 浏览器的 `touEnergyCost`/`touCostByLabel`、报告服务自己的计价、`energy_cost` 指标（`TARIFF_ENERGY_COST`）以及 `tariffmodel.Rates`/`Covering` 全部删除 |

## 怎么运作

### 同步电价窗口

1. 启动时和之后每 5 分钟一轮。需要计价的站点 = 最近 48 小时有站点总表用电区间的 `(tenant_id, site_id)`，再加上已经同步过的站点；窗口从站点最早的电价版本生效时刻铺到「今天 UTC 零点 + 4 天」，任何时区的今天和之后几天都有电价。
2. 向 Registry `GET /internal/v1/registry/sites/{siteId}/import-tariffs?before=`（`tariff.read` 授权）取这之前的进线电价版本，按生效时间排序：生效区间（版本与分配的交集）、时区、币种、各时段（日类型、起止本地分钟、电度单价）。没有分配电价的站点返回空列表。
3. 用 `libs/tariffmodel` 展开窗口。电价版本序列的摘要与上次相同、范围已覆盖，就什么都不写；摘要相同只是范围要往后延，就按当前代次追加新的日子；摘要变了，就写一个新代次的完整窗口，写完再记同步行。
4. `analytics.tariff_price_windows_visible` 只露出每个站点最新同步行指向的代次，所以新代次是写完才切换；旧代次随后删除。
5. Registry 出错、币种不是 CNY 或时区无效时，该站点这一轮失败、不写同步行，其他站点照常；已有窗口保持不变。一轮里有站点失败，就记一次失败日志和计数（带各站点的错误）。每次写新代次都用新的代次号，失败那次写下的窗口不会混进下一次，之后成功的同步会删掉它们。

### Cube 与查询服务

6. 内部 cube `site_energy_cost_facts`：站点总表（`accounting_scope = 'SITE'`）用电区间 ASOF LEFT JOIN 可见窗口（同租户、同站点、`period_end >= window_start`），`period_end < window_end` 时取该窗口的单价和时段代码，否则未计价。两侧都先按站点过滤（`FILTER_PARAMS`），行策略与 `energy_facts` 相同。
7. 公开视图 `site_energy_cost`（站点电费估算）：`cost_valid_cny`、`cost_valid_and_suspect_cny`、`priced_valid_kwh`、`unpriced_valid_kwh`、`unpriced_valid_and_suspect_kwh` 等度量，`site_id`、`tariff_period`、`period_end` 维度；中文标题和说明写清楚「估算、只含电度电费、不含需量电费、以结算为准」。
8. 能耗序列（`energyType = electricity`）的每个点带 `cost`：`amountCNY`、`unpricedKWh`、按时段的 `periods[{periodCode, energyKWh, amountCNY}]`；供冷量没有 `cost`。查询服务多发一个按「时段 × 电价时段」分组的 Cube 查询。

### 谁读电费

9. 能耗分析（估算电费、分时电费）、总览、报告（当月和未归档月份在页面上拼出来的部分）读能耗序列里的 `cost`。
10. 报告服务的月度快照从同一个能耗序列取每日电费和按时段电费；`energyCostStatus` 由 `unpricedKWh` 决定。
11. AI 助手的能耗序列和同比工具原样带出电费，提示词里说明它是估算。
12. 优化建议以自己的后台服务身份（和 #572 的报告服务一样）向权限服务 IAM 取授权、读查询服务：站点本地日的最近 7 天里，最近一个已结束、数据已到齐（`period_end` 不晚于数据截至时间）且全部计价的日子，电费和用电量来自同一个能耗序列点；固定下来的输入记下这一天、数据版本和数据截至时间。优化服务读站点时区（迁移 027）。
13. 节能验证的节省金额：每个核验小时的避免电量 × 该小时的平均电价（该小时站点用电的电费 ÷ 已计价电量），电价来自查询服务；该小时没有已计价电量时记为未计价小时，与现在相同。报告服务、优化服务和 M&V 都用 `libs/energyseries` 的后台服务客户端。

## 分三步做（都已完成）

1. **电价窗口和 Cube 电费**：`tariffmodel` 展开窗口、Registry 接口、同步程序、ClickHouse 表和视图、Cube 的 cube 和视图、能耗序列带 `cost`、接口定义。验收：服务器上松雅轩 2026-09 的电费是 ¥28,777.85，峰、平、谷的拆分和报告快照第 5 版一致。
2. **网页、报告、AI 助手读同一个电费**：删掉浏览器和报告服务自己的计价。验收：能耗分析、总览、报告在 1440px 下用真实数据看过，数字和第一步一致。
3. **优化建议和 M&V**：两者改读查询服务，删掉 `energy_cost` 指标和 `tariffmodel.Rates`/`Covering`。服务器上当时没有优化运行和节能措施可以对比，就对比输入：查询服务给的每日电费和全部 31 个 `energy_cost` 指标结果逐日一致，抽查的 166 个小时里每小时电价都和电价表一致（时段边界都在整点）。服务器上 `energy_cost` 的定时任务已手工停用（已发布的绑定不能改，三个绑定还在，但不再运行）。

## 测试

1. `tariffmodel` 展开窗口：工作日、周末、版本切换、有夏令时的时区。
2. 同步程序把窗口写进 ClickHouse，切换代次后只露出新窗口（分析集成测试）。
3. 查询服务经 Cube 返回电费、按时段的电费和未计价电量（分析集成测试）。
4. 网页读接口里的电费（e2e 测试桩）。
5. 服务器上真实验收：松雅轩 9 月电费和报告快照一致；页面在 1440px 下看过。
