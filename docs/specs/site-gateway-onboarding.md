松雅轩空调机房的 Node-RED 网关（iotrouter Edge Computing Gateway，Node-RED 4.0），RS485-1（`/dev/ttyAS3`，9600 8N1）：

2026-10-14 用户请我先自行定义对应关系，依据现场系统图、ThingsBoard 大屏标签和 6 月旧设备的通道编号暂定：t1 公共冷却水进水、t2 公共冷冻水进水、t3–t10 依次为 A–D 机组的冷冻水出水和冷却水出水、t11 室外冷却水回水、t12 室外冷却水出水、t13/t14 A/B 冷却塔水温、t15 室外环境、t16/t17 总冷冻水回水/供水、t18/t19 总冷却水回水/供水、t20 备用；1–4 号电表为 A–D 机组电表，流量计为总冷冻水流量。A–D 机组登记为资产，电表绑定到各自机组，机组出水温度描述对应机组。ET1010 预留做控制，登记为控制模块，目前只读回 16 路通道状态；下发控制需要平台指令下行接到 Node-RED，另行设计。现场确认后改站点文件重跑即可，数据不受影响。

## 定下来的做法

| 问题 | 做法 |
| --- | --- |
| 怎么接入 | 网关直接按接入服务（Connectivity）规定的 MQTT 格式上报（ADR 0013、0015）：主题 `hvac/v1/<网关 ID>/up/telemetry`，信封 2.0；网关里的设备名就是平台的 source key，点位代码只用小写字母、数字和下划线 |
| 站点登记 | `scripts/site-onboarding.mjs <站点文件>`：按 `deploy/sites/*.site.json` 写入站点、机房、网关、设备、source key、点位和遥测在线与新鲜度策略，与模拟器种子同一套表，可重复执行 |
| 网关身份 | 私钥在网关本机生成（Node-RED「平台·证书」标签页），只把证书签名请求交给平台，用一次性码换取证书；证书 90 天，2027-01-12 到期 |
| 公网入口 | 宿主机 nginx 在 8884 四层原样转发到 Mosquitto（127.0.0.1:18883），双向 TLS 由 Mosquitto 校验；腾讯云安全组和 ufw 都放行 8884 |
| 未接探头 | 温度原始值正好为 0 视为未接探头，作为无效读数上报（质量位非 0），不当作 0 °C |
| 序号 | 信封（网关每次上报的一个 JSON 包，里面可以有多台设备的读数）的 `sequence` 取毫秒 × 1000 加计数，重启后仍递增（平台丢弃不递增的消息） |
| 历史 | `scripts/thingsboard-history-import.mjs`：先从 ThingsBoard 导出 CSV，再经 Telemetry Runtime 的历史回放通道逐条写入，数据集 `01a14000-7000-7000-8000-000000000001`；窗口截至平台开始收实时数据的 2026-10-14T10:26:30Z；每台设备一个分区按时间顺序写入，重跑按重复拒绝，不会写两份 |

## 切换步骤

1. 已完成：站点登记、网关证书、8884 入口、Node-RED 增加「平台·形成信封 → 平台·QoS1」分支，与 ThingsBoard 分支并行。
2. 历史导入完成后，逐台核对平台与导出文件（即 ThingsBoard 的数据）的条数和时间范围。
3. Node-RED 的耐久 Outbox（网关上存待发消息的本地队列，断网时先存着、恢复后再发）改为发往平台：各设备函数 →「平台·形成信封」→「Outbox·形成事件」→ 耐久 Outbox →「平台·QoS1（耐久）」，删除 ThingsBoard 的 MQTT 连接和临时直发（2026-10-14 已完成，切换时积压的 13 条 ThingsBoard 格式记录被平台以无权主题丢弃并确认，没有进入平台数据）。
4. 停 ThingsBoard（2026-10-14 已停止并关闭自启，数据卷和 `/opt/backups/thingsboard/` 保留；用户要求不必等历史导入结束，导入读的是导出的 CSV）。宿主机 nginx 的 8883 转发和 ufw 的 1883、8883 规则已删除，只保留 8884。

## 能耗、电价与智能服务（2026-10-14 第二批）

| 问题 | 做法 |

| 总用电 | 现场没有总电表。网关把四块机组电表的功率和累计电量相加，作为「空调总电表（四台机组合计）」（source key `ammeter-total`）上报；它的点位 source key 用 `hvac_meter.active_power` / `hvac_meter.energy`，实时页的冷站总功率读它。历史由 `thingsboard-history-import.mjs derive` 按同一规则从四块电表的历史合成后导入 |

| 冷量 / COP | 现场没有冷量表，网关计算「冷量计（总冷冻水流量 × 供回水温差计算）」：四台机组功率之和大于 20 kW 时为 1.163 × 流量 × (t16 − t18)（不小于 0），否则为 0（机组停机时水泵仍在循环，回水被管路和末端加热，那段温差不是制冷），按时间累加成累计供冷量，间隔超过 10 分钟不累加。供回水通道由 2026-08-22 至 10-14 的逐时历史判定：在所有通道组合里 t16 − t18 与四台机组功率之和的相关系数最高（0.96），高负荷（> 150 kW）时温差约 1.65 ℃、COP 中位数约 4.2。点位 source key 用 `btu_meter.*`，实时页的瞬时制冷量、COP 读它。站点文件 `energy.coolingMeter` 指向它：能源拓扑里是「冷站 → 建筑冷负荷」的冷量计，累计供冷量被算成每段时间的冷量，总览的今日供冷量、综合能效和能耗分析读这份能耗；逐时供冷量指标也绑它 |

## 已知问题

- 2026-10-14 12:19–12:31 UTC 约 12 分钟实时数据缺失：部署新函数时「平台·形成信封」的连线丢失，那段时间的采集没有进入耐久 Outbox，ThingsBoard 也已停用。
- 2026-10-14 13:52–15:09 UTC 约 77 分钟，除 4 号电表外所有设备没有实时数据：只重新部署了一个读取节点（4 号电表 UID4），七个读取节点共用 RS485 串口配置 `rs485-1`，其余六个从此全部超时，采集没有发生，补不回来。改任何读取节点之后，要用「重启流程」（Deployment-Type `reload`）让全部节点重连串口，并确认七个节点都显示 succeed。
- 4 号电表的累计电量原来读地址 64，一直是 0；2026-10-14 探测到实际在地址 60（当时 76938 kWh），网关改读 60，并减去这个读数，让平台上 D 机组的电量从原来的 0 接着累计，不出现一次 7.7 万 kWh 的跳变。之前的历史里 D 机组电量仍是 0，合计总表的累计电量因此少算了约三分之一。
- 备用通道 t8、t11、t14、t20 没接探头，网关不上报（函数里的 `SPARE`），站点文件里标 `"status": "INACTIVE"`，入网时写入停用状态。t14 从 2026-10-29 起确认没有探头：2026-10-14 03:26 起每分钟原始值都是 0、质量位非 0，平台也没收到从它复制的第二个室外温度。重跑 `scripts/site-onboarding.mjs` 时，点位的 `status` 按文件写回去（冲突更新用 `EXCLUDED.status`），所以停用会生效；接入只解析 `point_bindings_v1` 里状态为 `ACTIVE` 的点位，停用之后网关仍送来的 t14 对不上点位，不记成这条读数。
- 重跑 `scripts/site-onboarding.mjs` 只写站点文件里值真的变了的行：每个冲突更新带 `WHERE (现有列) IS DISTINCT FROM (文件里的值)`，值没变的行 `updated_at` 和 `revision` 都不动；变了的注册表行 `revision` 加 1，和注册表写入接口一致（`revision` 是乐观锁版本，接口按 `WHERE revision = $n` 更新并加 1，同时是变更事件的聚合版本）。遥测运行时的在线策略（`presence_policies`）和新鲜度策略（`freshness_policies`）值变了时 `policy_revision` 加 1（新建仍是 1；改回原值也是新修订号，不回退）：遥测给每条读数、在线状态和观测快照记下所用策略的修订号，修订号变了才能分出改前改后。另外两张表（`devices`、`observation_coverage`）没有修订号，只做到值不变不写。2026-10-29 之前每次重跑都会刷新所有行的 `updated_at`（那次部署后 67 条当前点位绑定和 81 个点位），而从 ACTIVE 改成 INACTIVE 的 14 条绑定 `revision` 仍是 1；这些历史值不回填。
- 2026-10-15 起遥测合格率降到约 33%：耐久 Outbox 每收到一条新记录，就把所有还没确认的记录再发一遍；温度消息复制出八台设备（`COPIES`）后连着形成九个信封，第一个被发八次，平台把后七次算作重复。2026-10-16 起网关一次采样只形成一个信封，复制出的设备、合计总表和冷量计都作为同一信封里的设备（接入格式允许一个信封最多 1024 台设备），部署后重复为 0。新增上报设备时也放进同一信封，不要再拆成多个。
- 温度通道：C、D 的四路按数据判定后改过（见「设备读数」）。A、B 的出水温度和冷却水进水等现场核对 t3、t4、t5、t9、t10 接在哪根管上以后再接回（#614）。改之前的历史里，四台机组的这几个温度点仍是按旧对照表复制的读数。
