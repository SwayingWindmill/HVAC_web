# 真实站点与网关接入：松雅轩

Issue #542。2026-10-14 与用户确认：接入 ThingsBoard 上那台真实网关，历史数据必须保留，确认无误后停用 ThingsBoard。

## 现场

松雅轩空调机房的 Node-RED 网关（iotrouter Edge Computing Gateway，Node-RED 4.0），RS485-1（`/dev/ttyAS3`，9600 8N1）：

| 网关里的设备名 | 采集 | 周期 | 平台点位 |
| --- | --- | --- | --- |
| `temperature` | UID 20 输入寄存器 30401–30420，÷10 | 60 s | `t1`–`t20`，°C |
| `waterflow` | UID 10 保持寄存器 1、5，换算为 m³/h、m/s | 60 s | `flow_meter`、`flow_velocity` |
| `ammeter-unit1`–`4` | UID 5、2、3、4 保持寄存器 36（÷10）、60（4 号为 64） | 300 s | `power_total` kW、`active_energy_total` kWh（累计量） |
| `et1010` | UID 31，16 路 | 60 s | `u11`–`u44` |

2026-10-14 用户请我先自行定义对应关系，依据现场系统图、ThingsBoard 大屏标签和 6 月旧设备的通道编号暂定：t1 公共冷却水进水、t2 公共冷冻水进水、t3–t10 依次为 A–D 机组的冷冻水出水和冷却水出水、t11 室外冷却水回水、t12 室外冷却水出水、t13/t14 A/B 冷却塔水温、t15 室外环境、t16/t17 总冷冻水回水/供水、t18/t19 总冷却水回水/供水、t20 备用；1–4 号电表为 A–D 机组电表，流量计为总冷冻水流量。A–D 机组登记为资产，电表绑定到各自机组，机组出水温度描述对应机组。ET1010 预留做控制，登记为控制模块，目前只读回 16 路通道状态；下发控制需要平台指令下行接到 Node-RED，另行设计。现场确认后改站点文件重跑即可，数据不受影响。

## 决定

| 决策 | 结论 |
| --- | --- |
| 接入路径 | 网关直接按 Connectivity 的 MQTT 契约上报（ADR 0013、0015）：主题 `hvac/v1/<网关 ID>/up/telemetry`，信封 2.0；网关里的设备名就是平台的 source key，点位代码只用小写字母、数字和下划线 |
| 站点登记 | `scripts/site-onboarding.mjs <站点文件>`：按 `deploy/sites/*.site.json` 写入站点、机房、网关、设备、source key、点位和遥测在线与新鲜度策略，与模拟器种子同一套表，可重复执行 |
| 网关身份 | 私钥在网关本机生成（Node-RED「平台·证书」标签页），只把证书签名请求交给平台，用一次性码换取证书；证书 90 天，2027-01-12 到期 |
| 公网入口 | 宿主机 nginx 在 8884 四层原样转发到 Mosquitto（127.0.0.1:18883），双向 TLS 由 Mosquitto 校验；腾讯云安全组和 ufw 都放行 8884 |
| 未接探头 | 温度原始值正好为 0 视为未接探头，作为无效读数上报（质量位非 0），不当作 0 °C |
| 序号 | 信封 `sequence` 取毫秒 × 1000 加计数，重启后仍递增（平台丢弃不递增的消息） |
| 历史 | `scripts/thingsboard-history-import.mjs`：先从 ThingsBoard 导出 CSV，再经 Telemetry Runtime 的历史回放通道逐条写入，数据集 `01a14000-7000-7000-8000-000000000001`；窗口截至平台开始收实时数据的 2026-10-14T10:26:30Z；每台设备一个分区按时间顺序写入，重跑按重复拒绝，不会写两份 |

## 切换步骤

1. 已完成：站点登记、网关证书、8884 入口、Node-RED 增加「平台·形成信封 → 平台·QoS1」分支，与 ThingsBoard 分支并行。
2. 历史导入完成后，逐台核对平台与导出文件（即 ThingsBoard 的数据）的条数和时间范围。
3. Node-RED 耐久 Outbox 改为发往平台：各设备函数 →「平台·形成信封」→「Outbox·形成事件」→ 耐久 Outbox →「平台·QoS1（耐久）」，删除 ThingsBoard 的 MQTT 连接和临时直发（2026-10-14 已完成，切换时积压的 13 条 ThingsBoard 格式记录被平台以无权主题丢弃并确认，没有进入平台数据）。
4. 停 ThingsBoard（2026-10-14 已停止并关闭自启，数据卷和 `/opt/backups/thingsboard/` 保留；用户要求不必等历史导入结束，导入读的是导出的 CSV）。宿主机 nginx 的 8883 转发和 ufw 的 1883、8883 规则已删除，只保留 8884。

## 能耗、电价与智能层（2026-10-14 第二批）

| 决策 | 结论 |
| --- | --- |
| 总用电 | 现场没有总电表。网关把四块机组电表的功率和累计电量相加，作为「空调总电表（四台机组合计）」（source key `ammeter-total`）上报；它的点位 source key 用 `hvac_meter.active_power` / `hvac_meter.energy`，实时页的冷站总功率读它。历史由 `thingsboard-history-import.mjs derive` 按同一规则从四块电表的历史合成后导入 |
| 能源拓扑 | 电网 →（总表）→ 空调机房 →（各机组电表）→ A–D 机组：总表计入站点合计，机组电表是其中的分项 |
| 指标 | 绑定租户已有的已发布指标：`hourly_energy`、`daily_energy`（读总表）、`energy_cost`（按电价折算逐时用电）、`device_hourly_energy`（每台机组电表），并按小时 / 每日计算；每月 1 日生成月度报告快照 |
| 电价 | 暂定深圳工商业分时电价：峰 1.03（10–12、14–19 时）、平 0.62（8–10、12–14、19–24 时）、谷 0.24（0–8 时）元/kWh，工作日与周末相同，按实际电费单修改站点文件后重跑 |
| 冷量 / COP | 现场没有冷量表，网关计算「冷量计（总冷冻水流量 × 供回水温差计算）」：四台机组功率之和大于 20 kW 时为 1.163 × 流量 × (t16 − t18)（不小于 0），否则为 0（机组停机时水泵仍在循环，回水被管路和末端加热，那段温差不是制冷），按时间累加成累计供冷量，间隔超过 10 分钟不累加。供回水通道由 2026-08-22 至 10-14 的逐时历史判定：在所有通道组合里 t16 − t18 与四台机组功率之和的相关系数最高（0.96），高负荷（> 150 kW）时温差约 1.65 ℃、COP 中位数约 4.2。点位 source key 用 `btu_meter.*`，实时页和总览的制冷量、COP 读它 |
| 智能层 | 服务器启用报告、节能、预测、诊断、优化 5 个服务（`single-lite` 档位、`--intelligence`）；Operations Agent 需要大模型密钥，暂不启用 |
| 历史指标 | `scripts/site-metric-recalc.mjs <站点文件> --from --to` 先算读点位的指标，再算依赖其它指标的电费 |

## 已知问题

- 2026-10-14 12:19–12:31 UTC 约 12 分钟实时数据缺失：部署新函数时「平台·形成信封」的连线丢失，那段时间的采集没有进入耐久 Outbox，ThingsBoard 也已停用。
- 4 号电表的累计电量寄存器（地址 64）一直读 0，功率正常，所以合计总表的累计电量少了 D 机组。需要现场确认地址。
- 温度通道按历史读数归类（冷冻水侧：t1–t4、t8、t10、t17、t19；冷却水侧：t5–t7、t9、t12；t13 冷却塔水温、t15 室外环境），不再分到具体机组：A 机组在历史里从未运行，其余三台总是同时运行，各通道随负荷同步变化，无法区分归属。现场确认后改名。

## 待办

- 平台 MQTT 服务器证书只有 `mqtt-broker` 这个名字，Node-RED 所用的 MQTT 库会用连接地址覆盖校验名，所以网关按 IP `139.199.58.47` 连接。应为 Mosquitto 签发带公网域名的证书，之后改回域名。
- 证书续期：2026-12-29 起可以续期。网关需要用当前证书调用 `/gateway/v1/renew`，在「平台·证书」标签页加续期流程。
- 能耗页面所需的能源拓扑、指标和电价，在确认点位含义后补齐。
