# 模拟冷站

用来在没有真实现场时，从设备一直到页面把整个平台跑一遍：模拟器像真的冷站一样运转、按真实网关的协议发数据，平台照常接收、算能耗、报警、诊断、开工单。2026-08 按问题单 #320–#330 定下，代码在 `tools/eg8200-simulator/`。冷站模型、场景、故障、ATV630 模拟从站和协议验收、历史导入都已实现；现场控制层里的安全 / 联锁控制器、现场清单和群控还没有（见 ADR 0012）。

## 它能做什么

- **模拟一个冷站**：冷水机组、冷冻水泵、冷却水泵、冷却塔、电表、冷量计和气象站，按工程上可信的关系运转：温度、流量、功率、冷量互相对得上，启停和调速有过程，不是瞬间跳变。不追求厂家级的精度。
- **按真实时间运行**（1 倍速），读数的时间就是当前时间。要几周的历史，用单独的历史导入（见下）。
- **按场景改变外部条件**：场景只有三个输入，室外干球温度、湿球温度、整个冷站的冷负荷（kW）。两种模式：固定值（`STATIC`），或者按时间一步一步变（`SCENARIO`）。每一步的值保持到下一步，不插值、不循环，最后一步的值一直保持。场景用 JSON 写（`configs/scenario-daily-a.json` 等），CSV 只能写一串按时间排的步骤。缺了必需的输入就报错，不用默认值。只检查真实的规则：数值有限、湿球温度不高于干球温度、冷负荷不为负、模式的格式对、步骤按时间顺序；不设人为的最长时长或负荷上限。
- **模拟故障**：故障只改变设备的物理表现，例如冷冻水泵变频器卡在高频：给它更低的目标，它仍然高速运转，流量变大，供回水温差按物理关系变小。模拟器不直接写告警或诊断结论。
- **用真实协议对接**：施耐德 ATV630 变频器（冷冻水泵用）有一个真实的 Modbus/TCP 模拟从站（`cmd/eg8200-virtual-atv630`），平台的 Modbus 主站和 ATV630 设备驱动（`libs/edgecontrol/atv630.go`）通过真实的 TCP 连接去读写它，以后接真设备用同一套驱动代码。
- **导入历史**：`cmd/eg8200-history-replay` 用同样的物理模型生成过去时间的读数，经遥测的历史导入（`HISTORY_REPLAY`）写进历史；本地用 `scripts/local-history-replay.mjs` 调它。

## 必须守住的规则

- **现场到云端只走 MQTT。** 不采用 OpenEMS 的后端 WebSocket；内存里直连的模拟路径只用于快速验证物理和控制，从不作为正式环境的兜底。
- **模拟器只产生「设备读数」。** 它不直接写遥测的当前状态，也不写告警、诊断、预测、优化、通知或工单。这些都由平台各自的模块根据读数算出来，和真实站点一样。
- **只在开发和验收环境里跑。** 正式部署不启动模拟器，也不在真实数据断了时拿模拟数据顶上。
- **页面不知道数据来自模拟器。** 站点、设备、读数、告警、工单里都没有「是否模拟」的字段，也没有专门给模拟器的接口、页面或权限。数据缺了就显示缺了，页面不自己补。
- **设备和点位用平台登记的那一套。** 模拟器不建自己的设备身份；寄存器地址、数据类型、倍率、字节序这些写在设备模板里，场景和页面里都不写。
- **设备模板发布后不改。** 真设备证明某个地址写错了，就发布一个新版本、明确地切过去，不加地址别名、不同时试两个地址。「用模拟从站验证过」和「用真设备验证过」是两回事，没有真设备就不能说验证过。
- **模拟器不发布自己的状态版本号。** 设备状态版本号只由遥测给出。
- **工单从告警开。** 运维人员在告警上点「创建工单」，工单的来源是那条告警；没有「来自模拟器」的工单。

## ATV630 的第一版

- 依据施耐德《Embedded Ethernet Manual》EAV64327 第 03 版和《Communication Parameters》EAV64332 4.6 版（2026-05-01），固定不变。
- 只用内置 Modbus TCP、CiA402/DriveCom 控制方式，命令和频率给定不分开；不自动识别、也不退回 I/O 控制方式。
- 只读写最少的几个地址：状态字 ETA 3201、实际频率 RFR 3202、最后故障 LFT 7121、命令字 CMD 8501、频率给定 LFR 8502。功率、电流、转矩、PID、温度这些以后再加。
- 平台发给它的命令是「启动、停止、复位故障、设定频率」，由驱动翻译成 CiA402 的命令字，控制逻辑不直接拼命令字。只有状态字表明当前有故障时，才把 LFT 当作「当前故障码」；否则那只是上一次的故障。

## 第一个验收场景：冷冻水泵卡在高频

1. 夏季场景下冷站正常运行，读数经 MQTT 进入遥测，总览和能耗页面照常显示。
2. 加上「冷冻水泵变频器卡在高频」的故障：实际频率和流量升高，供回水温差变小。
3. 告警模块按它自己的规则报「冷冻水回水温度过低」（验收用的规则版本：机组运行、制冷量不低于额定 30%、回水温度不高于 10.5 ℃ 持续 5 分钟就报；回到 11.5 ℃ 以上或机组停机就清除）。故障诊断按低温差规则（门槛 5 ℃，用冷量计的供回水温度）给出诊断结论。
4. 运维人员在告警上开工单。
5. 去掉故障，频率、流量、温度按物理过程恢复，告警清除，下一次诊断结论为正常；以前的告警和诊断记录都保留，工单不会自动完成。

告警和诊断的门槛写在有版本的规则里，不写死在代码里。

## 历史导入的规则

- 采样时间是历史时间，收到时间是真实的导入时间。点位用采样时间那时生效的版本；导入程序要有当前有效的授权。第一版只导入设备的点位。
- 照常做类型、单位、范围等校验，只跳过「数据太旧」的判断（导入的本来就是旧数据）；不为导入加新的质量等级。
- 只写历史，不改当前状态：不替换最新读数、不发在线信号、不重新计算设备快照、不改状态版本号，即使这个点位还没有最新读数。
- 一次导入有一个固定的批次号（UUIDv7），中途重试或重启也不会重复写入；每条读数的编号由批次号、设备和顺序号算出来。
- 一次请求只导入一条读数，导入程序自己控制并发；批量导入等实测需要时再做，并且不改变「一条一条」的含义。
- 导入只写到遥测历史为止。能耗和指标照常从历史里算；预测和优化的输入由服务端自己从历史里取，导入程序不直接写它们的表。

## 怎么测

- **模拟器本身**：一个确定性的测试，证明场景加上命令和故障，设备状态和读数在物理上说得通，包括卡在高频和恢复。
- **协议**：真实的 TCP 连接上，平台的 Modbus 主站和 ATV630 驱动对着模拟从站跑一遍「读 → 换算 → 控制决定 → 写 → 设备反应 → 再读回来」（`scripts/run-atv630-protocol-acceptance.mjs`）。
- **从头到尾的业务验收**：在 WSL 单机部署上跑上面那个验收场景，用真实的服务、数据库、MQTT 和页面。只靠内存里的测试不算完成。
- **历史导入**：导入一批读数，检查历史和下游能看到，当前最新读数、在线状态和状态版本号都没变；同一批重导不重复（`scripts/run-historical-replay-integration.mjs`）。

## 不做

- 厂家级的机组或压缩机模型、流体仿真。
- 通用的模拟插件框架、脚本语言，或者加速的实时模拟、自动循环的场景。
- 场景里加人员在室、建筑热负荷模型。
- BACnet、OPC UA 的模拟，以及通用的多协议框架，等真有第二种协议再说。
- ATV630 的全部参数、I/O 控制方式。
- 批量导入、按资产导入，或者导入程序直接写 ClickHouse、能耗、指标、预测、优化。
- 照搬 OpenEMS 的 OSGi 和组件框架（OpenEMS 是设计参照，不是依赖）。
