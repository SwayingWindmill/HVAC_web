# 0024 小程序的登录会话放在 Authorization 头里

状态：已采纳（2026-10-21，#664）

## 背景

网页登录靠浏览器跳转（OIDC 授权码 + PKCE）和一个 HttpOnly cookie；因为浏览器会把 cookie 带在任何请求上，哪怕请求是别的网站发起的，所以网页改数据时还要核对页面来源（`Origin`）和 CSRF 令牌。微信小程序跟不了这些跳转，`wx.request` 也不会替它保存 cookie，发出的请求也没有网页来源。

## 决定

- 小程序在自己的页面里填账号密码，交给网关的 `POST /api/v1/auth/app/sessions`。网关在内网替它调身份服务的 `/app/login`（开了验证码的再调 `/app/mfa/totp`），带上和网页登录一样的客户端、回调地址、state、nonce 和 PKCE 挑战，再像网页回调一样拿授权码换 ID 令牌、建登录会话。密码规则、锁定、停用和验证码都是身份服务原来那一套。
- 会话记下它是给谁发的（`gateway.sessions.client`：`BROWSER` 或 `MINI_PROGRAM`）。网页的会话只认 cookie，改数据仍要 `Origin` 和 CSRF 令牌；小程序的会话只认 `Authorization: Bearer` 头，不要这两样，因为别的网站没法让浏览器替它加上这个头。拿错了方式出示的会话一律当作无效。
- 撤销、停用账号、退出、过期和空闲超时对两种会话一样。
- nginx 不对外转发 `/identity/app/`，只有网关在内网调得到。

## 放弃的做法

- **内嵌网页登录（web-view）**：要企业主体的小程序和业务域名，网页又是按桌面做的。
- **小程序自己走一遍跳转、手动带 cookie**：`wx.request` 自动跟随跳转、读不到中间的 cookie；改数据时也拿不出网页来源。
- **只用微信登录（`wx.login`）**：平台没有自助注册，账号由管理员建；微信编号只能绑定到已有账号，第一次仍要账号密码；绑定以后可以微信一键登录（`POST /api/v1/auth/app/sessions/wechat`，同样由网关在内网调身份服务、换授权码）。

## 后果

- 小程序的会话令牌存在小程序自己的本地存储里；谁拿到它，就能在有效期内以那个人的身份读数据，和拿到网页 cookie 一样。退出、撤销或停用会让它立刻失效。
- 身份服务的 `/app/login` 在内网不核对调用方是谁，和对外开放的 `/login` 一样靠锁定挡住猜密码；它发出的授权码只有拿着 PKCE 校验码的网关换得了。
- 以后新加的改数据接口，核对 CSRF 时用 `session.needsBrowserProof()`，不要只看有没有 cookie。
