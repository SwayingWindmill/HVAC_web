# 0031 设备告警按站点路由发给值班人员，没人确认就升级

状态：提议（2026-11-05）。补充 ADR 0026「设备告警改发企业微信自建应用」那一段：写明怎么发、发给谁、什么时候升级。

## 背景

2026-11-01 北京时间 14:26 前后松雅轩网关断线，「网关上报中断」响了，没有人收到也没有人确认；同一天 20:34 那次断线之后，二十多条零散告警到 11-04 也没有一条被确认（#749）。原因：

- Alertmanager 的接收方是空的，而且它只管平台自己的告警，不管设备告警。
- 设备告警只靠小程序的一次性订阅提醒。点一次「允许」只能发一条，用完就悄悄发不出去（ADR 0026）。
- 没有升级：第一个人没看到，就没有第二个人知道。
- 网关断线时，它引起的读数长时间没有更新、一动不动、数据质量告警一起发，值班人员要自己拼出原因。

## 决定

1. **设备告警由通知模块直接发，不经过 Alertmanager。** Alertmanager 只认 Prometheus 的告警，没有确认这一步，也不知道告警属于哪个站点。设备告警的确认已经在告警模块里（网页、小程序、网关接口），升级要看的就是它。告警模块在改变告警的事务里写待发事件，本次加上第一次确认和恢复两种。
2. **路由按站点写在 Git 里，联系方式不进 Git。** `deploy/sites/<站点>.alarm-routing.json` 只写收件人编号、等级、渠道、等待、升级时间、免打扰和限流；编号对应的邮箱和企业微信账号在服务器的 `recipients.json`。路由改动可以评审，换人不用改代码。
3. **一个出公网的适配器持有所有渠道的密钥。** 已有的 `wecom-alert-adapter` 多一个带令牌的 `POST /send`，支持 SMTP（QQ 邮箱）、企业微信自建应用和群机器人。通知模块（energy-api）不出公网，不读 SMTP 密码和企业微信 Secret。
4. **每条消息都有去重键，发送记录在通知库里**（`alarm_delivery_attempt`，开启并强制行级安全）。同一条消息只写一次；连不上就按 1、4、9 分钟重试，第 4 次仍失败就放弃并记下来；被拒的（没配好、地址不对、企业微信不认识这个人、IP 不可信）不重试。
5. **升级只看确认。** 第一条发出后，每一级到时间、告警还亮着、仍没有人确认，就发下一级。确认和恢复只告诉已经收到过的人。
6. **根因归并只做一层**：站点上「网关上报中断」亮着时，压住它会引起的那几类告警。不做 ThingsBoard 那样的告警传播树（#749 第 1、2 点另外做）。
7. **三档开关**：`off`（默认）、`dry-run`（决定、记录、升级都照做，只是不发）、`live`。开着时配置有错就不启动，不会悄悄谁都不告诉。
8. **规则长时间判断不了也报一条告警**（#749 第 3 点）：站点上有规则 `INDETERMINATE` 满 30 分钟（排除时间表外和本身就看数据的规则），报一条站点级「告警规则长时间无法判断」（警告），没有了自动恢复。它也受根因归并。

## 不选的做法

- **全部交给 Alertmanager**（把设备告警推成 Alertmanager 告警）：要么在两处各存一份确认，要么升级不知道有人确认过；还要把站点、租户和人的对照搬进 Alertmanager 配置。
- **通知模块直接连 SMTP 和企业微信**：energy-api 要出公网、要读所有密钥；适配器已经在 `alert-egress` 网络上，只多一个入口。
- **按值班表轮换**：现在一个站点只有一两个固定的人，先不做。

## 后果

- 企业微信自建应用要把服务器公网 IP 加进「企业可信IP」，换云（`docs/research/cloud-migration-options-2026-10.md`）时一起改。
- 适配器多连一个 `application` 网络，energy-api 才能访问它。它能读到 `recipients.json`（两者共用 `alarm-delivery/` 目录，为的是令牌只有一份）。
- 发送中途进程死掉，租约过期后会再发一次，可能重复一条：宁可重复也不漏。
- 重要及以上不受免打扰限制，半夜也会发。
- 企业微信跑稳一周后，按 ADR 0026 删掉小程序的订阅提醒。
