# 0026 2026-10 对标复查定下不做和推迟的事

状态：已采纳（2026-10-22）。修订 ADR 0013 第 6 节（通用规则）和第 8 节（通知和外发）。

## 背景

2026-08 按 ThingsBoard、OpenEMS、MyEMS 排的路线图里，有几项两个月后仍没有做，或者做法改了。2026-10 的对标复查（`docs/research/thingsboard-gap-review-2026-10.md` 第 5、6 节）把它们逐条列了出来。这里记下哪些不做、哪些推迟、为什么，以及什么时候重新考虑，免得以后有人照旧路线图把它们补回来。要补的事各有问题单，不在这里。

## 不做

| 事情 | 为什么 | 什么时候重新考虑 |
| --- | --- | --- |
| 通用规则：「自动化规则」页、网关的规则接口、`services/rule-runtime-service` 都删掉 | 规则能发布但从没有进程执行；告警和低温差诊断各有自己的规则，冷站用不到通用规则 | 出现告警和诊断都装不下的自动化需求时 |
| 统一外发投递：删掉 `services/outbound-delivery-service` | 写好以后从没有进程在跑；设备告警由通知模块直接发给值班人员，平台自身的故障由 Alertmanager 发邮件，两条路都不需要它 | 要接短信、邮件网关或第三方系统，而且需要重试记录和死信的时候 |
| 通知收件箱、通知规则和模板：删掉，网页的通知页像小程序一样直接读告警；通知模块只管把设备告警发到值班人员手上 | 服务器上从没配过规则，收件箱一直是空的；它唯一的出口就是上面删掉的外发投递 | 同上 |
| 通知模块自己记发送状态（发送中、已发、被拒），不交给统一的外发服务 | 外发服务不做了；发送状态本来就在通知库里 | 同上 |
| 小程序长期订阅消息 | 微信只向政务民生、医疗等公共服务领域开放长期订阅（见 `docs/research/cloud-migration-options-2026-10.md` 第 7 节），暖通告警拿不到；一次性订阅每点一次「允许」只能发一条，用完告警就悄悄发不出去 | 微信放开开放范围时 |

设备告警和每日运行结论改发企业微信自建应用的消息：值班人员都是自己公司的人，不用订阅、不限条数。企业微信接通并跑稳一周后，删掉小程序的订阅提醒，小程序继续用来看数据；接通之前小程序订阅提醒照旧。
| Kafka：删掉 `audit-owner` 拆分入口和 `outbox-relay` 里的 Kafka 代码 | 默认部署里操作记录已经走 PostgreSQL 发件箱，这两处没有部署 | 按 ADR 0013 第 13 节，容量或可用性的证据超过写明的门槛时 |
| API Key 和服务账号（2026-10-21 已删） | 网页和小程序从没用过；后台服务用后台服务身份（ADR 0017） | 要让第三方系统调平台接口时 |
| 一个人切换多个租户（2026-10-21 已删） | 接口一直被路由登记挡成 404，没人用过 | 出现第二个租户、并且有人要同时管两个租户时 |
| 租户配额和用量页面 | 只有一个真实租户 | 出现第二个租户时 |
| 告警的屏蔽和评论 | 值班人员现在只用确认和指派 | 值班人员提出要用时 |
| 碳排、能源计划和目标、工作日历（MyEMS 有） | 第一阶段的核心诉求由节能验证和站点对标覆盖 | 客户要碳排报告或用能计划考核时 |

## 推迟

| 事情 | 开始做的条件 |
| --- | --- |
| 真实站点登记改走登记模块的写接口（现在 `scripts/site-onboarding.mjs` 直接写表，没有并发冲突检查，也不留操作记录） | 接第二个真实站点之前 |
| 能耗按日、按月的汇总表 | 服务器上任何一次能耗查询的内存超过 1 GiB，或一个站点的数据满 6 个月 |
| 原始历史数据的保留期限 | 磁盘压力重新来自原始历史时（现在增长最快的告警判断记录已由 #651 只保留 30 天） |

## 后果

- ADR 0013 第 6 节的规则执行负责方、第 8 节的外发服务，以及边界表里的"规则""外发"两行不再成立；"通知"只负责把设备告警发到值班人员手上。
- 删除模块时，按冻结迁移的规则新增迁移删表，不改已执行的迁移。
