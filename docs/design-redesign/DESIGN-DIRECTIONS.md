# 重设计方向

日期：2026-10-13 · 阶段：设计研究（第二阶段）

依据：[DESIGN-RESEARCH.md](DESIGN-RESEARCH.md)（证据 R1–R24，模式 P1–P22）、[CURRENT-AUDIT.md](CURRENT-AUDIT.md)、[DESIGN-CONSTRAINTS.md](DESIGN-CONSTRAINTS.md)。

下面给出 4 个差异明显的方向和一个推荐组合。线框只是信息架构草图，**不是高保真设计**。所有方向都必须满足 DESIGN-CONSTRAINTS 的约束，尤其是 §1.3 的图表真实性规则：它们不是可选风格，所以不算作任何一个方向的“特色”。

---

## 方向 A：值班台（Operations Console）

**核心理念**：把产品当成值班人员的监视台。第一屏回答“现在是否正常、哪里不正常”，时间和状态是主轴。

**参考来源**：Datadog 的分面列表、状态页头、状态时间条和事件叠加（R18–R21）；Grafana 的插值与缺口处理、告警规则列表（R22、R24）；Vercel Observability 的阶梯图（R12）。

### 布局与信息架构

```
┌ 侧栏 ┬──────────────────────────────────────────────────────────┐
│ 运行 │ 中央机房 ▾   ● 实时   [过去 24 小时 ▾]          搜索  通知 │  ← 全局时间范围 + 站点 + 实时状态
│ 设备 ├──────────────────────────────────────────────────────────┤
│ 告警 │ 冷站系统图（主角，占 60% 高度）           │ 当前异常（分面）│
│ 能源 │                                          │ 严重 2  主要 0  │
│ 控制 ├──────────────────────────────────────────┤ 无数据 1        │
│ …    │ 状态时间条：冷机 ▇▇▇▁▁▇▇  水泵 ▇▇▇▇▇▇▇     │ ……              │
│      │ 功率 / COP 时序（指令和告警以竖线叠加）    │                 │
└──────┴──────────────────────────────────────────┴─────────────────┘
```

- 首页就是“运行”：系统图、状态时间条、带事件叠加的功率 / COP 曲线，右栏是带分面计数的当前异常。
- 全局时间范围放在顶栏，所有页面共用。
- 告警、设备、诊断都用 Datadog 式的左侧分面加表格；状态页头见 P15。

### 视觉风格

- 冷灰中性色，信息密度高：行高 32px，正文 13px，数字等宽。
- 浅色为默认，深色主题作为值班夜间模式正式支持。
- 颜色只给状态和数据；品牌色几乎不出现。
- 状态用实心标签（Datadog 风格），对比强。

### 为什么适合

PRODUCT §4.2、§4.3 的首要任务是“当前系统运行是否稳定、哪个异常最值得先处理”。值班人员是第一类用户。冷站是实时系统，时间轴和状态时间条比静态指标卡更能说明问题。

### 对现有组件的改造范围（较大）

- **新建**：全局时间范围控件、状态时间条、事件叠加层、分面面板。
- **重做**：`PlantDiagram` 成为首页主角；`PageHeader` 改为状态页头。
- **淘汰**：`MetricGrid` 的标配用法。
- 能耗类页面只按约束修图表，构图基本不动。

### 优点与缺点

| 优点 | 缺点 |
| --- | --- |
| 最贴近值班场景，异常可见性最好 | 对能源经理、业主不友好，电费、节能被挤到次要位置 |
| 图表最“工程化”，事件叠加对节能核算很有价值 | 信息密度高，新用户上手慢，中文长标签容易拥挤 |
| 和 Datadog / Grafana 用户的习惯一致 | 视觉偏工具化，商业“质感”主要来自克制，而不是品牌 |
| | 状态时间条和事件叠加需要新的数据查询组合，前端工作量大 |

## 方向 B：分诊工作区（Triage Workspace）

**核心理念**：平台的价值是把“需要人处理的事”处理完。所有待处理事项进同一个队列，每条有明确动作，处理完就消失。

**参考来源**：Linear 的 Triage、Inbox、分组列表、Peek 预览、上下文栏（R1、R2、R4、R5、R6）；Stripe 的右栏队列（R7）；Datadog 状态页头（R19）。

### 布局与信息架构

```
┌ 侧栏 ───────────┬───────────────────────────────┬─────────────────────┐
│ 待处理      7   │ 待处理                         │ 冷冻水低温差         │
│ 总览            │ [全部 7][告警 2][诊断 1]       │ ● 严重偏离 · 未认领  │ ← 状态页头
│ 运行            │ [工单 3][待审批 1]             │ BTU-METER-01 · 22:15│
│ 设备            │ ─ 严重 ──────────────── 2     │ [认领][转工单][搁置▾]│
│ 能源            │ ▲ 冷冻水低温差  BTU-01  22:15 │ ── 证据 ──           │
│ 节能            │ ▲ 冷机负载异常  CH-01   21:40 │ 温差 1.1 K / 阈值 3.5│
│ 报告            │ ─ 待审批 ────────────── 1     │ （带事件的趋势）     │
│ ─────           │ ◆ 停止冷水机    张三    09:02 │ ── 时间线 ──         │
│ 通知 · 集成 · 系统│                              │                     │
└─────────────────┴───────────────────────────────┴─────────────────────┘
       ↑ 空格预览，↑↓ 切换，单键动作（认领、转工单、搁置）
```

- 新增一级入口“待处理”，汇集：
  - 未确认 / 未认领的告警；
  - 近期诊断发现；
  - 待处理和受阻的工单；
  - 待审批或结果不明的控制指令；
  - 未处理的优化建议。
- 各类事项仍然由各自的 owner 和 API 提供，前端只负责汇总，不新建后端。
- 列表按严重度和类型分组，组头带计数。右侧是并排的详情栏（`?inspect=`）：状态页头 + 证据 + 时间线 + 动作。
- 总览变成“运行快照 + 待处理摘要”。原来的告警、工单页保留为历史台账和高级筛选。
- 队列为空时显示“运行平稳”，以及最近一次事件、近 7 天恢复情况等正向信息，解决审计里空页面的问题。

### 视觉风格

- 以列表为主：安静的中性底、细分隔线，几乎没有卡片。
- 状态用 Linear 式“形状 + 颜色”图标（P21）：▲ 严重、● 主要、◆ 待审批、○ 未开始、◐ 处理中、✓ 完成。
- 字号档少，层级靠字重和灰度。
- 键盘优先：显示快捷键提示，命令面板能直接执行动作。

### 为什么适合

PRODUCT §4.1 的闭环是“发现 → 定位 → 证据 → 判断 → 决策 → 执行 → 验证”。现在这条链被拆在告警、诊断、工单、控制 4 页（审计 §4）。B 方向把它收成一条可以连续处理的流，也天然容纳 AI 运维助手（PRODUCT §8）以后提出的建议。

### 对现有组件的改造范围（中等偏大，主要在信息架构）

- **新建**：待处理队列（汇总现有 query：`activeAlarmsQuery`、`siteFindingsQuery`、`openWorkOrdersQuery`、指令查询、`latestRecommendationQuery`）、键盘导航、统一的状态图标组件。
- **重做**：Sheet 改为并排详情栏；`AlarmInspector`、`WorkOrderInspector`、诊断详情统一为同一种“状态页头 + 证据 + 时间线 + 动作”结构。
- **保留**：`DataTable`（历史台账）、`Timeline`、`FactList`。
- 能耗类页面只按约束修图表。

### 优点与缺点

| 优点 | 缺点 |
| --- | --- |
| 最直接地解决“流程分散”和“空页面”两个大问题 | 信息架构变动最大，e2e 夹具和导航要大面积调整 |
| 和 PRODUCT 的闭环一致，为 AI 助手留出位置 | 各类事项的动作不同（告警确认 ≠ 工单流转 ≠ 指令审批），统一队列的交互设计难度高 |
| 列表型界面的商业质感容易做好（Linear 的经验） | 对“看能耗、看电费”的用户帮助有限，需要和别的方向组合 |
| 键盘操作对高频值班用户效率高 | 当前本地数据里告警和工单都是 0，验收需要夹具数据 |

## 方向 C：能效账本（Energy Ledger）

**核心理念**：把能源当钱来管。界面像一份可信的财务报表：数字清楚，口径清楚，“估算 / 核算 / 预计”分得很清楚。

**参考来源**：Stripe 的整页应用、图表布局、Chip 筛选、详情示意（R7–R11）；Vercel 的指标页签和未完成段虚线（R13）；Linear Insights 的“图 + 透视表”（R3）。

### 布局与信息架构

```
┌ 侧栏 ──────┬──────────────────────────────────────────────────────────┐
│ 首页       │ 今天                                    [日期范围 今日 ▾] │
│ 能源       │ 空调用电 1,377 kWh ↓4%   电费(估) ¥972   综合能效 1.49    │ ← 一行文字指标
│ 节能       │ ┌──────────────────────────────────────┐  需要处理         │
│ 运行       │ │ 用电（阶梯图，未完成时段虚线）         │  ▲ 冷冻水低温差   │
│ 运维       │ │                                      │  ◆ 1 条指令待审批 │
│ 报告       │ └──────────────────────────────────────┘  节能 · 本月      │
│            │ 分时电费   峰 ¥620 · 平 ¥116 · 谷 ¥219    ¥0 已核算       │
│ ────       │ （单条比例条）                             建议 45 元/天    │
│ 平台       │                                                          │
└────────────┴──────────────────────────────────────────────────────────┘
能源模块：[用电][分项][需量][预测]  ← 页内页签，共享日期范围
```

- 侧栏按业务对象收敛成 6–7 个一级入口；“能源”内部用下划线页签切换用电 / 分项 / 需量 / 预测，共用一个日期范围。
- 首页按 Stripe 的构图：一行文字指标 + 主图（2/3）+ 右栏“需要处理 / 节能”（1/3）。
- 节能项目和月度报告做成文档式详情页：区块标题、数字、口径注释，没有卡片外框。
- 所有金额和电量统一数值排版：千分位、单位小号灰色、估算标记位置固定。

### 视觉风格

- 白底，留白充足，区块之间靠大间距和一条分隔线，几乎不用卡片和阴影。
- 品牌色只用在选中页签、链接和主按钮；数据色单一主色加 1–2 个辅色。
- 页面标题大且粗，数值排版有明确的“财务感”（等宽数字、对齐、千分位）。
- 涨跌颜色按指标的好坏方向着色（用电上升是坏事），不照搬 Stripe 的“涨一律绿”。

### 为什么适合

刚上线的分时电费估算（`feat/tou-energy-cost`）、节能核算（IPMVP 选项 C）、月度报告和站点对标，都是“钱和证据”的问题。能源管理人员和业主是付费决策者，商业 SaaS 的质感对他们最重要。这个方向和现有 shadcn 基础的距离也最近，风险最低。

### 对现有组件的改造范围（中等，主要在视觉层和能源模块）

- **新建**：一行文字指标组件、日期范围 chip、Chip 筛选、行内比例条排行、文档式区块。
- **重做**：`MetricTabsChartCard`（连续时间轴、阶梯图或柱图、未完成段虚线）、`TouCostCard`（单条比例条，峰时段不用警告色）、`PageHeader`（大标题 + 页签）。
- **合并**：能耗、分项、需量、预测 4 个页面合为“能源”模块。
- **淘汰**：`MetricGrid` 标配用法、卡套卡。
- 运维页面只换皮。

### 优点与缺点

| 优点 | 缺点 |
| --- | --- |
| 商业 SaaS 质感最强，最容易让付费决策者接受 | 留白多，信息密度下降，值班人员同屏信息变少 |
| 改造风险最低，延续 shadcn 基础和现有组件 | 对“流程分散”只做了右栏汇总，没有根本解决 |
| 能源模块合并后，导航和期间控件的不一致一次性解决 | 容易做成“好看的 Stripe 仿品”，需要自己的数值和状态语言来建立识别度 |
| 文档式详情天然适合节能核算和报告的证据展示 | 实时运行页的价值在这个方向里不突出 |

## 方向 D：系统画布（Plant Canvas）

**核心理念**：冷站本身就是导航。界面以系统图为中心，设备、能流、告警、趋势都从图上的对象展开。

**参考来源**：本项目已验收的冷站两环路示意图（PlantDiagram）；Datadog 的小倍数图和状态时间条（R20），用于对象展开后的证据；Linear 上下文栏（R5），用于对象侧栏。**同赛道产品（Willow、KODE Labs）的界面这次拿不到可核实的截图**（见 DESIGN-RESEARCH §0.3），所以这个方向的行业证据最弱。

### 布局与信息架构

```
┌ 侧栏 ┬────────────────────────────────────────────────┬──────────────────┐
│      │ [运行][能耗][告警]  ← 图层切换                  │ CHILLER-01       │
│      │  冷却塔 ─→ 冷却水泵 ─→ 冷水机组 ─→ 冷冻水泵 ─→ 末端 │ ● 运行 · 在线    │
│      │   (每个节点显示该图层的关键量：功率 / kWh / 告警数)  │ 141 kW · COP 5.7 │
│      │                                                │ 24h 趋势         │
│      │ 底部：选中对象的时间条与趋势                     │ 告警 0 · 工单 0  │
└──────┴────────────────────────────────────────────────┴──────────────────┘
```

- 系统图有多个图层：
  - 运行（状态、读数）；
  - 能耗（各设备 kWh 和占比，取代分项能耗页）；
  - 告警（异常设备高亮）。
- 选中设备后，右侧是设备上下文：状态、读数、趋势、告警、工单、可用控制；底部是该对象的时间条。

### 视觉风格

- 画布型：大面积留给系统图，周边 UI 极简。
- 工程示意的视觉语言：管段、节点、流向，但遵守 DESIGN.md 的规定，不做大屏或 HMI 风格。
- 深浅两套主题都需要精调，画布对色彩要求最高。

### 为什么适合

冷站是一个物理系统，工程师的心智模型就是“塔 → 泵 → 机 → 泵 → 末端”。系统图已经是本产品最有辨识度的资产（审计中唯一不像模板的页面）。

### 对现有组件的改造范围（大，且偏定制）

- **新建**：画布图层系统、节点选中态、对象上下文栏、能流图层（必须遵守“不伪造能流分配”，只显示有分表的设备）。
- **重做**：`PlantDiagram` 从示意图升级为可交互的主导航。
- 其他页面仍然需要另一个方向来覆盖（报告、节能、系统管理不适合画布）。

### 优点与缺点

| 优点 | 缺点 |
| --- | --- |
| 辨识度最高，最不像模板 | 行业证据最弱，风险最高 |
| 工程师上手直观 | 目前只有冷站一种系统，扩展到空调箱、末端或多站点时画布难以复用 |
| 把分项能耗、设备、告警的空间关系一次讲清楚 | 容易滑向 DESIGN.md 明确拒绝的“大屏 / HMI”风格 |
| | 定制组件多，维护成本高；只能覆盖运行相关的页面 |

## 推荐：B 的信息架构 + C 的视觉语言 + A 的图表能力

单一方向都有明显短板：A 不照顾能源和钱，B 不照顾分析，C 不解决流程，D 证据不足。推荐组合如下，各部分职责不重叠：

| 层 | 采用 | 内容 |
| --- | --- | --- |
| 信息架构 | **B** | 新增“待处理”分诊工作区；告警、诊断、工单、指令的详情统一为“状态页头 + 证据 + 时间线 + 动作”；并排详情栏 |
| 视觉语言 | **C** | 白底留白、区块标题代替卡片、一行文字指标、Chip 筛选、行内比例条排行、文档式详情；“能源”合为一个模块并用页签切换 |
| 图表 | **A** | 连续时间轴、阶梯图 / 柱图、缺口断开、未完成段虚线（这些是约束）；再加事件叠加和状态时间条（这些是增强） |
| 实时运行 | 现有 PlantDiagram + **A** 的状态时间条 | 系统图仍是实时运行页的主角，D 的“图层”思路留作后续 |

这个组合下侧栏的草案（约 8 个入口，比现在少一半）：

```
待处理（计数）
总览
运行        —— 实时运行 + 设备（页签）
能源        —— 用电 / 分项 / 需量 / 预测（页签）
节能        —— 优化建议 / 节能项目（页签）
报告        —— 月度报告 / 站点对标（页签）
控制指令
──────
通知 · 集成 · 系统管理（平台区，固定在侧栏底部）
```

告警、工单的完整台账作为“待处理”的历史视图保留，控制指令单独保留一级入口，以突出它的高风险属性。

### 推荐方向的风险

- 信息架构变化会影响 e2e 夹具和导航测试，需要一次改干净（不留兼容跳转层）。
- “待处理”队列要汇总 5 类事项，各自动作不同，需要单独做交互设计。
- 当前本地数据里告警和工单为 0，评审要借助 e2e 夹具或评审构建。

## 进入下一阶段前需要你决定

1. **方向**：选单一方向，还是推荐组合？如果选组合，哪些部分要调整？
2. **品牌色**：保留青绿，还是重新定义（组合方案里品牌色只用于主按钮、选中态和链接，所以可以更克制）？
3. **中文字体**：
   - 可以自托管中文字体（例如思源黑体或 HarmonyOS Sans 的子集，会增加 1–3 MB 资源）；
   - 也可以只用系统字体栈。

   这直接决定字重层级能不能成立。
4. **信息架构范围**：是否接受合并页面和新增“待处理”入口？这会改 URL 和 e2e 夹具。
5. **深色主题**：作为正式支持的值班夜间模式（A 的主张），还是维持现状只做跟随？
6. **下一阶段的产出形式**：建议先做 2–3 个关键页面（总览、待处理、能源）的低保真线框和一套 token 草案，确认后再进入高保真和开发。
